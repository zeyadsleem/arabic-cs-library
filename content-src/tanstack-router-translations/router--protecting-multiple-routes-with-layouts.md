## ماذا سنتعلّم؟

في الدرس السابق حمينا صفحة واحدة، `/about`، بشرط مكتوب داخل ملفها: إن لم يكن في السياق مستخدم، ارمِ تحويلًا إلى `/login`. هذا حلٌّ صحيح لصفحة واحدة، لكنّه لا يتوسّع. كلّ صفحة جديدة تريد حمايتها تعيد كتابة الشرط نفسه، وأخطر من التكرار أنّ نسيانه مرة واحدة يكفي لتسريب صفحة كاملة.

الفكرة التي يثبتها هذا الدرس أنّ الحماية صفةٌ تُورَّث، لا شرطٌ يُنسخ. نُنشئ مسارًا أبًا لا مقطع له في العنوان، ونضع فيه التحقّق مرة واحدة، ثم نجعل كلّ مسار محميّ ابنًا له. فيصبح سؤال «هل هذا المسار محميّ؟» سؤالًا عن موضعه في الشجرة، لا عن محتوى ملفّه.

## الشرح

### أين يجب أن يقف الشرط؟

الصفحة المحميّة قد تجلب بياناتها من الشبكة، والجلب يحدث في المُحمِّل (loader). فإن وقف الشرط داخل المكوّن، بعد أن يكون المُحمِّل قد عمل، فقد تأخّرت الحماية: الزائر لا يرى المحتوى، لكنّ الطلب انطلق فعلًا. أمّا `beforeLoad` فمكانه قبل `loader` وقبل التصيير، ويستقبل الخصائص نفسها التي يستقبلها `loader`، ومنها `context` و`location`.

والخصلة التي تجعل الأب صالحًا لهذا الدور هي الترتيب: `beforeLoad` الخاصّ بالأب يُنادى قبل `beforeLoad` كلّ ابن من أبنائه، ورمي استثناء فيه يمنع تحميل الأبناء جميعًا. فالأب حاجزٌ واحد على مدخل مجموعة كاملة، لا شرطٌ مكرَّر في كلّ غرفة.

### إنشاء التخطيط المحميّ

ننشئ ملف `src/routes/_authenticated.tsx`:

```tsx
import { createFileRoute, Outlet, redirect } from "@tanstack/react-router";

export const Route = createFileRoute("/_authenticated")({
  component: RouteComponent,
  beforeLoad: ({ context, location }) => {
    if (!context.user) {
      throw redirect({
        to: "/login",
        search: {
          redirect: location.href,
        },
      });
    }
  },
});

function RouteComponent() {
  return <Outlet />;
}
```

الشرط في `beforeLoad` منقول كما هو من درس الحماية السابق: لا مستخدم في السياق ⇒ تحويل إلى `/login` ومعه عنوان الصفحة المقصودة في معامل `redirect`، ليُعاد الزائر إليه بعد الدخول. والمكوّن لا يعرض إلا `<Outlet />`، أي أنّه لا يضيف شيئًا مرئيًا: هو مكان عرض الابن فحسب. وهذا اختيار مقصود؛ لو أضفت شريط تنقّل أو عنوانًا هنا لظهر في كلّ صفحة محميّة، وهذا شأن تخطيط الواجهة لا شأن حاجز الأمان.

أمّا دلالة الاسم ففي الشرطة السفلية الأولى. في TanStack Router كلّ ملف أو مجلّد يبدأ اسمه بـ`_` يبقى في شجرة المسارات لكنّه لا يُسهم في بناء العنوان. فالأب موجود في الشجرة بمعرّف `/_authenticated`، لكنّ الزائر لا يرى هذا المقطع في شريط العنوان أبدًا. والبديل — أبٌ عادي له مقطع عنوان — كان سيفرض على كلّ صفحة محميّة عنوانًا مثل `/authenticated/about`، أي أنّه كان سيغيّر واجهة الموقع لا حمايته فقط.

في سجلّ الفرع يظهر أنّ الملف `src/routes/about.tsx` أُعيدت تسميته إلى `src/routes/_authenticated.tsx`. هذا أثرٌ للمسار العملي الذي سلكه المؤلف: أخذ ملف الصفحة المحميّة، ونزع منه واجهة الصفحة وأبقى الشرط، فصار الملف حاجزًا. ولهذا كان لا بدّ من ملف جديد للصفحة نفسها.

### إعادة `about` ابنًا للتخطيط

```tsx
import { createFileRoute, redirect } from "@tanstack/react-router";

export const Route = createFileRoute("/_authenticated/about")({
  component: RouteComponent,
  // beforeLoad: ({ context, location }) => {
  //   if (!context.user) {
  //     throw redirect({
  //       to: "/login",
  //       search: {
  //         redirect: location.href,
  //       },
  //     });
  //   }
  // },
});

function RouteComponent() {
  return (
    <div className="p-2 bg-pink-600">
      <h3 className="text-xl font-bold">About</h3>
    </div>
  );
}
```

اسم الملف `_authenticated.about.tsx` يقرأه المولّد سطرًا واحدًا: النقطة تفصل الأب عن الابن في أسلوب المسارات المسطّحة، فالمعرّف `/_authenticated/about`. أمّا العنوان فيبقى `/about`، لأنّ مقطع الأب لا يُسهم فيه. لا رابط في التطبيق يحتاج تعديلًا، ولا إشارة مرجعية في أيّ `<Link>` تنكسر؛ هذه هي ميزة الحماية بتخطيط: تتغيّر الشجرة، ويثبت العنوان.

ولاحظ الشرط المعلَّق في أعلى الملف والاستيراد الذي بقي. الشرط انتقل إلى الأب، ولو بقي هنا فعّالًا لعمل مرتين على المسار نفسه: مرة في الأب ومرة في الابن. أمّا إبقاؤه معلَّقًا فيوثّق من أين جاء، ويسهّل العودة إليه إن أردت مسارًا محميًّا خارج هذه المجموعة. والملف القديم `src/routes/about.tsx` لم يبق له وجود، لأنّه صار التخطيط نفسه؛ ولو بقي لتنازع الملفّان على العنوان `/about`.

### مسار ثانٍ يدخل تحت الحماية

لنُثبت أنّ الأمر يتكرّر بلا شرط جديد، ننقل صفحة الكلمة العشوائية إلى المجموعة نفسها. تعريفها في الفرع:

```tsx
type LangType = z.infer<typeof randomWordSearchParamsSchema>["lang"];

export const Route = createFileRoute("/_authenticated/random-word")({
  component: RouteComponent,
  validateSearch: zodValidator(randomWordSearchParamsSchema),
  preloadStaleTime: 5_000,
  staleTime: 30_000,
  // shouldReload: ({context, params, deps, route}) => {

  // },
  loaderDeps: ({ search }) => ({ lang: search.lang }),
  loader: async ({ deps }) => {
    const res = await fetch(
      `https://random-words-api.kushcreates.com/api?words=1&language=${deps.lang || "en"}`
    );
    await new Promise((r) => setTimeout(r, 1000));
    const resJSON = await res.json();
    return { word: resJSON[0]?.word };
  },
});
```

في الفرع أُعيدت تسمية `src/routes/random-word.tsx` إلى `src/routes/_authenticated.random-word.tsx`، وتغيّر المعرّف في `createFileRoute` إلى `/_authenticated/random-word`. العنوان ظلّ `/random-word`، لكنّ ما تغيّر فعليًا أهمّ من العنوان: صار `loader` هذا المسار تحت أبٍ يرفض قبل أن يعمل أيّ ابن. فزائر غير مسجَّل يفتح `/random-word` لا يصل إلى الجلب أصلًا؛ يُحوَّل إلى `/login` قبل أن يُنادى المُحمِّل.

وهذه هي الفائدة العملية التي تستحقّ الملاحظة: الحماية لم تُلغِ كود الصفحة ولا بياناتها، بل غيّرت موضعها في الشجرة، فورثت الحاجز. ولو احتجت لاحقًا إلى صفحة عامّة من النوع نفسه، أخرجتها من تحت التخطيط بإعادة تسمية معاكسة، وعادت عامّة بلا حذف شرط ولا كتابته.

### حين تريد المنع بلا تحويل

الجزء الأخير من الدرس يجرّب بديلًا للتحويل: أن يبقى الزائر في مكانه ويرى رسالة «لا تملك صلاحية» بدل صفحة الدخول. الطريقة الأولى التي يجرّبها المؤلف أن يعرض مكوّن التخطيط رسالةً بدل `<Outlet />`، بالاعتماد على `Route.useRouteContext()` لقراءة المستخدم. الرسالة تظهر، ويبدو الحلّ مكتملًا، لكنّ لوحة الشبكة في أدوات المطوّر تكشف الخطأ: طلب بيانات الصفحة المحميّة أُرسل رغم أنّ شيئًا منها لم يُعرض. السبب أنّ المنع وقع في مرحلة التصيير، أي بعد أن عمل المُحمِّل. وإخفاء نتيجة الطلب ليس منعًا له؛ ومع بيانات حسّاسة أو أثر جانبي في `loader` يكون الفرق جوهريًّا.

لذلك يعود المؤلف إلى `beforeLoad` في التخطيط، لكنّه هذه المرة يرمي خطأً بدل التحويل. والرمي هناك يوقف الأبناء قبل تحميلهم، فتصبح الحماية حقيقية لا بصرية. وثمن ذلك أنّ الخطأ يُلتقط عند حدّ الأخطاء، فإن أردت رسالة عربية مفهومة بدل واجهة الخطأ الافتراضية مرّرت `errorComponent` للتخطيط، وتفحص فيه نوع الخطأ لتميّز خطأ المصادقة عن غيره. والفرق بين الأسلوبين في تجربة الزائر: التحويل ينقله إلى `/login` ويحفظ وجهته، والخطأ يُبقيه في صفحته ويعرض له سبب المنع.

### القاعدة التي تُلخّص الدرس

التخطيط يضيف أبًا في الشجرة، والشرطة السفلية تمنعه من إضافة مقطع في العنوان. فإذا نُقل مسار من الجذر إلى تحت الحماية لم يتغيّر عنوانه، ولم يحتج أيّ رابط إلى تعديل. ولهذا تكون خطوة الحماية في هذا الأسلوب «نقل ملفّ» بدل «إعادة كتابة ملفّ»: تعديل في اسم الملف والمعرّف، ثم لا شيء.

## جرّب بنفسك

1. اجعل المستخدم في `main.tsx` يبدأ بقيمة `null`، ثم افتح `/about` وراقب شريط العنوان: ستجد التحويل إلى `/login` ومعه معامل `redirect` يحمل العنوان المطلوب. اضغط زرّ الدخول وتأكّد من العودة إلى `/about` نفسها.
2. جرّب `/random-word` وأنت غير مسجَّل، ثم افتح لوحة الشبكة في أدوات المطوّر وأعد المحاولة: لا ينبغي أن يظهر أيّ طلب إلى واجهة الكلمات العشوائية.
3. علّق `beforeLoad` في `_authenticated.tsx` مؤقّتًا، ثم افتح `/about` و`/random-word`: يعود المساران عامّين معًا، وهذا برهان أنّ الحماية في الأب لا في الأبناء.
4. أعد `beforeLoad` إلى العمل، ثم استبدل `<Outlet />` في مكوّن التخطيط بشرط يعرض رسالة منع عند غياب المستخدم، وانتقل من `/about` إلى `/random-word` وأنت تنظر إلى لوحة الشبكة: الطلب يحدث رغم أنّ المحتوى مخفيّ.
5. أضف مسارًا جديدًا `_authenticated.secret.tsx` وضع فيه رابطًا في شريط التنقّل الجذر، ثم تحقّق من أنّه محميّ تلقائيًا بلا سطر تحقّق واحد فيه.
