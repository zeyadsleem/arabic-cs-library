## ماذا سنتعلّم؟

في الدرس السابق كان المُحمِّل (loader) في مسار `posts/$postId` ينتظر كلّ شيء قبل أن يُصيَّر المسار: نصّ التدوينة وتعليقاتها معًا. هذا مقبول حين تصل البيانات كلّها بالسرعة نفسها، لكنه يصير مؤلمًا حين تكون التعليقات أبطأ بكثير من نصّ التدوينة؛ يقف الزائر أمام شاشة انتظار كاملة، مع أنّ ما جاء من أجله — العنوان والنصّ — جاهز منذ اللحظة الأولى.

فكرة هذا الدرس أنّ البيانات ليست كلّها متساوية. هناك بيانات حرجة يجب أن ينتظرها المسار قبل التصيير، وبيانات ثانوية يمكن أن تصل بعد التصيير. سنعيد ترتيب المُحمِّل بحيث يبدأ طلب التعليقات ثم ينتظر نصّ التدوينة وحده، ونُرجع الوعد (promise) غير المحلول إلى المكوّن بدل بيانات التعليقات الجاهزة. بعد ذلك نستعمل مكوّن `Await` من TanStack Router لعرض بديل مؤقّت في مكان التعليقات، ثم نستبدله بالبيانات حين تصل.

النتيجة: يرى الزائر الصفحة فورًا ويقرأ التدوينة بينما تُحمَّل التعليقات في الخلفية.

## الشرح

### المشكلة: مُحمِّل ينتظر كلّ شيء

لنجعل البطء مرئيًا قبل أن نعالجه، نضيف تأخيرًا صناعيًا إلى دالة جلب التعليقات في `src/data/posts.ts`:

```ts
export async function getPostComments(id: number) {
  const res = await fetch(`https://dummyjson.com/posts/${id}/comments`);
  await new Promise((r) => setTimeout(r, 3000));
  if (res.ok) {
    return (await res.json()) as PostCommentsResponse;
  } else {
    throw new Error("Failed to fetch post comments");
  }
}
```

السطر `await new Promise((r) => setTimeout(r, 3000));` يؤخّر الدالة ثلاث ثوانٍ بعد وصول الاستجابة. الغرض منه تعليمي فقط: أن يجعل سلوك الشبكة البطيئة واضحًا أمامك في كلّ تحديث للصفحة، لا أن يبقى في الإنتاج.

مع هذا التأخير، إذا انتظر المُحمِّل التعليقات كما ينتظر نصّ التدوينة، فلن يُصيَّر المسار إلّا بعد مرور ثلاث ثوانٍ على الأقل. ولا يستطيع `pendingComponent` أن ينقذ الموقف هنا: فهو يعرض شاشة انتظار للمسار كلّه، فيبقى العنوان والنصّ محجوبين بسبب بيانات لا علاقة لهما بهما.

### بدء الطلب دون انتظاره

الحلّ يبدأ من المُحمِّل نفسه. نطلب التعليقات، ونحفظ وعدها في متغيّر، ثم ننتظر نصّ التدوينة وحده:

```ts
  loader: async ({ params }) => {
    const commentsPromise = getPostComments(+params.postId);
    const post = await getPost(+params.postId);

    return {
      post,
      commentsPromise,
    };
  },
```

الفرق الجوهري أنّ `getPostComments` تُستدعى دون `await`. الاستدعاء يبدأ طلب الشبكة فورًا ويعيد وعدًا، لكنّ المُحمِّل لا يتوقّف عنده. الذي يتوقّف عنده هو `await getPost(...)` فقط، وأثناء ذلك يكون طلب التعليقات قد انطلق بالفعل.

ثم نُرجع الوعد كما هو داخل كائن البيانات. هذه النقطة هي قلب الدرس: TanStack Router ينتظر القيم المحلولة في نتيجة المُحمِّل، ولا ينتظر الوعود غير المحلولة. فبمجرّد أن يحلّ وعد نصّ التدوينة، يعتبر المسار جاهزًا ويصيّره، ويترك وعد التعليقات يكمل طريقه في الخلفية.

### ترتيب السطرين ليس تفصيلًا

لو عكست السطرين فانتظرت نصّ التدوينة أولًا ثم طلبت التعليقات، لبقي الحلّ صحيحًا من ناحية النتيجة: سيُصيَّر المسار بعد وصول النصّ وستصل التعليقات بعده. لكنّ التوقيت سيكون أسوأ، لأنّ طلب التعليقات لن يبدأ إلّا بعد أن ينتهي طلب النصّ. بهذا الترتيب يصبح الزمن الكلّي مجموع الطلبين تقريبًا، أما بترتيبنا فيصبح قريبًا من زمن الطلب الأبطأ وحده، لأنّ الطلبين يعملان في الوقت نفسه.

لذلك ضع طلب البيانات الثانوية أولًا، ثم انتظر البيانات الحرجة. القاعدة عامّة: كلّ ما تريد أن يبدأ مبكرًا، أطلقه قبل أوّل `await` في المُحمِّل.

### عرض البديل ثم البيانات: مكوّن `Await`

الآن يصل إلى المكوّن كائنٌ فيه `post` جاهز و`commentsPromise` غير محلول. لا يمكن المرور على التعليقات بـ`map` كما كان الحال سابقًا، لأنّ ما لدينا وعد لا مصفوفة. نستورد `Await` مع `getRouteApi`:

```tsx
import { Await, getRouteApi } from "@tanstack/react-router";

export default function Post() {
  const { useParams, useLoaderData } = getRouteApi("/posts/$postId");
  const { postId } = useParams();
  const { post, commentsPromise } = useLoaderData();
```

ثم نستعمل `Await` في موضع قائمة التعليقات داخل المكوّن:

```tsx
      <div className="border-2 p-4 mt-4">
        <h2 className="text-xl font-bold mb-2">Comments</h2>
        <Await promise={commentsPromise} fallback={<div>Loading...</div>}>
          {(comments) => (
            <ul>
              {comments.comments.map((comment) => (
                <li
                  key={comment.id}
                  className="bg-purple-800 border-1 p-2 mb-2"
                >
                  {comment.body}
                  <br />
                  <span className="text-sm text-gray-200">
                    - {comment.user.username}
                  </span>
                </li>
              ))}
            </ul>
          )}
        </Await>
      </div>
```

لـ`Await` خاصيتان: `promise` هو الوعد الذي ننتظره، و`fallback` هو ما يُعرض ريثما يحلّ. أما `children` فهي دالة لا عنصر جاهز، ويُمرَّر إليها ناتج الوعد بعد حلوله. هذا التصميم مقصود: قبل الحلول لا وجود للبيانات، فلا معنى لكتابة كود يتعامل معها كأنّها موجودة. الدالة تضمن أنّك لا تلمس التعليقات إلّا في اللحظة التي صارت فيها متاحة فعلًا.

أثناء الانتظار يعرض `Await` البديل، وهو هنا نصّ `Loading...` بسيط. ويمكنك بدله بهيكل تحميل (`skeleton`) بثلاثة أعمدة رمادية مثلًا، المهم أن يشغل المساحة نفسها تقريبًا حتى لا تقفز الصفحة حين تصل التعليقات.

### انتظار المسار وانتظار جزء منه

يبقى التمييز الذي يفسّر لماذا لم نستغنِ عن `pendingComponent`. انظر إلى تعريف المسار:

```tsx
export const Route = createFileRoute("/posts/$postId")({
  component: RouteComponent,
  pendingComponent: () => <div>Loading...</div>,
  pendingMs: 0,
  pendingMinMs: 500,
```

`pendingComponent` هو ما يعرضه الموجّه حين يكون الانتقال نفسه قيد الانتظار، أي حين لا يزال المُحمِّل ينتظر نصّ التدوينة. القيمة `pendingMs: 0` تجعله يظهر فورًا بدل أن ينتظر ثانية قبل إظهار أيّ شيء، و`pendingMinMs: 500` تُبقيه نصف ثانية على الأقل حتى لا يومض ويختفي بسرعة مربكة.

أما بديل `Await` فيظهر بعد أن صار المسار مصيَّرًا، ولا يخصّ إلّا التعليقات. الفرق عملي: لو أعدت التعليقات إلى قائمة الانتظار في المُحمِّل، عاد `pendingComponent` يغطّي الصفحة كلّها وعدنا إلى المشكلة الأولى. ولو أزلت `Await` وأبقيت الوعد في البيانات، لما عرف المكوّن كيف يعرضه. الركنان معًا — وعد غير منتظر في المُحمِّل، و`Await` في المكوّن — هما ما يجعل التحميل في الخلفية ممكنًا.

## النتيجة

في الصورة نرى التخطيط الجذري كما هو، ثم عنوان التدوينة ونصّها قد ظهرا كاملين، مع أنّ التعليقات لم تصل بعد: صندوق `Comments` لا يحتوي إلّا على `Loading...`. هذا هو الفرق الذي أحدثه الدرس؛ قبل التعديل كانت الصفحة كلّها تنتظر تلك الثواني الثلاث، أما الآن فقد وصل القارئ إلى ما يهمّه، وستحلّ التعليقات مكان العبارة حين يجهز طلبها.

## جرّب بنفسك

1. احذف سطر التأخير من `getPostComments` وأعد التحديث؛ لاحظ أنّ البديل يكاد لا يظهر، لأنّ الوعد يحلّ قبل أن يراه أحد.
2. عكّس السطرين في المُحمِّل: انتظر نصّ التدوينة أولًا ثم أطلق طلب التعليقات. راقب لوحة الشبكة في أدوات مطوّر المتصفح ولاحظ أنّ الطلب الثاني يبدأ متأخرًا.
3. أضف تأخيرًا مشابهًا إلى `getPost` بدل التعليقات؛ سترى `pendingComponent` يغطّي الصفحة كلّها، وهذا يوضّح الفرق بين انتظار المسار وانتظار جزء منه.
4. استبدل بديل `Await` بهيكل تحميل من ثلاثة أعمدة رمادية، ثم قارن ارتفاع الصندوق قبل وصول التعليقات وبعده.
5. غيّر عنوان طلب التعليقات إلى عنوان خاطئ وراقب أين يظهر الخطأ وأيّ عرض يتولّاه، ثم أعد العنوان الصحيح.
