# المراقبات (مهجورة)

## D

في الوقت الذي كانت فيه البرمجة المتزامنة (concurrent programming) تتحوّل إلى أمر ذي شأن، كانت البرمجة كائنية التوجّه (object-oriented programming) أيضًا تكتسب أرضًا. ولم يكن مفاجئًا أن يبدأ الناس في التفكير في سُبل دمج المزامنة (synchronization) في بيئة برمجة أكثر تنظيمًا.

ومن المقاربات التي برزت في هذا الشأن المراقب (monitor). وقد وصفه بير برنك هانسن [BH73] أول مرة، ثم هذّبه توني هور [H74] لاحقًا، والفكرة التي يقوم عليها المراقب بسيطة إلى حد بعيد. لننظر إلى المراقب التخيّلي التالي المكتوب بصيغة C++:

monitor class account { private:

int balance = 0;

public:

void deposit(int amount) { balance = balance + amount; } void withdraw(int amount) { balance = balance - amount; } };

الشكل D.1: صنف مراقب تخيّلي

ملاحظة: هذا صنف «تخيّلي» لأن C++ لا تدعم المراقبات، ومن ثمّ فالكلمة المفتاحية monitor غير موجودة فيها. غير أن Java تدعم المراقبات بما يُسمّى الطرائق المتزامنة (synchronized methods). وسنفحص أدناه كيف نصوغ شيئًا شبيهًا جدًا بالمراقب في C/C++، وكيف نستخدم الطرائق المتزامنة في Java.

في هذا المثال، قد تلاحظ أن لدينا صديقنا القديم account وبعض الروتينات لإيداع مبلغ في الرصيد وسحبه منه. وقد تلاحظ أيضًا أن هذه أقسام حرجة (critical sections)؛ فإن استدعتها عدة خيوط على نحو متزامن، وقعت حالة تسابق (race condition) واحتمل الحصول على نتيجة غير صحيحة.

غير أنك لا تقع في مشكلة داخل صنف المراقب، لأن المراقب يضمن ألّا يكون نشطًا داخله إلا خيط واحد في المرة الواحدة. ومن ثمّ فمثالنا أعلاه قطعة شيفرة آمنة وسليمة تمامًا؛ فيمكن لعدة خيوط أن تستدعي deposit() أو withdraw() وهي تعلم أن الاستبعاد المتبادل (mutual exclusion) محفوظ.

فكيف يفعل المراقب ذلك؟ ببساطة: بقفل. فحين يحاول خيط استدعاء روتين من روتينات المراقب، فإنه يحاول ضمنًا الحصول على قفل المراقب. فإن نجح، أمكنه الدخول إلى الروتين وتنفيذ شيفرة الطريقة. وإن لم ينجح، تعطّل إلى أن ينتهي الخيط الموجود داخل المراقب مما يفعله. ومن ثمّ، لو كتبنا صنفًا في C++ على النحو التالي، لأنجز الهدف نفسه بالضبط الذي ينجزه صنف المراقب أعلاه:

class account { private:

int balance = 0; pthread_mutex_t monitor;

public:

void deposit(int amount) { pthread_mutex_lock(&monitor); balance = balance + amount; pthread_mutex_unlock(&monitor); } void withdraw(int amount) { pthread_mutex_lock(&monitor); balance = balance - amount; pthread_mutex_unlock(&monitor); };

الشكل D.2: صنف C++ يتصرّف كمراقب

ومن ثمّ، كما ترى من هذا المثال، لا يفعل المراقب الكثير لك تلقائيًا. فهو في الأساس يحصل على قفل ويطلقه فحسب. وبذلك نحقّق ما يطلبه المراقب: ألّا يكون نشطًا داخل deposit() أو withdraw() إلا خيط واحد، على النحو المرغوب.

## D.1 لماذا نتكلّف عناء المراقبات؟

قد تتساءل لماذا اختُرعت المراقبات أصلًا بدلًا من الاكتفاء بالأقفال الصريحة. في ذلك الوقت، كانت البرمجة كائنية التوجّه قد بدأت تنتشر للتو. ومن ثمّ كانت الفكرة هي مزج بعض المفاهيم الأساسية في البرمجة المتزامنة مع بعض المقاربات الأساسية للتوجّه الكائني مزجًا أنيقًا. لا أكثر من ذلك.

## D.2 هل نحصل على أكثر من القفل التلقائي؟

monitor class BoundedBuffer { private:

int buffer[MAX]; int fill, use; int fullEntries = 0; cond_t empty; cond_t full;

public:

void produce(int element) { if (fullEntries == MAX) // line P0 wait(&empty); // line P1 buffer[fill] = element; // line P2 fill = (fill + 1) % MAX; // line P3 fullEntries++; // line P4 signal(&full); // line P5 }

int consume() { if (fullEntries == 0) // line C0 wait(&full); // line C1 int tmp = buffer[use]; // line C2 use = (use + 1) % MAX; // line C3 fullEntries--; // line C4 signal(&empty); // line C5 return tmp; // line C6 } }

الشكل D.3: المنتج/المستهلك بالمراقبات ودلالات هور

نعود إلى صلب الموضوع. كما نعلم من مناقشتنا للسيمافورات، لا تكفي الأقفال وحدها تمامًا؛ فمثلًا، لتنفيذ حل المنتج/المستهلك، استخدمنا سابقًا سيمافورات لإنامة الخيوط عند انتظار تغيّر شرط ما (كمنتج ينتظر إفراغ مخزن مؤقت)، ولإيقاظ خيط عند تغيّر شرط معيّن (كمستهلك يشير إلى أنه أفرغ مخزنًا مؤقتًا فعلًا).

وتدعم المراقبات هذه الوظيفة عبر بناء صريح يُعرف بالمتغيّرة الشرطية (condition variable). لننظر إلى حل المنتج/المستهلك، المكتوب هنا بالمراقبات والمتغيّرات الشرطية.

في صنف المراقب هذا روتينان، هما produce() وconsume(). فخيط المنتج يستدعي produce() مرارًا ليضع بيانات في المخزن المؤقت المحدود، بينما يستدعي المستهلك consume() مرارًا. والمثال إعادة صياغة حديثة لحل هور [H74].

ينبغي أن تلاحظ بعض أوجه الشبه بين هذه الشيفرة والحل القائم على السيمافورات في الملاحظة السابقة. وأحد الفروق الكبرى هو كيفية وجوب استخدام المتغيّرات الشرطية جنبًا إلى جنب مع متغيّرة حالة صريحة؛ في هذه الحالة، يحدّد العدد الصحيح fullEntries ما إذا كان على المنتج أو المستهلك أن ينتظر، بحسب حالته. أما السيمافورات، في المقابل، فلها قيمة عددية داخلية تؤدّي الغرض نفسه. ومن ثمّ يجب أن تُقرن المتغيّرات الشرطية بنوع من قيمة حالة خارجية لتحقيق الغاية نفسها.

غير أن أهم جانب في هذه الشيفرة هو استخدام المتغيّرتين الشرطيتين empty وfull، ونداءي wait() وsignal() اللذين يستخدمانهما. وهاتان العمليتان تفعلان بالضبط ما قد تتوقعه: wait() تعطّل الخيط المستدعي على شرط معيّن؛ وsignal() توقظ خيطًا واحدًا منتظرًا على ذلك الشرط.

غير أن في كيفية عمل هذين النداءين بعض الدقائق؛ وفهم دلالات هذه النداءات مهم إلى حدّ حاسم لفهم سبب عمل هذه الشيفرة. ففيما يسمّيه باحثو أنظمة التشغيل دلالات هور (Hoare semantics) — وهو اسم مؤسف نوعًا ما، نعم — توقظ signal() فورًا خيطًا واحدًا منتظرًا وتشغّله؛ ومن ثمّ يُنقل قفل المراقب، الذي يحمله الخيط العامل ضمنًا، فورًا إلى الخيط الموقظ، الذي يعمل عندئذٍ إلى أن يتعطّل أو يخرج من المراقب. ولاحظ أنه قد يكون هناك أكثر من خيط منتظر؛ فـsignal() لا توقظ إلا خيطًا واحدًا وتشغّله، أما الآخرون فعليهم انتظار إشارة لاحقة.

يزيدنا مثال بسيط فهمًا لهذه الشيفرة. تخيّل وجود خيطين، أحدهما منتج والآخر مستهلك. يعمل المستهلك أولًا، ويستدعي consume()، ليجد أن fullEntries = 0 (C0)، إذ لا شيء في المخزن بعد. فيستدعي wait(&full) (C1)، وينتظر امتلاء المخزن. ثم يعمل المنتج، فيجد أنه ليس عليه أن ينتظر (P0)، ويضع عنصرًا في المخزن (P2)، ويزيد الفهرس fill (P3) وعدّاد fullEntries (P4)، ويستدعي signal(&full) (P5). وفي دلالات هور لا يواصل المنتج عمله بعد الإشارة؛ بل تنقل الإشارة السيطرة فورًا إلى المستهلك المنتظر، الذي يعود من wait() (C1) ويستهلك فورًا العنصر الذي أنتجه المنتج (C2) وهكذا. ولن يعمل المنتج مرة أخرى ويعود من روتين produce() إلا بعد أن يعود المستهلك.

## D.3 حيث تلتقي النظرية بالممارسة

كان توني هور، الذي كتب الحل أعلاه واستنبط الدلالات الدقيقة لـsignal() وwait()، رجل نظرية. ومن الواضح أنه ذكي أيضًا؛ فقد استنبط خوارزمية الترتيب السريع (quicksort) في النهاية [H61]. غير أن دلالات الإشارة والانتظار، كما تبيّن، لم تكن مثالية لتنفيذ حقيقي. وكما يقول المثل القديم: من حيث النظرية لا فرق بين النظرية والممارسة، لكن من حيث الممارسة ثمة فرق.

«...الممارسة، لكن في الممارسة ثمة فرق». وبالطبع لا يخبرك بذلك إلا الممارسون؛ أما رجل النظرية فيستطيع بلا شك أن يبرهن على أنه غير صحيح.

وبعد بضع سنوات، كان بتلر لامبسون وديفيد ريدل من Xerox PARC يبنون لغة متزامنة تُعرف باسم Mesa، فقرّرا استخدام المراقبات بدائيةً أساسية للتزامن [LR80]. وكانا باحثين معروفين في الأنظمة، وسرعان ما وجدا أن دلالات هور، مع أنها أكثر ملاءمة للبراهين، صعبة التحقيق في نظام حقيقي (ثمة أسباب كثيرة لذلك، وربما أكثر من أن نستعرضها هنا).

وتحديدًا، لبناء تنفيذ عامل للمراقبات، قرّر لامبسون وريدل تغيير معنى signal() تغييرًا دقيقًا لكنه حاسم. فصار روتين signal() يُعدّ مجرّد تلميح [L83]؛ فهو ينقل خيطًا منتظرًا واحدًا من حالة التعطيل إلى حالة القابلية للتشغيل، لكنه لا يشغّله فورًا. بل يحتفظ الخيط المشير بالسيطرة إلى أن يخرج من المراقب ويُزال من الجدولة.

## D.4 أوه، ثمة حالة تسابق

في ضوء دلالات Mesa الجديدة هذه، لنعد إلى فحص الشيفرة أعلاه. تخيّل مرة أخرى مستهلكًا (المستهلك 1) يدخل المراقب فيجد المخزن فارغًا، ومن ثمّ ينتظر (C1). الآن يأتي المنتج ويملأ المخزن ويشير إلى أن مخزنًا قد امتلأ، فينقل المستهلك المنتظر من حالة التعطيل على المتغيّرة الشرطية full إلى حالة الجاهزية. ويواصل المنتج عمله لبعض الوقت، ثم يتنازل عن المعالج في النهاية.

لكن يا هاوستن، لدينا مشكلة. هل تراها؟ تخيّل أن مستهلكًا آخر (المستهلك 2) يستدعي الآن روتين consume()؛ سيجد مخزنًا ممتلئًا، فيستهلكه ويعود، ضابطًا fullEntries على 0 في أثناء ذلك. هل ترى المشكلة بعد؟ حسنًا، ها هي ذي. صديقنا القديم المستهلك 1 يعمل أخيرًا الآن، ويعود من wait() وهو يتوقع أن المخزن ممتلئ (C1...)؛ لكن هذا لم يعد صحيحًا للأسف، فقد تسلّل المستهلك 2 واستهلك المخزن قبل أن تسنح للمستهلك 1 فرصة استهلاكه. ومن ثمّ لا تعمل الشيفرة، لأنه في الفترة بين signal() من المنتج والعودة من wait() لدى المستهلك 1 تغيّر الشرط. ويوضّح هذا الخط الزمني المشكلة:

Producer Consumer1 Consumer2 C0 (fullEnt=0)

C1 (Con1: blocked) P0 (fullEnt=0) P2 P3 P4 (fullEnt=1) P5 (Con1: ready)

C0 (fullEnt=1)

C2 C3 C4 (fullEnt=0)

C5 C6 C2 (using a buffer, fullEnt=0!)

## D.5 نظرة خاطفة تحت الغطاء قليلًا

لفهم سبب سهولة تنفيذ دلالات Mesa على نحو أفضل قليلًا، لنفهم المزيد عن تنفيذ مراقبات Mesa. يصف لامبسون وريدل في عملهما [LR80] ثلاثة أنواع مختلفة من الطوابير التي يمكن أن يكون الخيط جزءًا من أحدها في وقت معيّن: طابور الجاهزية، وطابور قفل المراقب، وطابور المتغيّرة الشرطية. ولاحظ أن البرنامج قد يحتوي عدة أصناف مراقبات وعدة نسخ من المتغيّرات الشرطية؛ فثمة طابور لكل نسخة من تلك العناصر.

وبوجود مراقب واحد لمخزن مؤقت محدود، يصبح لدينا أربعة طوابير للنظر فيها: طابور الجاهزية، وطابور مراقب واحد، وطابورا متغيّرتين شرطيتين (واحد للشرط full وآخر للشرط empty). ولنفهم على نحو أفضل كيف تدير مكتبة خيوط هذه الطوابير، سنُظهر كيف ينتقل خيط عبر هذه الطوابير في مثال المنتج/المستهلك.

في هذا المثال، نمضي في حالة قد يُوقَظ فيها مستهلك لكنه يجد أنه لا يوجد ما يستهلكه. لننظر إلى الخط الزمني التالي. على اليسار مستهلكان (Con1 وCon2) ومنتج (Prod) والسطر من الشيفرة الذي ينفّذه كل منهم؛ وعلى اليمين حالة كل من الطوابير الأربعة التي نتتبّعها في هذا المثال: طابور جاهزية العمليات القابلة للتشغيل، وطابور قفل المراقب المسمّى Monitor، وطابورا المتغيّرتين الشرطيتين empty وfull. ونتتبّع أيضًا الزمن (t)، والخيط العامل (بأقواس مربعة حول الخيط العامل في طابور الجاهزية)، وقيمة fullEntries (FE).

كما ترى من الخط الزمني، يتسلّل المستهلك 2 (Con2) ويستهلك البيانات المتاحة (t=9..14) قبل المستهلك 1 (Con1)، الذي كان

monitor class allocator { int available; // how much memory is available?

cond_t c;

void *allocate(int size) { while (size > available)

wait(&c); available -= size; // and then do whatever the allocator should do // and return a chunk of memory }

void free(void *pointer, int size) { // free up some memory available += size; signal(&c); } };

الشكل D.7: مخصّص ذاكرة بسيط

منتظرًا على الشرط full حتى يُشار إليه (منذ t=1)، تسنح له فرصة ذلك. غير أن Con1 يُوقَظ فعلًا بإشارة المنتج (t=7)، فيعمل مرة أخرى مع أن المخزن فارغ بحلول ذلك الوقت. ولو لم يعد Con1 فحص متغيّرة الحالة fullEntries (t=16)، لكان حاول خطأً استهلاك بيانات حين لا توجد بيانات تُستهلك. ومن ثمّ، فهذا التنفيذ الطبيعي هو بالضبط ما يقودنا إلى دلالات Mesa (لا دلالات هور).

## D.6 استخدامات أخرى للمراقبات

يشير لامبسون وريدل أيضًا في ورقتهما عن Mesa إلى بضعة مواضع يُحتاج فيها إلى نوع مختلف من الإشارة. فمثلًا، لننظر إلى مخصّص الذاكرة التالي (الشكل D.7).

تُرك كثير من التفاصيل خارج هذا المثال، لنركّز على شروط الإيقاظ والإشارة. وتبيّن أن شيفرة signal/wait أعلاه لا تعمل تمامًا؛ هل ترى السبب؟

تخيّل أن خيطين يستدعيان allocate. يستدعي الأول allocate(20) ويستدعي الثاني allocate(10). لا توجد ذاكرة متاحة، فيستدعي الخيطان wait() ويتعطّلان. وبعد مدة، يأتي خيط آخر ويستدعي free(p, 15)، فيحرّر بذلك 15 بايت من الذاكرة. ثم يشير إلى أنه فعل ذلك. لكنه للأسف يوقظ الخيط المنتظر لـ20 بايت؛ فيعيد ذلك الخيط فحص الشرط، ويجد أن 15 بايت فقط متاحة، فيستدعي wait() مرة أخرى. أما الخيط الذي كان يمكن أن يستفيد من تحرير 15 بايت، أي الخيط الذي استدعى allocate(10)، فلا يُوقَظ.

يقترح لامبسون وريدل حلًا بسيطًا لهذه المشكلة. فبدلًا من signal() التي توقظ خيطًا منتظرًا واحدًا، يستعملان broadcast() التي توقظ جميع الخيوط المنتظرة. ومن ثمّ تُوقَظ جميع الخيوط

monitor class Semaphore { int s; // value of the semaphore Semaphore(int value) { s = value; } void wait() { while (s <= 0)

wait(); s--; } void post() { s++; signal(); } };

في دلالات Mesa، يكون استخدام broadcast() صحيحًا دائمًا، لأن على جميع الخيوط أن تعيد فحص الشرط المعني عند الإيقاظ على أي حال. غير أنه قد يمثّل مشكلة أداء، ومن ثمّ ينبغي ألّا يُستخدم إلا عند الحاجة. في هذا المثال، قد توقظ broadcast() مئات الخيوط المنتظرة، فلا ينجح في المواصلة إلا واحد، بينما يتعطّل الباقون فورًا من جديد؛ وهذه المشكلة، المعروفة أحيانًا بالقطيع الهادر (thundering herd)، مكلفة بسبب كل تبديلات السياق الإضافية التي تحدث.

## D.7 استخدام المراقبات لتنفيذ السيمافورات

يمكنك على الأرجح أن ترى أوجه شبه كثيرة بين المراقبات والسيمافورات. وليس مفاجئًا أن تستطيع استخدام أحدهما لتنفيذ الآخر. وهنا نُظهر كيف يمكنك تنفيذ صنف سيمافور باستخدام مراقب (الشكل D.8).

كما ترى، تنتظر wait() ببساطة أن تصبح قيمة السيمافور أكبر من 0، ثم تنقص قيمته، بينما تزيد post() القيمة وتوقظ خيطًا منتظرًا واحدًا (إن وُجد). الأمر بهذه البساطة.

لاستخدام هذا الصنف سيمافورًا ثنائيًا (أي قفلًا)، ما عليك إلا تهيئة السيمافور على 1، ثم وضع أزواج wait()/post() حول الأقسام الحرجة. وبذلك نكون قد أظهرنا أن المراقبات يمكن استخدامها لتنفيذ السيمافورات.

class BoundedBuffer { private: int buffer[MAX]; int fill, use; int fullEntries; pthread_mutex_t monitor; // monitor lock pthread_cond_t empty; pthread_cond_t full;

public: BoundedBuffer() { use = fill = fullEntries = 0; } void produce(int element) { pthread_mutex_lock(&monitor); while (fullEntries == MAX)

pthread_cond_wait(&empty, &monitor); buffer[fill] = element; fill = (fill + 1) % MAX; fullEntries++; pthread_cond_signal(&full); pthread_mutex_unlock(&monitor); }

int consume() { pthread_mutex_lock(&monitor); while (fullEntries == 0)

pthread_cond_wait(&full, &monitor); int tmp = buffer[use]; use = (use + 1) % MAX; fullEntries--; pthread_cond_signal(&empty); pthread_mutex_unlock(&monitor); return tmp; } }

الشكل D.9: منتج/مستهلك في C++ بـ«مراقب»

ذكرنا أعلاه أننا كنا نستخدم مراقبات «تخيّلية»؛ فـC++ لا تعرف هذا المفهوم. ونُظهر الآن كيف نصوغ صنفًا في C++ شبيهًا بالمراقب، وكيف تستخدم Java الطرائق المتزامنة لتحقيق غاية مشابهة.

## مراقب C++ من نوع ما

هذه شيفرة المنتج/المستهلك مكتوبة بـC++ مع أقفال ومتغيّرات شرطية (الشكل D.9). وترى في مثال الشيفرة هذا أن الفرق قليل بين شيفرة المراقب التخيّلي وصنف C++ العامل الذي لدينا أعلاه. وبالطبع، أحد الفروق الواضحة هو الاستخدام الصريح لقفل باسم monitor. وأدقّ من ذلك هو التحوّل إلى نداءي POSIX القياسيين pthread cond signal() وpthread cond wait(). وتحديدًا، لاحظ أن المرء يمرّر أيضًا عند استدعاء pthread cond wait() القفل المحمول وقت الانتظار. فالقفل مطلوب داخل pthread cond wait() لأنه يجب إطلاقه حين يُنام هذا الخيط وإعادة الحصول عليه قبل أن يعود إلى المستدعي (السلوك نفسه كما داخل المراقب، لكن مع أقفال صريحة هذه المرة).

## Java والمتغيّرة الشرطية الواحدة

في النسخة الأصلية من Java، كانت تُرفَق متغيّرة شرطية بكل صنف متزامن أيضًا. ولاستخدامها، كنت تستدعي إما wait() أو notify() (يُستخدم المصطلح notify أحيانًا بدل signal، لكنهما يعنيان الشيء نفسه). ومن الغريب أنه في هذا التنفيذ الأصلي لم تكن هناك طريقة للحصول على متغيّرتين شرطيتين (أو أكثر). وقد تلاحظ في حل المنتج/المستهلك أننا نستخدم دائمًا اثنتين: واحدة للإشارة إلى أن مخزنًا قد أُفرغ، وأخرى للإشارة إلى أن مخزنًا قد مُلئ.

لفهم قيود توفير متغيّرة شرطية واحدة فقط، لنتخيّل حل المنتج/المستهلك بمتغيّرة شرطية واحدة فقط. تخيّل أن مستهلكين يعملان أولًا، وكلاهما يعلق منتظرًا. ثم يعمل منتج، ويملأ مخزنًا واحدًا، ويوقظ مستهلكًا واحدًا، ثم يحاول الملء مرة أخرى فيجد المخزن ممتلئًا (MAX=1). ومن ثمّ يصبح لدينا منتج ينتظر مخزنًا فارغًا، ومستهلك ينتظر مخزنًا ممتلئًا، ومستهلك كان منتظرًا وهو على وشك أن يعمل لأنه أُوقظ.

ثم يعمل المستهلك ويستهلك المخزن. غير أنه حين يستدعي notify()، يوقظ خيطًا واحدًا منتظرًا على الشرط. ولأن ثمة متغيّرة شرطية واحدة فقط، فقد يوقظ المستهلك المستهلكَ المنتظر بدلًا من المنتج المنتظر. ومن ثمّ لا يعمل الحل.

ولعلاج هذه المشكلة، يمكن المرء أن يستخدم حل البثّ مرة أخرى. ففي Java يستدعي المرء notifyAll() لإيقاظ جميع الخيوط المنتظرة. وفي هذه الحالة،

## D.9 الخلاصة

رأينا تقديم المراقبات، وهو مفهوم بنيوي طوّره برنك هانسن ثم هور في أوائل السبعينيات. فحين يعمل خيط داخل المراقب، فإنه يحمل ضمنًا قفل مراقب، فيمنع بذلك الخيوط الأخرى من دخول المراقب، مما يتيح بناء الاستبعاد المتبادل بسهولة.

ورأينا أيضًا تقديم المتغيّرات الشرطية الصريحة، التي تتيح للخيوط أن تستدعي signal() وwait() على نحو شبيه بما رأيناه مع السيمافورات في الملاحظة السابقة. ودلالات signal() وwait() حاسمة؛ ولأن جميع الأنظمة الحديثة تنفّذ دلالات Mesa، فإن إعادة فحص الشرط الذي نام عليه الخيط مطلوبة للتنفيذ الصحيح. ومن ثمّ فـsignal() مجرّد تلميح إلى أن شيئًا قد تغيّر؛ والمسؤولية تقع على الخيط الموقظ ليتأكد من أن الشروط مناسبة لمواصلة تنفيذه.

وأخيرًا، لأن C++ لا تدعم المراقبات، رأينا كيف نحاكي المراقبات بأقفال pthread ومتغيّرات شرطية صريحة. ورأينا أيضًا كيف تدعم Java المراقبات بروتيناتها المتزامنة، وبعض قيود توفير متغيّرة شرطية واحدة فقط في بيئة كهذه.
