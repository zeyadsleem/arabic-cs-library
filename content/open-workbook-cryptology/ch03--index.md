# الفصل 3: أنظمة التشفير غير المتماثلة [المفتاح العام]

**Jonathan A. Poritz**

رأينا أن هناك أنظمة تشفير آمنة وسريعة و(نسبيًا) سهلة الاستخدام، لكنها تتطلّب نشاطًا خاصًا قبل أن تبدأ الاتصالات العادية: تبادل مفتاح سرّي آمن. وهناك مقاربات متنوعة لتجاوز الصعوبة العملية التي قد يمثّلها ذلك في العالم الواقعي (مثل إيصال رقم بطاقتك الائتمانية بأمان إلى متجر إلكتروني لم تُتحَ لك فرصة أداء طقس تبادل المفتاح السرّي معه)، ومنها:

- بروتوكولات تتيح لطرفين إنشاء سرّ مشترك عبر تبادل رسائل على شبكة عامة: لا يحتاج Alice وBob إلا إلى تبادل رسالتين لينتهي بهما الأمر إلى قيمة سرّية مشتركة لن تستطيع Eve حسابها حتى لو رأت الرسالتين معًا. ثم يمكن استخدام تلك القيمة المشتركة، مباشرةً أو بعد معالجة إضافية، مفتاحًا لشيفرة كتل لاتصالات أكثر أمانًا. وأشهر هذه البروتوكولات هو تبادل مفاتيح Diffie-Hellman، ويمكن العثور على مزيد من المعلومات عنه، مثلًا، هنا:
  - [صفحة ويكيبيديا «تبادل مفاتيح Diffie-Hellman»](https://en.wikipedia.org/wiki/Diffie-Hellman_key_exchange)
  - [مقال مسحي جيد](https://ieeexplore.ieee.org/document/1006971) — Marks 1999
  - [الورقة الأصلية عن اكتشافهما له لدى Diffie وHellman](https://citeseerx.ist.psu.edu/viewdoc/summary?doi=10.1.1.37.9720) — Diffie and Hellman 1976
  وتستند تفاصيل Diffie-Hellman إلى رياضيات متواضعة: وهي في متناول طالب متقدّم في تخصّص الرياضيات بالمرحلة الجامعية الأولى بسهولة. أما أمنه فيرتكز على فرضية يعتقدها كثير من الرياضيين وعلماء الحاسوب اعتقادًا واسعًا، لكنها لم تُبرهن قط!
- وبدلًا من أن نبني طريقة آمنة ليصنع الأطراف سرًّا مشتركًا عبر اتصالات على قناة عامة على فرضيات نظرية، هناك طريقة لفعل الشيء نفسه بالاستعانة بعتاد متخصّص وفهم عميق لميكانيكا الكم. وتُسمّى **توزيع المفاتيح الكمّي [QKD]**، وقد ابتُكرت في ثمانينيات القرن العشرين، ثم بُرِّئت تجريبيًا منذ ذلك الحين في المختبرات وعلى مسافات متزايدة، لكنها ليست بعدُ شائعة الاستخدام عمليًا. ولمزيد من المعلومات:
  - [صفحة ويكيبيديا «توزيع المفاتيح الكمّي»](https://en.wikipedia.org/wiki/Quantum_key_distribution)
  - موقع تعريفي عام: [Quantum computing 101](https://web.archive.org/web/20131225083723/https://uwaterloo.ca/institute-for-quantum-computing/quantum-computing-101)
  - [ورقة Bennett وBrassard البحثية الأصلية سنة 1984 في هذا الموضوع](https://arxiv.org/pdf/2003.06557.pdf) — Bennett and Brassard 2020
- وهناك مقاربة أخرى واسعة التطبيقات ومثيرة للاهتمام، وهي موضوع معظم هذا الفصل: أنظمة التشفير غير المتماثلة.

## أنظمة التشفير المتماثلة وغير المتماثلة و«المملّحة»: الأساسيات

إذا نظرنا عن كثب، نجد أن المشكلة التي لاحظناها في نهاية الفصل السابق تنبع من أن Alice وBob يجب أن يملكا المفتاح نفسه للتشفير وفكّ التشفير، وعليهما بالتالي إبقاءه بعيدًا عن Eve. فلو كان المفتاح بيد Eve، لأمكنها أن تشفّر رسائل وترسلها إلى Bob منتحلةً شخص Alice، ولأمكنها أيضًا أن تعترض رسائل Alice الحقيقية إلى Bob وتفكّ تشفيرها. هذه هي مشكلة استخدام المفتاح نفسه. ولأنظمة التشفير التي تفعل ذلك اسم:

**التعريف 2.1.1.** **نظام التشفير المتماثل** هو الذي يُستخدم فيه المفتاح نفسه لتشفير النصوص الصريحة إلى نصوص مشفَّرة، ولفكّ تشفير النصوص المشفَّرة إلى نصوص صريحة.

تُسمّى أنظمة التشفير المتماثلة أحيانًا **أنظمة التشفير بالمفتاح الخاص**.

وبيانيًا، تعمل أنظمة التشفير المتماثلة هكذا:

**نظام تشفير متماثل [مفتاح خاص]، بيانيًا:**

|  | على الشبكة العامة |  |
| --- | --- | --- |
|  | (حيث تراقب Eve) |  |
| تُنشئ رسالة النص الصريح m_A؛ |  |  |
| وباستخدام k، تشفّر m_A إلى c_A |  |  |
| وترسل c_A | ↣ النص المشفَّر c_A ↣ | تستقبل c_A؛ |
|  |  | وباستخدام k، تفكّ تشفير c_A |
|  |  | وتستعيد النص الصريح m_A |
|  |  | وتُنشئ رسالة النص الصريح m_B؛ |
|  |  | وباستخدام k، تشفّر m_B إلى c_B |
| وتستقبل c_B؛ | ↢ النص المشفَّر c_B ↢ | وترسل c_B |
| وباستخدام k، تفكّ تشفير c_B |  |  |
| وتستعيد النص الصريح m_B |  |  |

والمشكلة التي نتعامل معها الآن هي الاتفاق الخاص المسبق على المفتاح السرّي k.

ومن الطرق إلى تجاوز هذه المشكلة أن يستخدم Alice وBob مفتاحين مختلفين للتشفير وفكّ التشفير. ولهذا النوع من أنظمة التشفير اسم أيضًا:

**التعريف 2.1.2.** **نظام التشفير غير المتماثل** هو الذي يُستخدم فيه مفتاح kₑ، ويُسمّى **مفتاح التشفير** أو **المفتاح العام**، لتشفير النصوص الصريحة إلى نصوص مشفَّرة، بينما يلزم مفتاح مختلف k_d، ويُسمّى **مفتاح فكّ التشفير** أو **المفتاح الخاص**، لفكّ تشفير النصوص المشفَّرة إلى نصوص صريحة.

تُسمّى أنظمة التشفير غير المتماثلة أحيانًا **أنظمة التشفير بالمفتاح العام**، لأن المستخدم حين يستخدمها ينشر عادةً مفتاح تشفيره kₑ في مكان عام ليراه الجميع ويستخدموه.

وبيانيًا، تعمل أنظمة التشفير غير المتماثلة هكذا:

**نظام تشفير غير متماثل [مفتاح عام]، بيانيًا:**

| Alice | على الشبكة العامة | Bob |
| --- | --- | --- |
|  | (حيث تراقب Eve) |  |
| تُولّد زوج المفاتيح (k^Aₑ، k^A_d) |  | يُولّد زوج المفاتيح (k^Bₑ، k^B_d) |
| تُنزّل k^Bₑ | ↢ مفتاح التشفير العام k^Bₑ ↢ | ينشر k^Bₑ |
| تنشر k^Aₑ | ↣ مفتاح التشفير العام k^Aₑ ↣ | يُنزّل k^Aₑ |
| تُنشئ رسالة النص الصريح m_A؛ |  |  |
| وباستخدام k^Bₑ، تشفّر m_A إلى c_A |  |  |
| وترسل c_A | ↣ النص المشفَّر c_A ↣ | تستقبل c_A؛ |
|  |  | وباستخدام k^B_d، تفكّ تشفير c_A |
|  |  | وتستعيد النص الصريح m_A |
|  |  | وتُنشئ رسالة النص الصريح m_B؛ |
|  |  | وباستخدام k^Aₑ، تشفّر m_B إلى c_B |
| وتستقبل c_B؛ | ↢ النص المشفَّر c_B ↢ | وترسل c_B |
| وباستخدام k^A_d، تفكّ تشفير c_B |  |  |
| وتستعيد النص الصريح m_B |  |  |

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تفهم كيف سيستخدم Alice وBob نظام تشفير غير متماثل؟

وأبسط جزء في تصميم أنظمة التشفير غير المتماثلة *الآمنة* هو أنه **يجب أن يكون حساب مفتاح فكّ التشفير k_d مستحيلًا عمليًا على Eve حتى حين تعرف مفتاح التشفير [العام] kₑ**. فمفتاح التشفير عام، ولو كان هذا الحساب ممكنًا لفعلته Eve ببساطة، ولأمكنها فكّ تشفير كل النصوص المشفَّرة بنفسها.

وهناك اعتبار آخر لأمن هذه الأنظمة: يجب أن يكون فضاء مفاتيح فكّ التشفير الممكنة كبيرًا جدًا. وإلا لأمكن Eve ببساطة تنفيذ هجوم القوة الغاشمة بتجربة كل مفاتيح فكّ التشفير الممكنة.

وفي الحقيقة، هناك هجوم قوة غاشمة آخر ممكن على أنظمة التشفير غير المتماثلة، وهو كالتالي: لو كان لدى Eve تصوّر جيد إلى حد ما لمجموعة صغيرة من الرسائل المحتملة التي قد تشفّرها Alice لترسلها إلى Bob، لأمكنها أن تستخدم مفتاح التشفير العام بنفسها وتنفّذ كل تلك التشفيرات. فإن أصابت إحدى تخميناتها للرسالة الأصلية، فسيكون تشفيرها هو نفسه النص المشفَّر الذي رأته على الشبكة العامة منتقلًا من Alice إلى Bob. لذلك يجب أن يكون فضاء الرسائل المحتملة كبيرًا جدًا لمنع هذا النوع من هجمات القوة الغاشمة.

وهناك في الواقع طريقة جميلة لمنع هجوم القوة الغاشمة هذا القائم على فضاء الرسائل، وهي أن تُكبَّر رسالة النص الصريح تكبيرًا مصطنعًا قبل تشفيرها. ويُفعل ذلك عادةً بإضافة ما يلي:

**التعريف 2.1.3.** **المِلح التشفيري** هو بيانات عشوائية تُضاف إلى رسالة تريد Alice إرسالها إلى Bob قبل أن تشفّرها، وتُزال تلقائيًا عند طرف Bob بعد أن يفكّ تشفير النص المشفَّر.

وبمجرد أن تملّح Alice رسالتها، فإن أرادت Eve تنفيذ هجوم القوة الغاشمة القائم على فضاء الرسائل، فعليها أن تجرّب تشفير كل الرسائل المحتملة التي قد تكون Alice أرسلتها، *إضافة إلى* كل الاختيارات العشوائية الممكنة للملح. وحتى بعدد صغير نسبيًا من بتات الملح، سيجعل ذلك هذا الهجوم مكلفًا من حيث الزمن أكثر من اللازم بكثير.

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تفهم هذا «هجوم القوة الغاشمة القائم على فضاء الرسائل»، وكيف يمنعه الملح التشفيري؟

وتبقى ملاحظة أخيرة عن المفاتيح و*توليدها* في أنظمة التشفير غير المتماثلة: مفاتيح هذه الأنظمة أكثر حساسية من مفاتيح الأنظمة المتماثلة. فعادةً يُختار مفتاح خاص/لفكّ التشفير بحجم معيّن — كبير، لمنع هجمات القوة الغاشمة، وباستخدام عشوائية قوية في الغالب، لمنع هجمات القوة الغاشمة التي تصبح ممكنة لو عرف الخصم شيئًا عن بنية المفاتيح التي يُرجَّح أن تختارها.

ثم يُجرى حساب باستخدام ذلك المفتاح الخاص/لفكّ التشفير لإنتاج مفتاح التشفير/العام المقابل. ويجب أن يكون هذا الحساب عسيرًا جدًا في الاتجاه *العكسي*، وإلا لأمكن Eve العثور على المفتاح الخاص بمعرفة مفتاحه العام!

لذلك قد تكون عملية إنشاء المفاتيح كلها معقّدة إلى حد بعيد في أنظمة التشفير غير المتماثلة. فيجب أن تتضمّن التنفيذات خطوة توليد مفاتيح قد تكون مكلفة زمنيًا فعلًا، لكنها تُنفَّذ مرة واحدة فقط من الشخص الذي يريد أن يكون قادرًا على استقبال رسائل مشفَّرة من غرباء على الشبكة. وهذا بالطبع على النقيض من حال أنظمة التشفير المتماثلة، حيث يتفق Alice وBob ببساطة على مفتاح ما بالعدد الصحيح من البايتات، كيفما شاءا، ويبدآن التشفير وفكّ التشفير فورًا: فلا وجود لخطوة «*توليد مفاتيح*» خاصة في الأنظمة المتماثلة.

## استخدام نظام RSA غير المتماثل في Python

من أقدم أنظمة التشفير غير المتماثلة وأكثرها استخدامًا حتى اليوم[^1] نظام يُعرف باسم **RSA**، سُمّي تكريمًا لمخترعيه الثلاثة: Ron **R**ivest وAdi **S**hamir وLeonard **A**dleman. وسنستخدم تنفيذًا بلغة **Python** لـRSA لاستكشاف الخصائص الأساسية لاستخدام أنظمة التشفير غير المتماثلة، كتوليد المفاتيح والتشفير وفكّ التشفير، أولًا بطريقة مباشرة تمامًا غير آمنة تمامًا. ثم سنعود إلى هذه الدوال الأساسية في إعداد أكثر تعقيدًا بقليل لكنه آمن فعلًا.

### RSA مباشر — غير آمن تمامًا! — في Python

تضمّن وحدة **Python** المسماة `Crypto` وحدة فرعية هي `Crypto.PublicKey` تنفّذ صنفًا هو `RSA`. ويمكنك استخدام هذا الصنف بالطريقة المعتادة:

```text
from Crypto.PublicKey import RSA
```

وأول ما تفعله بكائن `RSA` هو توليد كائن جديد، وذلك بـ:

```text
key=RSA.generate(n)
```

ويجب أن تكون القيم المسموح بها لهذا المعامل 1024 على الأقل، وأن تكون من مضاعفات 256.

وكما هي الحال كثيرًا، فكلما كان المفتاح أكبر كان نظام التشفير أكثر أمانًا، لكن كانت الحسابات أبطأ في توليد المفتاح وأيضًا في التشفير وفكّ التشفير. ومن القيم الشائعة اليوم 1024 و2048، ولا يندر أيضًا 4096.

> **مهمة برمجية.**
>
> اكتب دالة **Python** اسمها `timeRSAkeygen(n)` تأخذ مدخلًا حجم مفتاح `n` وتولّد 100 مفتاح RSA بذلك الحجم. وقِس زمن توليد كل مفتاح باستخدام مقاربة قياس زمن التنفيذ المعروفة في المهمة البرمجية، ثم أضف زمن التنفيذ الجديد إلى قائمة. وينبغي أن تُعيد `timeRSAkeygen(n)` بعد ذلك متوسط هذه القائمة من مئة قياس.

> **مهمة برمجية.**
>
> ثم شغّل هذا البرنامج `timeRSAkeygen(n)` لأحجام المفاتيح التي تبدأ من 1024 وتصعد إلى 4096 بخطوة 256، أي لقيم `n` التي تتراوح في القائمة `[x for x in range(1024,4097,256)]`، واطبع لكل حجم مفتاح متوسط زمن توليد المفاتيح الذي أنتجته `timeRSAkeygen(n)` لذلك الحجم.

> **مهمة إضافية.**
>
> ارسم مخططًا لبيانات الزمن التي جمعتها للتو. أي إنك حسبت لكل طول مفتاح متوسط الزمن المستغرق في توليد كل مفتاح من ذلك الطول على مدى مئة مرة. ارسم الآن مخططًا خطيًا تكون فيه قيم x هي أحجام المفاتيح تلك، وقيم y المقابلة هي متوسطات أزمنة توليد المفاتيح بذلك الحجم. واحرص على أن يكون للمخطط عنوان وتسميات لمحوري x وy.

> **مهمة إضافية.**
>
> إن لم تكن على دراية برسم المخططات الخطية البسيطة في **Python**، فابحث فقط عن «*python line plot*»، وستجد حرفيًا مئات الصفحات التي تحوي أدلة بداية سريعة لرسم المخططات الخطية باستخدام `matplotlib.pyplot`، وكثير منها يحوي شيفرة يمكنك نسخها وتكييفها بسهولة.

وإذا كان بمقدورك تصدير مفتاح، فمن المنطقي أن يكون بمقدورك استيراد مفتاح أيضًا. وهذا سهل فعلًا: افترض أن سلسلة بايتات المفتاح الخاص مخزّنة في متغيّر اسمه `exported_key`. عندئذٍ يمكنك صنع كائن RSA مطابق تمامًا بـ:

وفي حالة RSA، فإن الاتجاه السهل من المفتاح الخاص إلى المفتاح العام هو مجرّد *ضرب*، والاتجاه الصعب العكسي هو في الأساس مجرّد *قسمة*. وكما يتذكّر معظمنا من المدرسة الابتدائية، فمن الأسهل والأكثر مباشرة بكثير ضرب عددين من قسمة أحدهما على الآخر. وفي RSA، العددان اللذان يُضرب أحدهما في الآخر هما **عددان أوّليان**، أي عددان ليس لهما عوامل صحيحة موجبة غير الواحد ونفسيهما. ويبقى ضرب الأعداد الأولية سهلًا (وسريعًا) كضرب أي نوع آخر من الأعداد، حتى لو كانت مئات الأرقام طولًا. لكن إن أُعطيت عددًا من 600 رقم وقيل لك إنه حاصل ضرب عددين أوّليين من 300 رقم، فسيستغرق العثور على هذين العددين الأوليين زمنًا هائلًا — جزءًا كبيرًا من عمر الكون: *زمنًا هائلًا حقًا* — ولو بأفضل الخوارزميات والعتاد المتاحين اليوم.

### RSA أكثر أمانًا في Python باستخدام OAEP وPKCS #1

للأسف، الاستخدام المباشر لـRSA كما فعلنا للتو لا يُعدّ آمنًا. وذلك لأسباب عدة، بعضها يتعلّق بالبنية الخاصة لـRSA، وبعضها يتعلّق ببساطة بأن RSA العاري الذي استخدمناه أعلاه لا ملح فيه، فيشفّر دائمًا النص الصريح نفسه إلى النص المشفَّر نفسه عند استخدام المفتاح نفسه — وللتفاصيل (بعضها) انظر قسم [Attacks against plain RSA](https://en.wikipedia.org/wiki/RSA_(cryptosystem)#Attacks_against_plain_RSA) في مقال ويكيبيديا [RSA (cryptosystem)](https://en.wikipedia.org/wiki/RSA_(cryptosystem)).

وقد طوّر مجتمع التشفير بنية نظرية تحمي من هذه الهجمات على RSA العاري تُسمّى **حشو التشفير غير المتماثل الأمثل [OAEP]**. وقد أُدرج OAEP في معيار يُسمّى **PKCS #1، معيار التشفير بالمفتاح العام رقم 1**، أصدرته مختبرات RSA، وهي شركة أمن تقنية معلومات أمريكية أسّسها Rivest وShamir وAdleman أنفسهم، مبتكرو نظام RSA. والمعيار الذي يُعدّ آمنًا للاستخدام العملي هو PKCS #1[^4].

ويُنفَّذ PKCS #1 في **Python** بصنف `PKCS1_OAEP` في الوحدة `Crypto.Cipher`. ولأنه في جوهره مجرّد حشو لنظام تشفير غير متماثل — والحرف «P» في «OAEP» — فإننا نصنع كائن تشفير PKCS #1 بإطعامه كائن مفتاح RSA:

```text

>>> key = gen_save_RSA_pub_priv(1024, "BobRSA")

>>> from Crypto.PublicKey import RSA
>>> public_key = recall_RSA_public("BobRSA.public")
>>> from Crypto.Cipher import PKCS1_OAEP
>>> cipher_for_encryption = PKCS1_OAEP.new(public_key)
>>> # and Alice can encrypt messages, e.g.,
>>> cleartext = b'This is a test. This is only a test.'
>>> ciphertext = cipher_for_encryption.encrypt(cleartext)
>>> print(ciphertext)

>>> from Crypto.Cipher import PKCS1_OAEP
>>> cipher_for_decryption = PKCS1_OAEP.new(key)
```

- إن كتبتَ، عزيزي القارئ، الأوامر نفسها حرفيًا في حاسوبك، فستحصل عند فكّ التشفير على النص الصريح الأصلي نفسه، لكن الخطوة الوسيطة، أي النص المشفَّر، ستكون مختلفة عن المبيَّن أعلاه. والسبب في ذلك أن OAEP يتضمّن بعض الملح التشفيري، فتحصل في كل مرة تشفّر فيها، حتى للنص الصريح نفسه، على نص مشفَّر مختلف. (وهذا **أمر جيد**، فهو يزيد الأمان.)
- لا يمكنك تشفير نصوص صريحة كبيرة جدًا بالمقاربة الموصوفة أعلاه. ففي الوضع العملي يجب إما تجزيء رسالة طويلة إلى قطع صغيرة وتشفير كل منها، وإما استخدام مقاربة أخرى تتفادى حدّ الحجم. وسيُوصف الحل الثاني في القسم التالي مباشرةً.

### كيف نستخدم RSA بطريقة سريعة وآمنة معًا

كان ينبغي أن يكون واضحًا من المهام البرمجية أعلاه أن RSA، مع ما له من خصائص جميلة كنظام تشفير غير متماثل من حيث توزيع المفاتيح وإدارتها، بطيء جدًا. وإضافة إلى ذلك، فيه مشكلة أنه لا يمكن تشفير رسائل كبيرة — وإن كان في الإمكان افتراضًا حلّ هذه المشكلة بإحدى طرائق تسلسل الكتل التي نوقشت أعلاه. لكن هناك مقاربة أخرى تستفيد من مزايا أنظمة التشفير غير المتماثلة وتتفادى نقاط ضعفها.

ولذلك تُستخدم المقاربة الكاملة الموصوفة في هذا الفصل للتشفير غير المتماثل، بما فيها توليد مفتاح عام ومفتاح خاص، ونشر المفتاح العام على موقع عام ليستخدمه أي أحد، *وغير ذلك*. لكن بدلًا من إجراء الاتصال كله بـRSA (أو بنظام تشفير غير متماثل آخر)، يُستخدم ذلك النظام غير المتماثل البطيء والآمن لنقل «مفتاح جلسة» مختار عشوائيًا. ثم يُجرى بقية الاتصال بشيفرة كتل سريعة جيدة التسلسل (مثل AES).

وقد تتكوّن «الجلسة» في هذا السياق من عدد متفق عليه من الرسائل، أو من كل الرسائل اللازمة لإتمام بروتوكول ما (كإجراء دفع ببطاقة ائتمانية على الشبكة)، أو من كل الرسائل المُرسَلة قبل انقضاء حدّ زمني ما. وأيًّا كان ما ينهي الجلسة، فعند حدوثه يجب توليد مفتاح جلسة عشوائي جديد لمزيد من الاتصالات الآمنة بين الطرفين أنفسهما.

وهذه المقاربة شائعة للغاية على الإنترنت اليوم. فمعظم الوقت الذي يشاهد فيه العملاء فيلمًا عبر الإنترنت، تكون هذه هي طريقة إرسال بثّ الفيديو إليهم من المزوّد. فالمزوّدون يريدون إرسال بيانات الفيديو مشفَّرة، كي لا تُسرق أفلامهم الثمينة من شخص يراقب الحزم فقط وهي تمرّ على الشبكة. ولأن العملاء لم يقابلوا المزوّدين شخصيًا على الأرجح ليتفقوا على مفتاح لنظام تشفير متماثل، يبدو أن على المزوّدين استخدام نظام غير متماثل لبثّ الفيديو المشفَّر هذا — لكن أنظمة التشفير غير المتماثلة أبطأ من أن تمرّ بها فيديوهات دون أن يلاحظ المشاهد البشري! وفي المقابل، شيفرات الكتل مثل AES *سريعة* بما يكفي. ولأن التفاوض على مفتاح الجلسة في بداية البثّ يستغرق جزءًا من الثانية، فإن مقاربة هذا القسم تتيح الأمان بلا صعوبات توزيع المفاتيح، ومع ذلك باستخدام شيفرة كتل سريعة (للبثّ كله، بعد إرسال مفتاح الجلسة الأولي بنظام تشفير غير متماثل).

## التوقيعات الرقمية

لقد غيّر اكتشاف أنظمة التشفير غير المتماثلة — أو كما تُسمّى أكثر في السياقات غير التقنية كالفقرة الحالية، أنظمة التشفير بالمفتاح العام — وجه الإنترنت، إذ أتاح اتصالات آمنة بين كيانات لم تلتقِ قطّ في العالم الواقعي لتتشارك مفتاحًا سرّيًا. ولولا هذا الابتكار لكانت التجارة عبر الإنترنت أعقد بمراحل لا نهائية، مثلًا. لكن أبعد من هذا التطبيق المباشر لتشفير المفتاح العام في تأمين الاتصالات من المتلصّصين، اكتُشفت تطبيقات أخرى قوية أيضًا. ومنها تطبيق جميل جدًا كثير الاستخدام في عالم الشبكات، وهو فكرة:

**التعريف 2.3.1.** **التوقيع الرقمي** قطعة S من البيانات ترافق رسالة m. وهناك أيضًا خوارزمية تُسمّى **التحقّق من التوقيع** يمكن تشغيلها بمدخلات هي S وm وبعض البيانات العامة الأخرى، والتي إذا أعادت *قبولًا* برهنت على أن التوقيع لم يكن ليُنتج إلا من شخص يملك قطعة معيّنة من البيانات السرّية.

وإذا افترضنا بعض الافتراضات حول السلوك في العالم الواقعي — وقد تكون مبرَّرة أو غير مبرَّرة! — فسيكون لهذه التوقيعات الرقمية تطبيقات بالغة القيمة. ومن الافتراضات التي سنحتاجها:

- وجود ارتباط موثوق بين المعلومة العامة المستخدمة للتحقّق من التوقيع والشخص الواقعي الذي يدّعي أنه أنشأ التوقيع. فمثلًا، ربما يلزم، كي تُدرَج المعلومة العامة على موقع معروف موثوق بجوار اسم إنسان، أن يذهب ذلك الإنسان إلى مكتب حكومي ما، ويعرض هوية، ويسجّل بياناته العامة.
- إمكان الوثوق بأن البشر يحفظون البيانات السرّية اللازمة لتوليد تلك التوقيعات آمنةً حفظًا موثوقًا. فمثلًا، لا يحفظونها على جهاز يمكن اختراقه أبدًا، ولا ينسون محوها قبل أن يتخلّصوا من قرص صلب قديم، *وغير ذلك*.

### توقيعات رقمية ساذجة

كان من المهم منذ بداية دراستنا لعلم التشفير أن التشفير وفكّ التشفير *متضادان*: أي ما نسمّيه في الرياضيات «دوالًّا عكسية»[^5]، بمعنى أن إجراء إحداهما ثم الأخرى يعيدك ببساطة إلى ما بدأت منه. ولأن الدوال العكسية تعمل بأي ترتيب، فهذا يعني أن فكّ تشفير تشفير رسالة ما ليس مجرّد الرسالة الأصلية فحسب، بل إن تشفير فكّ تشفير رسالة ما هو أيضًا كذلك.

وقد يبدو ذلك مجرّد طرافة حسابية — ولماذا يفكّ أحد تشفير رسالة لم تُشفَّر أولًا؟ — لكن فيه في الواقع خصيصة جميلة جدًا: لا يستطيع فكّ التشفير إلا من يملك المفتاح الخاص لنظام تشفير غير متماثل ما، بينما يستطيع أي شخص نزّل مفتاح التشفير العام المقابل أن يشفّر. وحالة أن يستطيع شخص واحد فقط يملك معلومة سرّية (المفتاح الخاص) فعْل شيء ما بينما يستطيع كل الآخرين فعل شيء آخر بقطعة معلومة عامة (المفتاح العام) تبدو شبيهة جدًا بما يُفترض أن يحدث في نظام توقيع رقمي.

وبالتحديد، لنفترض أن Bilbo يريد أن يوقّع رقميًا رسالة m ما، وأن Aragorn يريد أن يتحقّق من التوقيع. أولًا ينبغي أن يولّد Bilbo زوج مفاتيح عام/خاص ويضع مفتاحه العام على موقعه. ثم ينبغي أن يستخدم خوارزمية فكّ التشفير بمفتاحه الخاص على الرسالة m، فيحصل على قطعة بيانات نسمّيها s. وأخيرًا ينبغي أن يرسل Bilbo الرسالة m والتوقيع s معًا إلى Aragorn.

وسيكون Aragorn قد نزّل مفتاح Bilbo العام. وما يمكنه فعله هو تشفير توقيع Bilbo (المدَّعى) s باستخدام ذلك المفتاح العام، فيحصل على قطعة بيانات نسمّيها mprime. ثم سـ**يقبل** Aragorn التوقيع صحيحًا إذا كان mprime لديه هو نفسه رسالة Bilbo m. ولأنه لا ينبغي أن يكون قادرًا على صنع قطعة بيانات s التي تشفيرها m إلا من يملك مفتاح Bilbo الخاص، فإن هذه الطريقة تنفّذ نظام التوقيع الرقمي فعلًا كما وُعد.

> **مهمة برمجية.**
>
> اكتب دالة **Python** اسمها `sign(key, m)` تأخذ مدخلًا مفتاحًا كاملًا (عامًّا وخاصًّا) `key` لـRSA، في صورة سلسلة بايتات قد تكون أنتجها `exportKey()`، ورسالة `m` (سلسلة بايتات)، وتنتج التوقيع `s` على `m` كما وُصف أعلاه. وللقيام بذلك استخدم `RSA.importKey` على المتغيّر `key` لبناء كائن RSA. واستخدم دالة `decrypt` لهذا الكائن على المتغيّر `m` لإنتاج التوقيع `s`، الذي ينبغي أن تعيده دالتك.

> **مهمة برمجية.**
>
> ثم اكتب دالة **Python** اسمها `verify(pk, m, s)` تأخذ مدخلًا مفتاحًا عامًّا `pk` لـRSA، في صورة سلسلة بايتات قد تكون أنتجها `exportKey()`، ورسالة `m` (سلسلة بايتات)، وتوقيعًا `s` (سلسلة بايتات) على تلك الرسالة، وتعيد قيمة منطقية تشير إلى صحة التوقيع أو عدمه، وفق المخطّط أعلاه. وللقيام بذلك استخدم `RSA.importKey` على المتغيّر `pk` لبناء كائن RSA اسمه `public_key`، واستخدم دالة `encrypt` للكائن `public_key` لإنشاء سلسلة البايتات `mprime`. ولا تنسَ أن `encrypt` يأخذ متغيّرًا ثانيًا شكليًا قد تكون قيمته `1`، ويعيد صفًا عنصره رقم 0 هو التشفير. بعبارة أخرى، عليك أن تستخدم `mprime = public_key(s, 1)[0]`. ثم أعِد ببساطة القيمة (المنطقية) لـ`mprime == m`.

### توقيعات رقمية أفضل باستخدام دوال التلبيد

من المشكلات الكبيرة في التوقيعات الرقمية الساذجة الموصوفة أعلاه أنها (قد تكون)... كبيرة. أي إن التوقيع s على رسالة m يكون في جوهره بالحجم نفسه الذي عليه الرسالة نفسها — فهو فكّ تشفير في نهاية المطاف، متظاهرًا بأن الرسالة نص مشفَّر. فتوقيع مستند كبير، أو ربما قاعدة بيانات كبيرة أو صورة عالية الدقة، سيتطلّب أساسًا ضعف المساحة اللازمة للتخزين أو الإرسال، وهو أمر غير مقبول!

وما نحتاجه لصنع توقيعات أصغر بكثير هو نوع من الخوارزميات التي *تلخّص* في جوهرها محتوى الرسالة m التي تريد توقيعها. وعندئذٍ يمكن لنظام توقيع شبيه جدًا بالذي وُصف أعلاه أن ينفّذ خوارزمية تحقّقه بمقارنة التوقيع المشفَّر بملخّص الرسالة، لا بالرسالة كاملة.

ولهذه الخوارزمية الملخِّصة السحرية اسم:

**التعريف 2.3.2.** **دالة التلبيد التشفيرية** خوارزمية H تأخذ مدخلات سلاسل بتات x بطول اعتباطي وتنتج مخرجات H(x) ثابتة الحجم، محقّقةً الخصائص الآتية:

1. «**سهولة الحساب**»: حساب H(x) سريع جدًا؛
2. «**مقاومة الصورة السابقة**»: إذا بدأت بأي سلسلة بتات y بحجم مخرجات H، فمن العسير جدًا العثور على سلسلة بتات x بحيث H(x)=y؛
3. «**مقاومة الصورة السابقة الثانية**»: إذا بدأت بسلسلة بتات محدّدة x₁، فمن العسير جدًا العثور على x₂ أخرى بحيث H(x₂)=H(x₁)؛
4. «**مقاومة التصادم**»: من العسير جدًا العثور على أي سلسلتي بتات x₁ وx₂ بحيث H(x₂)=H(x₁).

وبمعنى ما، فإن العبارة المفتاحية في التعريف أعلاه هي «عسير جدًا»، بمعنى أن هناك بالتأكيد مدخلات ممكنة كثيرة جدًا لدالة تلبيد تعطي المخرج نفسه — بل هناك عدد لا نهائي من هذه المدخلات المتصادمة! فكّر في الأمر: لو كان حجم مخرج دالة تلبيد، مثلًا، 256 بتة، فماذا يحدث إن نظرت إلى سلاسل بتات مدخلة بطول 257 بتة؟ هناك ضعف عدد المدخلات بذلك الحجم مقارنةً بالمخرجات، فأكفأ طريقة ممكنة لتوزيع علاقة المخرجات بالمدخلات ستجعل كل مخرج ناتجًا عن مدخلين! والقدر نفسه من البرهان يقول إن هناك أربعة مدخلات على الأقل بطول 258 بتة تعطي المخرج نفسه، *وهكذا*. لكن ليسطر كونها دالة تلبيد تشفيرية يجب أن يكون العثور على هذه التصادمات *عسيرًا جدًا*.

وعمليًا، يعني ذلك أن الخوارزميات المستخدمة في دوال التلبيد تُجري كثيرًا من العبث العشوائي ببتات مدخلاتها، فلا تبقى في الخوارزمية بنية كافية قد تمنح مهاجمًا طريقة منتظمة لمحاولة إيجاد تصادمات أو صور سابقة أو صور سابقة ثانية. وبلا بنية، تبدو الخيار الوحيد المتبقي هو هجوم القوة الغاشمة، لكن بما أن عدد سلاسل البتات بطول 256 بتة يساوي تقريبًا عدد الجسيمات في الكون (باستثناء الفوتونات والنيوترينوات، مع ذلك)، فليس القوة الغاشمة هجومًا قابلًا للتنفيذ.

ودوال التلبيد التشفيرية مفيدة لأنه إذا كانت لديك رسالة أو مستند — فكّر فيه سلسلة بتات m — فإن H(m) يعمل نوعًا من «بصمة» لـm. فمثلًا: لنفترض أن Bilbo أخبر Aragorn ما هو H(m) دون أن يكشف m يوم الاثنين، ثم كشف m يوم الجمعة فقط. فيمكن Aragorn أن يثق بأنها الرسالة m نفسها التي كان Bilbo يفكّر فيها يوم الاثنين كالتي كشفها يوم الجمعة، لأنه كان سيكون «عسيرًا جدًا» العثور على mprime أخرى بحيث H(mprime)=H(m).

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تشعر بأنك تفهم ما هو مفيد في دالة التلبيد، ولماذا يوجد نظريًا عدد لا نهائي من الإخفاقات لشروط مقاومة الصورة السابقة ومقاومة الصورة السابقة الثانية ومقاومة التصادم، ومع ذلك فإن كون العثور على تلك الإخفاقات «عسيرًا جدًا» يجعل دوال التلبيد عملية؟

وهناك عدد من دوال التلبيد المستخدمة اليوم، وهناك دوال استُخدمت زمنًا ثم لم تعد تُعدّ آمنة. وكما ذُكر أعلاه، فإن أمن دالة التلبيد يرتكز جزئيًا على انعدام بنيتها... لكن أي خوارزمية واضحة بما يكفي لتُكتب وتُقبل معيارًا لا بدّ أن تحوي بعض البنية، وقد وجد علماء الحاسوب في النهاية سبيلًا لمهاجمة بعض دوال التلبيد الأقدم باستخدام ذلك القليل من البنية فقط. وهنا بعض دوال التلبيد التي كانت أو ما زالت مستخدمة على نطاق واسع:

- لعقد من الزمن تقريبًا انطلاقًا من مطلع تسعينيات القرن العشرين، كانت دالة التلبيد التشفيرية الأكثر استخدامًا تُسمّى **md5**. وقد طوّرها Ron Rivest ونشرها سنة 1992. وحجم مخرج md5 هو 128 بتة. ومع أن md5 كان يُظنّ معيبًا منذ منتصف التسعينيات، لم يُنشر هجوم فعلي إلا سنة 2004، حين بُيِّن أنه غير مقاوم للتصادم — Wang and Yu 2005. غير أن md5 ما زال مستخدمًا على نطاق واسع اليوم للتحقّق من أن نقل بيانات كبير لم يعانِ خطأ في الإرسال — أي إنه ما زال أداة مفيدة لاختبار التلف غير المتعمَّد في البيانات.
- أما دالة التلبيد التشفيرية الأكثر استخدامًا من أواخر التسعينيات حتى وقت قريب، والمدمجة في كثير من البروتوكولات التشفيرية المعيارية المقبولة على نطاق واسع، فهي **SHA-1**، بحجم مخرج 160 بتة. طوّرتها وكالة الأمن القومي الأمريكية في عملية شبه علنية، واعتمدها المعهد الوطني للمعايير والتقنية [NIST] ضمن عدة معايير فيدرالية أمريكية لمعالجة المعلومات. وفي سنة 2004 نُشر عمل أشار إلى أن SHA-1 قد يكون عرضة لأنواع معيّنة من الهجوم. (انظر Poritz and Swimmer 2004.) ولهذا طالب NIST سنة 2010 كثيرًا من تطبيقات حماية البيانات الفيدرالية الأمريكية بالانتقال إلى دالة تلبيد أخرى.
- وفي وقت كتابة هذه السطور، يوصي معظم المستخدمين والمؤسسات الواعين بأمن المعلومات بـ**SHA-2**، وبصيغتها **SHA-256** عادةً، التي حجم مخرجها 256 بتة. ونظرًا إلى الكشوف الأخيرة عن تورّط وكالة الأمن القومي في البروتوكولات التشفيرية وإضعافها لها، فقد يكون من دواعي القلق أنها شاركت في تطوير SHA-2.

ويُنفَّذ SHA-2 في **Python** بصنف `SHA256` في الوحدة `Crypto.Hash`. ويمكنك إنشاء هذا الكائن بـ`SHA256.new(s)`، حيث `s` هي سلسلة البايتات كاملة المطلوب تلبيدها. وهناك طريقة أخرى لاستخدام هذا الصنف، مفيدة خصوصًا إذا كانت البيانات المطلوب تلبيدها كثيرة، وهي تمرير أول قطعة من البيانات إلى `SHA356.new`، ثم استدعاء دالة `update` للصنف ببقية قطع البيانات.

وفي كلتا الطريقتين، حين تنتهي من إطعام نسخة `SHA256` بياناتك المطلوب تلبيدها، يمكنك استدعاء دالة `digest()` للحصول على قيمة التلبيد سلسلةَ بايتات، أو دالة `hexdigest()` للحصول على قيمة التلبيد نفسها سلسلةً حرفية مكتوبة بالنظام السادس عشري. فمثلًا:

```text
>>> from Crypto.Hash import SHA256
>>> hash_object = SHA256.new(b'first bit of data')
>>> hash_object.update(b'some more data')
>>> hash_object.update(b'last bit of the data')
>>> hash_object.digest()
b':\x93"P`\xd2Y-\x8c/\xab\xfa=\x8e\xa7\xb7N\xdcF\xae[\xf9\xa4\xd6.\xa1\xfeR\xe4\xcb\x89\xb8'
>>> hash_object.hexdigest()
3a93225060d2592d8c2fabfa3d8ea7b74edc46ae5bf9a4d62ea1fe52e4cb89b8
```

وبدالة `update` تحصل لاحقًا على `digest` يكون مخرج دالة التلبيد لكل المدخلات التي أعطيتها تلك النسخة منذ إنشائها بـ`new`. ويعني ذلك أنه يجب عليك إنشاء نسخة جديدة بـ`new` في كل مرة تريد أن تبدأ من الصفر في حساب دالة التلبيد لسلسلة بتات جديدة.

> **مهمة برمجية.**
>
> بما أن SHA256 يُعتقد أنه يحوز الخصائص التي تجعله دالة تلبيد تشفيرية جيدة، فلا بدّ أن التغييرات الصغيرة في المدخل تُحدث تغييرات جذرية في المخرج، أي قيمة التلبيد ذات الـ256 بتة. بل إن الأفضل هو أن تُحدث فروق بقدر بتة واحدة في المدخل — بتغيير بتة، أو بإضافة بتة أخرى إلى التسلسل (في أي مكان: في البداية أو النهاية أو في الوسط) — تغيّرًا في نحو نصف بتات قيمة التلبيد. لنختبر ذلك!
>
> **مهمة برمجية.**
>
> أولًا اختر سلسلة بايتات أساسية تعجبك بطول نحو 50 بايتًا. واحسب قيمة تلبيد SHA256 لها. وجرّب الآن تغيير بتة واحدة من هذه المدخلات الأساسية، واحسب قيمة تلبيد سلسلة المدخلات الجديدة، وقارن قيمتي التلبيد ببرنامجك `bits_diff_display` من المهمة البرمجية لترى أين تختلف قيمتا التلبيد ومقدار الاختلاف.
>

وكما ذُكر أعلاه، فإن كون التلبيد التشفيري لرسالة ما بصمةً موثوقة لتلك الرسالة يتيح لنا بناء نظام توقيع أكثر كفاءة بكثير. ففي هذا النظام لا نرسل الرسالة وفكّ تشفيرها، بل نرسل الرسالة وفكّ تشفير تلبيد الرسالة. وبذلك يكون التوقيع قطعة بيانات بحجم مخرج دالة التلبيد المستخدمة، مهما كان حجم الرسالة المطلوب توقيعها.

## إدارة المفاتيح والحاجة إلى بنية مفاتيح عامة متينة

بدأنا هذا الفصل بالبحث عن مقاربة جديدة قد تحلّ مشكلة واجهتنا في أنظمة التشفير المتماثلة: مع أنها سريعة وآمنة، فهناك مواقف كثيرة جدًا يريد فيها أطراف لم يلتقِ بعضهم ببعض في الحياة الواقعية، في مكان وحال يتيحان لهم مشاركة مفتاح سرّي عالي الجودة (أي: كبير وعسير التخمين على الآخرين)، أن يتواصلوا مع ذلك بأمان عبر الإنترنت. وقد حلّت أنظمة التشفير غير المتماثلة هذه المشكلة بتقسيم المفتاح إلى قطعتين، إحداهما يجب أن تبقى سرّية (المفتاح الخاص) والأخرى يجب أن تُنشر (المفتاح العام).

غير أن هناك مسألة مهمة تبقى، هي إدارة المفاتيح: فمشكلة أن Aragorn وBilbo لم يلتقيا شخصيًا لإنشاء مفتاح سرّي مشترك هي أنهما، أساسًا، يجب أن يثق كلٌّ منهما بموقع الآخر حيث يجب نشر مفتاحه العام. فإن اختُرق الموقع، أو حتى إذا اختُرقت قناة الاتصال بين أحد المشاركين وموقع الآخر، فقد ينتهي بهما الأمر إلى استخدام مفتاح عام ليس لمستقبِل الرسالة المقصود، بل مفتاح عام استبدله المخترق: ويُسمّى هذا *هجوم الشخص في المنتصف*[^6]، وهو يتيح للمخترقين قراءة كل الاتصالات بين الطرفين بل تعديلها دون أن يعلموا أنهم بلا أمان أصلًا!

وبيانيًا، يعمل هجوم الشخص في المنتصف هكذا:

**هجوم الشخص في المنتصف على أنظمة التشفير غير المتماثلة:**

| Alice | Eve | Bob |
| --- | --- | --- |
|  |  | يُولّد المفاتيح: |
|  |  | العام k^Bₑ والخاص k^B_d؛ |
|  | تعترض k^Bₑ ↢ | ينشر k^Bₑ |
|  | تُولّد المفاتيح: |  |
|  | العام k^Eₑ والخاص k^E_d؛ |  |
| تُنزّل k^Eₑ ظانّةً أنها k^Bₑ | ↢ k^Eₑ، مع انتحال المصدر |  |
| وتُنشئ رسالة النص الصريح m_A؛ |  |  |
| وباستخدام k^Eₑ، تشفّر m_A إلى c_A |  |  |
| وترسل c_A | ↣ c_A، مع الاعتراض |  |
|  | وباستخدام k^E_d، تفكّ تشفير c_A |  |
|  | وتستعيد النص الصريح m_A؛ |  |
|  | وتقرأ m_A، وتغيّرها إلى m_E إن شاءت |  |
|  | وباستخدام k^Bₑ، تشفّر m_E إلى c_E |  |
|  | بانتحال المصدر c_E ↣ | تستقبل c_E ظانًّا أنها c_A |
|  |  | وباستخدام k^B_d، يفكّ تشفير c_E |
|  |  | ويستعيد النص الصريح m_E |
|  |  | ظانًّا أنه m_A من Alice |

وهناك أيضًا هجوم شخص في المنتصف على التوقيعات الرقمية، قائم على أفكار مشابهة لاستبدال مفتاح Eve العام بمفتاح Bob، نتركه للقارئ ليفكّر فيه بنفسه.

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تشعر بالارتياح لكيفية عمل هجوم الشخص في المنتصف على الاتصالات؟ وماذا عن التوقيعات الرقمية؟

> **مهمة إضافية.**
>
> وهذه مهمة إضافية أخرى لا علاقة لها بالبرمجة على الإطلاق:

> **مهمة إضافية.**
>
> اكتب شرحًا لهجوم الشخص في المنتصف على التوقيعات الرقمية. وأدرج فيه مخططًا، مثل المخطط أعلاه المسمّى «توقيعات رقمية أفضل [أصغر] بالتلبيد» ممزوجًا بالمخطط أعلاه المسمّى «هجوم الشخص في المنتصف على أنظمة التشفير غير المتماثلة».

يبدو أن كل عجائب التشفير غير المتماثل ستتهاوى ما لم نكن واثقين أصلًا من أن الشبكات التي نستخدمها والمواقع التي نزورها لا تُخترق أبدًا. أي ما لم تكن هناك طريقة ما لنحصل على نوع من **جذر الثقة**، وهو مفتاح عام مرتبط بكيان واقعي نثق به ضمنًا أصلًا، ونثق أيضًا بممارساته الأمنية، حتى نطمئن إلى أن المفتاح الخاص يُحفظ سرًّا.

فتأتي أنظمة التشغيل والمتصفحات الحديثة بجذور ثقة مدمجة لا يعرف عنها المستخدمون شيئًا، لكنها تُستخدم للتحقّق من التوقيعات الرقمية التي يوقّعها ذلك الكيان. وربما يكون ذلك الكيان قد أدّى عمل مقابلة Jeff Bezos في الواقع، ثم يصدر توقيعًا على مفتاح Jeff العام. وعندئذٍ إن أردت استخدام بطاقتك الائتمانية على amazon.com، أمكنك تنزيل مفتاح Amazon العام مع توقيع جذر الثقة على ذلك المفتاح، ما يتيح لك الثقة بأن المفتاح الذي يبدو أنه مفتاح Amazon هو في الواقع مفتاح Amazon.

وتُسمّى هذه التوقيعات الرقمية على المفتاح العام لشخص ما عادةً **الشهادات**، ويُسمّى جذر الثقة في هذا السياق **جهة إصدار الشهادات**.

والبنية العامة لجهات إصدار الشهادات والمفاتيح العامة التي يمكن الوثوق، ربما بفضل الشهادات، بأنها مرتبطة بأشخاص أو مؤسسات واقعية معيّنة، تُسمّى **بنية المفاتيح العامة [PKI]**. فلو كان للإنترنت بنية مفاتيح عامة متينة موثوقة، لأمكننا أن نحظى باتصالات آمنة واسعة الانتشار، وبمستندات (موقّعة رقميًا) ملزمة قانونًا على الشبكة. وهذه إذن آخر تجلٍّ لمسألة ملازمة طوال هذا الكتاب: إدارة المفاتيح عسيرة جدًا، لكنها مهمة جدًا، كما توضّحه مرة أخرى ضرورة وجود بنية مفاتيح عامة متينة.

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تشعر بالارتياح لأفكار جذر الثقة (أو جهة إصدار الشهادات)، والشهادات، وبصفة عامة بنية المفاتيح العامة؟

## خاتمة؛ ولنفكّر في سلسلة الكتل

قد تبدو فكرة نظام التشفير غير المتماثل في البداية شبيهة بالسحر قليلًا. بل يجب الاعتراف بأن أمن كل هذه الأنظمة الشائعة اليوم يقوم على افتراضات تبدو معقولة جدًا، لكنها ليست معلومة بيقين رياضي: فأمن RSA مثلًا يقوم على افتراض أن تحليل الأعداد الكبيرة مستحيل في زمن معقول (بمعنى دقيق ما لكلمة «معقول»).

(ومن المثير للاهتمام أن أفضل هجوم معروف على هذا الافتراض تحديدًا، باستخدام حاسوب كمّي، بدا زمنًا طويلًا كأنه خيال علمي، لكنه يبدو الآن كأنه سيبدأ بالتأكيد في الانتشار على الأقل من كيانات كالدول القومية التي تملك موارد كافية. فلْيكن الخيال العلمي أفضل سلاح ضد السحر!)

وإلى أي حدّ تصمد الافتراضات الكامنة وراء التشفير غير المتماثل كله أمام اختبار الزمن، وهل يمكن تصميم أنظمة تشفير غير متماثلة عملية مقاومة للحواسيب الكمّية وتنفيذها، سؤال بالغ الأهمية في العقد أو العقود المقبلة من تاريخ الإنترنت. وبينما يعمل تقنيون مجدّون في الكواليس على فكّ هذا التشويق، هناك تطبيقات غريبة أخرى للتشفير غير المتماثل طُوّرت وتقدّم فوائد محتملة مذهلة... بعضها، في الحقيقة، جيد إلى حدّ يكاد يكون من المؤكد أنه ليس حقيقيًا.

ومن الأمثلة على ذلك شيء كثر الحديث عنه مؤخرًا يُسمّى **سلسلة الكتل**، وقد سمعت عنه على الأرجح بوصفه البنية التي تقوم عليها العملة الرقمية **Bitcoin**. ولو كنت تعمل في التعليم لسمعت عن سلاسل الكتل بوصفها، على ما يُفترض، أفضل مكان لحفظ شهادات الثانوية وكشوف درجات الجامعات والشهادات المهنية.

تبدأ سلسلة الكتل ببنية بيانات تُسمّى **سلسلة التلبيد**، وهي أساسًا مجرّد تتابع من كتل بيانات يمكن أن يستمر في النمو (ربما إلى الأبد)، مع حقل إضافي واحد في كل كتلة: تلبيد الكتلة السابقة (بدالة تلبيد تشفيرية ما). ولاحظ أنه بما أن الكتلة السابقة تلك كانت تحوي تلبيد الكتلة التي سبقتها، فإن هذه التلبيبات تربط ضمنًا كل الكتل بالكتلة الأولى في السلسلة، التي تُسمّى غالبًا **كتلة التكوين**. وبيانيًا: كتلة التكوين (genesis block) تحوي بياناتها وحقل تلبيد قيمته معدوم (null)؛ ثم تأتي الكتلة 1 حاملة بياناتها وتلبيد الكتلة السابقة؛ وهكذا تتوالى الكتل، كل واحدة تحمل بياناتها وتلبيد الكتلة التي قبلها.

وتمنح خصائصُ الأمان لدوال التلبيد التشفيرية المعطاة في التعريف 2.3.2 سلاسلَ التلبيد خاصيةً لافتة: فهي **غير قابلة للتغيير**، أي لا يمكن تعديلها. وبالتحديد، يعني ذلك أنه إذا كان حشد كامل من الناس (لنسمّهم «الهوبيت») يتشاركون نسخًا من سلسلة تلبيد، فلا يمكن لشخص آخر (لنسمّه «Gollum») أن يأتيهم ويدّعي أنه يملك نسخة صحيحة من السلسلة متطابقة في البداية والنهاية، لكن أُدخلت في وسطها كتل زائدة. والسبب في استحالة ذلك أن الكتلة الأولى — ولنقل إنها الكتلة رقم 141592 قرب النهاية حيث يتوافق Gollum مع الهوبيت — ستكون فيها تلبيدُ «كتلة سابقة» مختلفة عن تلبيد «الكتلة السابقة» عند الهوبيت: فالهوبيت لديهم الكتلة نفسها التي يتفقون جميعًا على أنها رقم 141591، بينما لدى Gollum الكتلة الزائدة التي يحاول تهريبها إلى السلسلة... وهاتان القطعتان المختلفتان من البيانات لا يمكن أن يكون لهما التلبيد نفسه (أو، على الأقل، من العسير جدًا معرفة أي بيانات ينبغي أن تكون في الكتلة لتحصل على قيمة التلبيد نفسها).

> **استجابة القراءة.**
>
> هل كل هذا مفهوم؟ ما الجديد المثير للاهتمام منه، وما القديم غير المثير؟ هل تشعر بالارتياح لأفكار سلسلة التلبيد، ولسبب كونها غير قابلة للتغيير؟

وهناك خصائص إضافية عدة تجعل سلسلة التلبيد سلسلةَ كتل، منها أن أجزاء من البيانات في الكتل يجب أن تحمل توقيعات رقمية صحيحة — وهو موضوع ناقشناه في هذا الفصل! — وأن الكتل الجديدة ناتجة عن **بروتوكول إجماع**. وتتيح هذه البروتوكولات لكل من يحصل على نسخة من سلسلة الكتل أن يثق بأنه يملك سلسلة كتل البيانات نفسها التي يملكها كل من يستخدم تلك السلسلة.

وبروتوكولات الإجماع موضوع في صفوف تشفير أكثر تقدّمًا: لا تتوقّف هنا، فهناك الكثير الممتع والمفيد والقوي لتتعلّمه في هذا المجال!
