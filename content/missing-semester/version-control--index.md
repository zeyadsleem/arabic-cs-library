أنظمة التحكم في الإصدارات (version control systems / VCSs) هي أدواتٌ تُستخدم لتتبّع التغييرات على الكود المصدري (أو مجموعاتٍ أخرى من الملفات والمجلدات). وكما يوحي الاسم، تساعد هذه الأدوات على الحفاظ على سجلٍّ (history) من التغييرات؛ كما أنها تُسهّل التعاون بين المطوّرين. منطقيًا، تتتبّع أنظمة التحكم في الإصدارات التغييرات على مجلدٍ ومحتوياته في سلسلةٍ من _اللقطات_ (snapshots)، حيث تجسّد كل لقطةٍ الحالة الكاملة للملفات/المجلدات داخل دليلٍ أعلى مستوى (top-level directory). كما تحتفظ أنظمة التحكم في الإصدارات ببياناتٍ وصفية مثل: من أنشأ كل لقطة، وما الرسائل المرتبطة بكل لقطة، وهكذا.

لماذا يعد التحكم في الإصدارات مفيدًا؟ حتى عندما تعمل وحدك، يتيح لك الاطلاع على اللقطات القديمة للمشروع، والاحتفاظ بسجلٍّ يوضّح سبب إجراء تغييراتٍ معيّنة، والعمل على فروع (branches) متوازيةٍ من التطوير، وغير ذلك الكثير. وعند العمل مع الآخرين، إنها أداةٌ لا تُقدَّر بثمن لمعرفة ما غيّره الآخرون، وكذلك لحل تعارضات التطوير المتزامن.

كما تتيح لك أنظمة التحكم في الإصدارات الحديثة الإجابة بسهولةٍ (وغالبًا تلقائيًا) عن أسئلةٍ مثل:

- من كتب هذه الوحدة؟
- متى عُدِّل هذا السطر بالذات من هذا الملف بالذات؟ وبواسطة من؟ ولماذا عُدِّل؟
- خلال آخر 1000 مراجعة، متى ولماذا توقّف اختبار وحدةٍ معيّن عن العمل؟

في حين توجد أنظمة تحكم في الإصدارات أخرى، فإن **Git** هو المعيار الفعلي (de facto) للتحكم في الإصدارات. هذه [رسوم XKCD](https://xkcd.com/1597/) الهزلية تلتقط سمعة Git:

![xkcd 1597](https://imgs.xkcd.com/comics/git.png)

لأن واجهة Git تجريدٌ مُسرِّب (leaky abstraction)، فإن تعلّم Git من الأعلى إلى الأسفل (بدءًا بواجهته / واجهة سطر الأوامر) قد يقود إلى الكثير من الارتباك. من الممكن حفظ حفنةٍ من الأوامر والتفكير فيها كتعويذاتٍ سحرية، واتّباع المنهج في الرسوم الهزلية أعلاه كلما حدث خطأٌ ما.

في حين أن واجهة Git قبيحةٌ بلا خلاف، فإن تصميمها الأساسي وأفكارها جميلة. فبينما يجب _حفظ_ واجهةٍ قبيحةٍ عن ظهر قلب، يمكن _فهم_ تصميمٍ جميل. لهذا السبب، نقدم شرحًا تصاعديًا (bottom-up) لـGit، بدءًا من نموذج البيانات (data model) الخاص به، ثم تغطية واجهة سطر الأوامر لاحقًا. وبمجرد فهم نموذج البيانات، يمكن فهم الأوامر بشكلٍ أفضل من حيث كيفية تلاعبها بنموذج البيانات الأساسي.

# نموذج بيانات Git

تكمن براعة Git في نموذج البيانات المُصمَّم بعناية الذي يتيح كل ميزات التحكم في الإصدارات الرائعة، مثل الحفاظ على السجل، ودعم الفروع، وتمكين التعاون.

## اللقطات (Snapshots)

يمثّل Git تاريخ مجموعةٍ من الملفات والمجلدات داخل دليلٍ أعلى مستوى كسلسلةٍ من اللقطات. في مصطلحات Git، يُسمّى الملف "blob"، وهو مجرد مجموعةٍ من البايتات. أما الدليل فيُسمّى "tree"، وهو يربط الأسماء بالـblob أو الـtree (وبالتالي يمكن أن تحتوي الأدلة على أدلةٍ أخرى). اللقطة هي الـtree الأعلى مستوى الذي يتم تتبّعه. على سبيل المثال، قد يكون لدينا tree على النحو التالي:

```
<root> (tree)
|
+- foo (tree)
|  |
|  + bar.txt (blob, contents = "hello world")
|
+- baz.txt (blob, contents = "git is wonderful")
```

يحتوي الـtree الأعلى مستوى على عنصرين: tree اسمه "foo" (يحتوي هو نفسه على عنصرٍ واحدٍ: blob اسمه "bar.txt")، وblob اسمه "baz.txt".

## نمذجة التاريخ: ربط اللقطات

كيف ينبغي لنظام التحكم في الإصدارات ربط اللقطات ببعضها؟ أحد النماذج البسيطة هو امتلاك تاريخٍ خطّي. سيكون التاريخ قائمةً باللقطات بترتيبٍ زمني. ولأسبابٍ عديدة، لا يستخدم Git نموذجًا بسيطًا مثل هذا.

في Git، التاريخ هو رسم بياني موجَّه لا حلقاتيّ (directed acyclic graph / DAG) من اللقطات. قد يبدو ذلك كلفظةٍ رياضيةٍ فاخرة، لكن لا تُرعَب. كل ما يعنيه هذا أن كل لقطةٍ في Git تشير إلى مجموعةٍ من "الآباء" (parents)، أي اللقطات التي سبقتها. إنها مجموعةُ آباءٍ وليس أبًا واحدًا (كما في التاريخ الخطّي) لأن اللقطة قد تنحدر من آباء متعددين، على سبيل المثال بسبب دمج (merging) فرعين متوازيين من التطوير.

يسمّي Git هذه اللقطات "commits". قد يبدو تصوّر سجل الـcommits شيئًا مثل هذا:

```
o <-- o <-- o <-- o
            ^
             \
              --- o <-- o
```

في الرسم الحرفي أعلاه، تقابل `o`س الـcommits الفردية (اللقطات). تشير الأسهم إلى والد كل commit (إنها علاقة "يأتي قبل"، وليست "يأتي بعد"). بعد الـcommit الثالث، يتفرّع التاريخ إلى فرعين منفصلين. قد يقابل هذا، على سبيل المثال، تطوير ميزتين منفصلتين بالتوازي، وبشكلٍ مستقلٍ عن بعضهما. في المستقبل، قد يُدمج هذان الفرعان لإنشاء لقطةٍ جديدةٍ تدمج الميزتين معًا، منتجةً تاريخًا جديدًا يبدو هكذا، مع عرض commit الدمج المُنشأ حديثًا بخطٍ عريض:

```
o <-- o <-- o <-- o <---- o
            ^            /
             \          v
              --- o <-- o
```

الـcommits في Git غير قابلةٍ للتغيير (immutable). هذا لا يعني أنه لا يمكن تصحيح الأخطاء؛ بل إن "تعديلات" سجل الـcommits تُنشئ في الواقع commits جديدةً بالكامل، ويُحدَّث المراجع (references، انظر أدناه) لتشير إلى الجديدة.

## نموذج البيانات، ككودٍ زائف (pseudocode)

قد يكون من المفيد رؤية نموذج بيانات Git مكتوبًا في شكل كودٍ زائف:

```
// a file is a bunch of bytes
type blob = array<byte>

// a directory contains named files and directories
type tree = map<string, tree | blob>

// a commit has parents, metadata, and the top-level tree
type commit = struct {
    parents: array<commit>
    author: string
    message: string
    snapshot: tree
}
```

إنه نموذجٌ نظيفٌ وبسيطٌ للتاريخ.

## الكائنات والمعالجة بالمحتوى (Content-Addressing)

"الكائن" (object) هو blob أو tree أو commit:

```
type object = blob | tree | commit
```

في مخزن بيانات Git، تُعالَج جميع الكائنات بالمحتوى عبر [تجزئة SHA-1](https://en.wikipedia.org/wiki/SHA-1) الخاصة بها.

```
objects = map<string, object>

def store(object):
    id = sha1(object)
    objects[id] = object

def load(id):
    return objects[id]
```

تُوحَّد الـblob والـtree والـcommit بهذه الطريقة: فهي جميعًا كائنات. وعندما تشير إلى كائناتٍ أخرى، فإنها لا _تحتويها_ فعليًا في تمثيلها على القرص، بل تحمل مرجعًا لها عبر تجزئتها.

على سبيل المثال، يبدو الـtree الخاص بهيكل الدليل المثال أعلاه (مُصوَّرًا باستخدام `git cat-file -p 698281bc680d1995c5f4caaf3359721a5a58d48d`) هكذا:

```
100644 blob 4448adbf7ecd394f42ae135bbeed9676e894af85    baz.txt
040000 tree c68d233a33c5c06e0340e4c224f0afca87c8ce87    foo
```

يحتوي الـtree نفسه على مؤشراتٍ لمحتوياته، `baz.txt` (blob) و`foo` (tree). وإذا نظرنا إلى المحتويات المُعالَجة بالعنوان بالتجزئة المقابلة لـbaz.txt باستخدام `git cat-file -p 4448adbf7ecd394f42ae135bbeed9676e894af85`، نحصل على ما يلي:

```
git is wonderful
```

## المراجع (References)

الآن، يمكن تحديد جميع اللقطات عبر تجزئات SHA-1 الخاصة بها. هذا أمرٌ غير مريح، لأن البشر ليسوا جيدين في تذكّر سلاسلٍ من 40 حرفًا سداسيًا عشريًا.

حلّ Git لهذه المشكلة هو أسماءٌ قابلةٌ للقراءة البشرية لتجزئات SHA-1، تُسمّى "مراجع" (references). المراجع هي مؤشراتٌ إلى commits. وعلى عكس الكائنات، التي غير قابلةٍ للتغيير، فإن المراجع قابلةٌ للتغيير (يمكن تحديثها لتشير إلى commit جديد). على سبيل المثال، يشير المرجع `master` عادةً إلى أحدث commit في فرع التطوير الرئيسي.

```
references = map<string, string>

def update_reference(name, id):
    references[name] = id

def read_reference(name):
    return references[name]

def load_reference(name_or_id):
    if name_or_id in references:
        return load(references[name_or_id])
    else:
        return load(name_or_id)
```

بهذا، يمكن لـGit استخدام أسماءٍ قابلةٍ للقراءة البشرية مثل "master" للإشارة إلى لقطةٍ معيّنةٍ في التاريخ، بدلًا من سلسلةٍ سداسيةٍ عشريةٍ طويلة.

أحد التفاصيل هو أننا غالبًا نريد مفهوم "أين نحن الآن" في التاريخ، حتى نعرف، عندما نلتقط لقطةً جديدة، بالنسبة إلى ماذا هي (كيف نضبط حقل `parents` في الـcommit). في Git، ذلك "المكان الذي نحن فيه الآن" هو مرجعٌ خاصٌّ يُسمّى "HEAD".

## المستودعات (Repositories)

أخيرًا، يمكننا تعريف ما هو مستودع Git (بشكلٍ تقريبي): إنه بيانات `objects` و`references`.

على القرص، كل مخازن Git هي كائناتٌ ومراجع: هذا كل ما في نموذج بيانات Git. كل أوامر `git` تقابل تلاعبًا ما في رسم الـcommit البياني بإضافة كائناتٍ وإضافة/تحديث المراجع.

عندما تكتب أي أمرٍ، فكّر في التلاعب الذي يجريه الأمر على بنية الرسم البياني الأساسية. وعلى العكس، إذا كنت تحاول إجراء نوعٍ معيّنٍ من التغيير على رسم الـcommit البياني، مثل "تجاهل التغييرات غير الملتزمة واجعل مرجع 'master' يشير إلى commit `5d83f9e`"، فمن المحتمل وجود أمرٍ لفعل ذلك (مثلًا، في هذه الحالة: `git checkout master; git reset --hard 5d83f9e`).

# منطقة التدريج (Staging area)

هذا مفهومٌ آخر مستقلٌّ عن نموذج البيانات، لكنه جزءٌ من واجهة إنشاء الـcommits.

إحدى الطرق التي قد تتخيّل بها تنفيذ التقاط اللقطات الموصوف أعلاه هي امتلاك أمر "إنشاء لقطة" يُنشئ لقطةً جديدةً استنادًا إلى _الحالة الحالية_ لدليل العمل (working directory). تعمل بعض أدوات التحكم في الإصدارات بهذه الطريقة، لكن ليس Git. نحن نريد لقطاتٍ نظيفة، وقد لا يكون من المثالي دائمًا صنع لقطةٍ من الحالة الحالية. على سبيل المثال، تخيّل سيناريو نفّذت فيه ميزتين منفصلتين، وتريد إنشاء commitين منفصلين، حيث يُدخل الأول الميزة الأولى، والثاني الميزة الثانية. أو تخيّل سيناريو أضفت فيه جمل طباعةٍ لتصفية الأخطاء في كل أنحاء كودك، مع إصلاحٍ لخللٍ؛ تريد الالتزام بإصلاح الخلل مع تجاهل جميع جمل الطباعة.

يستوعب Git مثل هذه السيناريوهات بالسماح لك بتحديد أيّ التعديلات ينبغي تضمينها في اللقطة التالية عبر آليةٍ تسمى "منطقة التدريج" (staging area).

# واجهة سطر أوامر Git

لتجنّب تكرار المعلومات، لن نشرح الأوامر أدناه بالتفصيل في هذه الملاحظات. راجع كتاب [Pro Git](https://git-scm.com/book/en/v2) الموصى به بشدة لمزيدٍ من المعلومات، أو شاهد فيديو المحاضرة.

## الأساسيات

- `git help <command>`: الحصول على مساعدةٍ لأمر git
- `git init`: إنشاء مستودع git جديد، تُخزَّن بياناته في دليل `.git`
- `git status`: يخبرك بما يجري
- `git add <filename>`: إضافة ملفات إلى منطقة التدريج
- `git commit`: إنشاء commit جديد
    - اكتب [رسائل commit جيدة](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html)!
    - والمزيد من الأسباب لكتابة [رسائل commit جيدة](https://chris.beams.io/posts/git-commit/)!
- `git log`: يعرض سجلًّا مبسّطًا للتاريخ
- `git log --all --graph --decorate`: يصور التاريخ كرسمٍ بيانيٍّ موجَّهٍ لا حلقاتي
- `git diff <filename>`: يعرض التغييرات التي أجريتها بالنسبة إلى منطقة التدريج
- `git diff <revision> <filename>`: يعرض الفروقات في ملفٍ بين اللقطات
- `git checkout <revision>`: تحديث HEAD (والفرع الحالي إذا كنت تتفقد فرعًا)

## التفرع والدمج

- `git branch`: يعرض الفروع
- `git branch <name>`: إنشاء فرع
- `git switch <name>`: التبديل إلى فرع
- `git checkout -b <name>`: إنشاء فرعٍ والتبديل إليه
    - نفس `git branch <name>; git switch <name>`
- `git merge <revision>`: دمجٌ في الفرع الحالي
- `git mergetool`: استخدام أداةٍ فاخرة للمساعدة في حل تعارضات الدمج
- `git rebase`: إعادة بناء مجموعة الرقع (patches) على قاعدةٍ جديدة

## المستودعات البعيدة (Remotes)

- `git remote`: سرد المستودعات البعيدة
- `git remote add <name> <url>`: إضافة مستودعٍ بعيد
- `git push <remote> <local branch>:<remote branch>`: إرسال الكائنات إلى المستودع البعيد وتحديث مرجعه
- `git branch --set-upstream-to=<remote>/<remote branch>`: إعداد المراسلة بين الفرع المحلي والفرع البعيد
- `git fetch`: جلب الكائنات/المراجع من مستودعٍ بعيد
- `git pull`: نفس `git fetch; git merge`
- `git clone`: تنزيل المستودع من مستودعٍ بعيد

## التراجع

- `git commit --amend`: تعديل محتويات/رسالة commit
- `git reset <file>`: إزالة ملفٍ من التدريج
- `git restore`: تجاهل التغييرات

# Git المتقدم

- `git config`: Git [قابلٌ للتخصيص بدرجةٍ كبيرة](https://git-scm.com/docs/git-config)
- `git clone --depth=1`: استنساخٌ ضحل، دون سجل الإصدارات الكامل
- `git add -p`: تدريجٌ تفاعلي
- `git rebase -i`: إعادة بناءٍ تفاعلية
- `git blame`: يظهر من عدّل آخر سطرٍ
- `git stash`: إزالة التعديلات مؤقتًا من دليل العمل
- `git bisect`: بحثٌ ثنائي في التاريخ (مثلًا للانحدارات)
- `git revert`: إنشاء commit جديدٍ يعكس تأثير commitٍ سابق
- `git worktree`: تفقّد فروعٍ متعددةٍ في الوقت نفسه
- `.gitignore`: [حدّد](https://git-scm.com/docs/gitignore) الملفات غير المتتبَّعة عمدًا لتجاهلها

# أمور متفرقة

- **واجهات رسومية (GUIs)**: يوجد [عملاء واجهاتٍ رسومية](https://git-scm.com/downloads/guis) عديدةٌ لـGit. نحن شخصيًا لا نستخدمها ونستخدم واجهة سطر الأوامر بدلًا منها.
- **تكامل مع مُعالج الأوامر**: من المفيد جدًا وجود حالة Git كجزءٍ من موجه مُعالج الأوامر الخاص بك ([zsh](https://github.com/olivierverdier/zsh-git-prompt)، [bash](https://github.com/magicmonty/bash-git-prompt)). وغالبًا ما تكون مضمّنةً في أطرٍ مثل [Oh My Zsh](https://github.com/ohmyzsh/ohmyzsh).
- **تكامل مع المحرر**: على نحوٍ مماثل لما سبق، تكاملاتٌ مفيدةٌ بميزاتٍ عديدة. [fugitive.vim](https://github.com/tpope/vim-fugitive) هو التكامل القياسي لـVim.
- **سير العمل (Workflows)**: علّمناك نموذج البيانات، إضافةً إلى بعض الأوامر الأساسية؛ لم نخبرك بالممارسات التي ينبغي اتباعها عند العمل على مشاريع كبيرة (وهناك [مقارباتٌ](https://nvie.com/posts/a-successful-git-branching-model/) [متعددةٌ](https://www.endoflineblog.com/gitflow-considered-harmful) [ومختلفةٌ](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)).
- **GitHub**: Git ليس GitHub. لدى GitHub طريقةٌ محددةٌ للمساهمة بالكود في مشاريع الآخرين، تُسمّى [طلبات السحب (pull requests)](https://help.github.com/en/github/collaborating-with-issues-and-pull-requests/about-pull-requests).
- **مزودو Git آخرون**: GitHub ليس مميزًا: هناك مضيفاتٌ عديدةٌ لمستودعات Git، مثل [GitLab](https://about.gitlab.com/) و[BitBucket](https://bitbucket.org/).

- [Git for Computer Scientists](https://eagain.net/articles/git-for-computer-scientists/) شرحٌ قصيرٌ لنموذج بيانات Git، برمزٍ زائفٍ أقل ورسومٍ بيانيةٍ أكثر فخامةً من هذه الملاحظات.
- [Git from the Bottom Up](https://jwiegley.github.io/git-from-the-bottom-up/) شرحٌ مفصّلٌ لتفاصيل تنفيذ Git بما يتجاوز نموذج البيانات فقط، للمهتمين.
- [How to explain git in simple words](https://smusamashah.github.io/blog/2017/10/14/explain-git-in-simple-words)
- [Learn Git Branching](https://learngitbranching.js.org/) لعبةٌ قائمةٌ على المتصفح تُعلّمك Git.

# تمارين

1. إذا لم تكن لديك أي خبرةٍ سابقة مع Git، فجرّب إما قراءة الفصلين الأولين من [Pro Git](https://git-scm.com/book/en/v2) أو متابعة برنامجٍ تعليميٍّ مثل [Learn Git Branching](https://learngitbranching.js.org/). وأثناء عملك فيه، اربط أوامر Git بنموذج البيانات.
1. استنسخ [مستودع موقع المقرر الدراسي](https://github.com/missing-semester/missing-semester).
    1. استكشف سجل الإصدارات بتصويره كرسمٍ بياني.
    1. من هو آخر شخصٍ عدّل `README.md`؟ (تلميح: استخدم `git log` مع وسيطٍ).
    1. ما رسالة commit المرتبطة بآخر تعديلٍ على سطر `collections:` في `_config.yml`؟ (تلميح: استخدم `git blame` و`git show`).
1. من الأخطاء الشائعة عند تعلّم Git الالتزام بملفاتٍ كبيرةٍ لا ينبغي أن يديرها Git، أو إضافة معلوماتٍ حساسة. جرّب إضافة ملفٍ إلى مستودعٍ، وإجراء بعض الـcommits ثم حذف ذلك الملف من _السجل_ (وليس من أحدث commit فقط). قد تريد الاطلاع على [هذا](https://help.github.com/articles/removing-sensitive-data-from-a-repository/).
1. استنسخ مستودعًا ما من GitHub، وعدّل أحد ملفاته الموجودة. ماذا يحدث عند تنفيذ `git stash`؟ ماذا ترى عند تشغيل `git log --all --oneline`؟ نفّذ `git stash pop` للتراجع عمّا فعلته بـ`git stash`. في أي سيناريو قد يكون هذا مفيدًا؟
1. مثل الكثير من أدوات سطر الأوامر، يوفر Git ملف إعداداتٍ (أو ملف نقطة (dotfile)) يُسمّى `~/.gitconfig`. أنشئ اسمًا مستعارًا (alias) في `~/.gitconfig` بحيث يعطيك تنفيذ `git graph` مخرجات `git log --all --graph --decorate --oneline`. يمكنك فعل ذلك إما بتحرير ملف `~/.gitconfig` مباشرةً، أو باستخدام أمر `git config` لإضافة الاسم المستعار. يمكن العثور على معلوماتٍ حول أسماء Git المستعارة [هنا](https://git-scm.com/book/en/v2/Git-Basics-Git-Aliases).
1. يمكنك تعريف أنماط التجاهل العامة في `~/.gitignore_global` بعد تنفيذ `git config --global core.excludesfile ~/.gitignore_global`. يحدد هذا موقع ملف التجاهل العام الذي سيستخدمه Git، لكنك ما زلت بحاجةٍ إلى إنشاء الملف يدويًا في ذلك المسار. أعدد ملف gitignore العام لديك لتجاهل الملفات المؤقتة الخاصة بنظام التشغيل أو المحرر، مثل `.DS_Store`.
1. اعمل fork على [مستودع موقع المقرر الدراسي](https://github.com/missing-semester/missing-semester)، وابحث عن خطأٍ إملائيٍّ أو أي تحسينٍ آخر يمكنك إجراؤه، وقدّم طلب سحبٍ (pull request) على GitHub (قد تريد الاطلاع على [هذا](https://github.com/firstcontributions/first-contributions)). يُرجى تقديم طلبات سحبٍ مفيدةٍ فقط (لا تُرسل لنا رسائل مزعجة من فضلك!). إذا لم تجد تحسينًا لتجريه، يمكنك تخطّي هذا التمرين.
1. تدرب على حل تعارضات الدمج بمحاكاة سيناريو تعاونٍ:
    1. أنشئ مستودعًا جديدًا بالأمر `git init` وأنشئ ملفًا اسمه `recipe.txt` بأسطرٍ قليلة (مثلًا، وصفةً بسيطة).
    1. التزم به، ثم أنشئ فرعين: `git branch salty` و`git branch sweet`.
    1. في فرع `salty`، عدّل سطرًا (مثلًا، غيّر "1 cup sugar" إلى "1 cup salt") والتزم.
    1. في فرع `sweet`، عدّل السطر نفسه بشكلٍ مختلف (مثلًا، غيّر "1 cup sugar" إلى "2 cups sugar") والتزم.
    1. الآن بدّل إلى `master` وجرّب `git merge salty` ثم `git merge sweet`. ماذا يحدث؟ انظر إلى محتويات `recipe.txt` — ماذا تعني العلامات `<<<<<<<` و`=======` و`>>>>>>>`؟
    1. حلّ التعارض بتحرير الملف لإبقاء المحتوى الذي تريده، وإزالة علامات التعارض، وإكمال الدمج بالأمرين `git add` و`git commit` (أو `git merge --continue`). بدلًا من ذلك، جرّب استخدام `git mergetool` لحل التعارض بأداة دمجٍ رسوميةٍ أو قائمةٍ على الطرفية.
    1. استخدم `git log --graph --oneline` لتصوّر سجل الدمج الذي أنشأته للتو.
