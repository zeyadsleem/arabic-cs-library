WebSocket: اتصالات ثنائية الاتجاه

مقدمة (Introduction)

يتيح WebSocket بثًّا ثنائي الاتجاه قائمًا على الرسائل (message-oriented streaming) للنصوص والبيانات الثنائية بين العميل والخادم. وهو أقرب واجهة برمجة تطبيقات (API) إلى مقبس شبكة خام (raw network socket) في المتصفح. غير أن اتصال WebSocket هو أكثر بكثير من مجرّد مقبس شبكة، إذ يُجري المتصفح تجريدًا (abstraction) لكل التعقيدات خلف واجهة برمجة تطبيقات بسيطة ويقدّم عددًا من الخدمات الإضافية:

WebSocket هو أحد أكثر وسائل النقل (transports) تنوّعًا ومرونةً المتاحة في المتصفح. وتتيح واجهته البسيطة والمحدودة أن نُنشئ ونسلّم بروتوكولات تطبيقية اعتباطية (arbitrary application protocols) بين العميل والخادم—من حمولات JSON البسيطة إلى تنسيقات رسائل ثنائية مخصّصة—بأسلوب بثّ (streaming)، حيث يستطيع أيّ من الطرفين إرسال البيانات في أي وقت. لكنّ المقابل (trade-off) في البروتوكولات المخصّصة أنها مخصّصة بامتياز. إذ على التطبيق أن يعالج غياب إدارة الحالة (state management) والضغط (compression) والتخزين المؤقت (caching) وغيرها من الخدمات التي يوفّرها المتصفح عادةً. وهناك دائمًا قيودٌ في التصميم ومقايضاتٌ في الأداء، واستخدام WebSocket ليس استثناءً من ذلك. باختصار، WebSocket ليس بديلًا عن HTTP أو XHR أو SSE، ولأفضل أداء من الضروري أن نستثمر نقاط قوّة كل وسيلة نقل. وWebSocket مجموعة من عدة معايير: فواجهة WebSocket API يعرّفها W3C، وبروتوكول WebSocket (RFC 6455) وامتداداته يعرّفها مجموعة عمل HyBi Working Group (IETF).

واجهة WebSocket API (WebSocket API)

إنّ واجهة WebSocket API التي يوفّرها المتصفح صغيرةٌ وبسيطةٌ على نحو لافت. ومرةً أخرى، يتولّى المتصفح كلَّ التفاصيل منخفضة المستوى الخاصة بإدارة الاتصال ومعالجة الرسائل. ولبدء اتصال جديد، نحتاج إلى عنوان URL لمورد WebSocket وبعض دوال الاستدعاء (callbacks) الخاصة بالتطبيق:

var ws = new WebSocket('wss://example.com/socket'); 

ws.onerror = function (error) { ... } 
ws.onclose = function () { ... } 

ws.onopen = function () { 
 ws.send("Connection established. Hello server!"); 
}

ws.onmessage = function(msg) { 
 if(msg.data instanceof Blob) { 
 processBlob(msg.data);
 } else {
 processText(msg.data);
 }
}

الواجهة تتحدّث عن نفسها. وفي الواقع، ينبغي أن تبدو مشابهةً جدًا لواجهة EventSource API التي رأيناها في الفصل السابق. وهذا مقصود، إذ يقدّم WebSocket وظائف مشابهةً ومُوسَّعة. وعلى الرغم من ذلك، هناك أيضًا عددٌ من الاختلافات الجوهرية. فلننظر إليها واحدًا تلو الآخر.

محاكاة WebSocket (Emulating WebSocket)

لقد مرّ بروتوكول WebSocket بعددٍ من المراجعات (revisions) وعمليات التراجع في التنفيذ (implementation rollbacks) وتحقيقاتٍ أمنية. لكنّ الخبر الجيّد هو أنّ أحدث إصدار (v13) الذي يعرّفه RFC6455 مدعوم الآن في جميع المتصفحات الحديثة. والاستثناء الوحيد الذي يستحقّ الذكر هو متصفّح Android. ولأحدث حالة، انظر http://caniuse.com/websockets. وعلى غرار استراتيجية polyfill الخاصة بـ SSE (محاكاة EventSource بـ JavaScript مخصّص)، يمكن محاكاة واجهة WebSocket API في المتصفح عبر مكتبة JavaScript اختيارية. غير أنّ الجزء الصعب في محاكاة WebSocket ليس الواجهة، بل وسيلة النقل! ونتيجةً لذلك، فإنّ اختيار مكتبة polyfill ووسيلة نقلها الاحتياطية (XHR polling أو EventSource أو iframe polling وغيرها) سيؤثّر تأثّرًا كبيرًا في أداء جلسة WebSocket المُحاكاة. ولتبسيط النشر عبر المتصفحات، توفّر مكتبات شهيرة مثل SockJS تنفيذًا لكائن شبيه بـ WebSocket في المتصفح، لكنها تتقدّم خطوةً أبعد أيضًا بتوفير خادم مخصّص (custom server) ينفّذ دعم WebSocket ومجموعةً متنوعةً من وسائل النقل البديلة. وجمعُ الخادم المخصّص مع العميل هو ما يتيح «التراجع السلس» (seamless fallback): إذ يتضرّر الأداء، لكنّ واجهة التطبيق تبقى كما هي. أمّا مكتبات أخرى مثل Socket.IO فتذهب أبعد من ذلك بتنفيذ ميزات إضافية، مثل نبضات الحياة (heartbeats) والمهلات (timeouts) ودعم إعادة الاتصال التلقائية (automatic reconnects) وغيرها، بالإضافة إلى وظيفة التراجع متعدد الوسائط (multitransport fallback). وحينما تدرس مكتبة polyfill أو «إطار عمل آنيّ» (real-time framework) مثل Socket.IO، فابح عن التنفيذ الأساسي (underlying implementation) وضبط العميل والخادم عنايةً فائقة: استثمر دائمًا واجهة WebSocket الأصلية (native) للحصول على أفضل أداء، وتأكّد من أنّ وسائل النقل الاحتياطية تحقّق أهدافك الأدائية.

مخططات عنوان URL لـ WS و WSS (WS and WSS URL Schemes)

يستخدم عنوان URL لمورد WebSocket مخططه (scheme) الخاص: ws للاتصال بنصٍ صريح (plain-text)، مثل ws://example.com/socket، وwss عندما تكون هناك حاجة إلى قناة مشفّرة (TCP+TLS). ولماذا المخطط المخصّص بدلًا من المألوف http؟ إنّ حالة الاستخدام الأساسية لبروتوكول WebSocket هي توفير قناة اتصال ثنائية الاتجاه مُحسَّنة (optimized) بين التطبيقات العاملة في المتصفح وبين الخادم. غير أنّ بروتوكول WebSocket على مستوى السلك (wire protocol) يمكن استخدامه خارج المتصفح، ويمكن التفاوض عليه عبر تبادلٍ غير قائم على HTTP. ونتيجةً لذلك، اختارت مجموعة عمل HyBi Working Group اعتماد مخطط URL مخصّص. ورغم أنّ المخطط المخصّص يتيح خيار التفاوض غير المعتمد على HTTP، فلا توجد عمليًا أيّ معايير قائمة اليوم لآليات مصافحة بديلة (alternative handshake mechanisms) لإنشاء جلسة WebSocket.

استقبال البيانات النصية والثنائية (Receiving Text and Binary Data)

يتكوّن اتصال WebSocket من رسائل وشيفرة تطبيق، ولا يحتاج إلى الانشغال بالتخزين المؤقت (buffering) وتحليل (parsing) البيانات وإعادة بناء ما يُستقبل. فمثلًا، إذا أرسل الخادم حمولة (payload) حجمها 1 MB، فلا تُستدعى دالة الاستدعاء onmessage الخاصة بالتطبيق إلا عندما تتوفّر الرسالة كاملةً في جانب العميل. وإلى جانب ذلك، لا يفترض بروتوكول WebSocket شيئًا ولا يفرض قيودًا على حمولة التطبيق: فبيانات النص والبيانات الثنائية كلاهما محلّ الفحص. وداخليًا، لا يتتبّع البروتوكول سوى معاملين اثنين عن الرسالة: طول الحمولة كحقل متغيّر الطول (variable-length field)، ونوع الحمولة للتمييز بين النقل بترميز UTF-8 وبين النقل الثنائي. وحين يستقبل المتصفح رسالةً جديدة، فإنّه يحوّلها تلقائيًا إلى كائن DOMString للبيانات النصية، أو إلى كائن Blob للبيانات الثنائية، ثم يمرّرها مباشرةً إلى التطبيق. والخيار الوحيد الآخر، الذي يعمل كتلميحٍ للأداء (performance hint) وتحسينٍ للعميل، هو أن تطلب من المتصفح تحويل البيانات الثنائية المستقبَلة إلى ArrayBuffer بدلًا من Blob:

var ws = new WebSocket('wss://example.com/socket');
ws.binaryType = "arraybuffer"; 

ws.onmessage = function(msg) {
 if(msg.data instanceof ArrayBuffer) {
 processArrayBuffer(msg.data);
 } else {
 processText(msg.data);
 }
}

يمكن لوكلاء المستخدم (user agents) استخدام هذا كتلميحٍ لكيفية التعامل مع البيانات الثنائية الواردة: إذا كانت الخاصية مضبوطة على "blob" فإنّه من الآمن لفّها على القرص (spool it to disk)، وإذا كانت مضبوطة على "arraybuffer" فالأرجح أن يكون الاحتفاظ بالبيانات في الذاكرة أكثر كفاءةً. وبالطبع، يُشجَّع وكلاء المستخدم على استخدام استدلالات (heuristics) أدقّ لتحديد ما إذا كان ينبغي الاحتفاظ بالبيانات الواردة في الذاكرة أم لا…

واجهة WebSocket API، توصية W3C المرشّحة (W3C Candidate Recommendation)

يمثّل كائن Blob كائنًا شبيهًا بالملف (file-like object) من بيانات خام غير قابلة للتغيير (immutable). فإذا كنت لا تحتاج إلى تعديل البيانات ولا إلى تقسيمها إلى أجزاء أصغر، فإنّه الصيغة المثلى—مثلًا يمكنك تمرير كائن Blob بأكمله إلى وسم صورة (image tag) (انظر المثال في تنزيل البيانات باستخدام XHR). ومن جهة أخرى، إذا احتجت إلى إجراء معالجة إضافية على البيانات الثنائية، فإنّ ArrayBuffer سيكون على الأرجح الخيار الأنسب.

فكّ ترميز البيانات الثنائية باستخدام JavaScript (Decoding Binary Data with JavaScript)

إنّ ArrayBuffer هو مخزن عام (generic) لبيانات ثنائية ثابتة الطول. لكنّ ArrayBuffer يمكن أن يُستخدم لإنشاء كائن ArrayBufferView واحد أو أكثر، وكلٌّ منها يستطيع عرض محتويات المخزن بصيغة محدّدة. فمثلًا، لنفترض لدينا بنية بيانات ثنائية شبيهة بـ C التالية:

struct someStruct {
 char username[16];
 unsigned short id;
 float scores[32];
};

بالغطر على كائن ArrayBuffer من هذا النوع، يمكننا إنشاء عدة عروض (views) على المخزن نفسه، كلٌّ منها بإزاحته الخاصة (offset) ونوع بياناته الخاص:

var buffer = msg.data;

var usernameView = new Uint8Array(buffer, 0, 16);
var idView = new Uint16Array(buffer, 16, 1);
var scoresView = new Float32Array(buffer, 18, 32);

console.log("ID: " + idView[0] + " username: " + usernameView[0]);
for (var j = 0; j < 32; j++) { console.log(scoresView[j]) }

يأخذ كلُّ عرض المخزنَ الأصل (parent buffer) وإزاحة البداية بالبايت (starting byte offset) وعددَ العناصر المطلوب معالجتها—تُحسب الإزاحة بناءً على حجم الحقول السابقة. ونتيجةً لذلك، تمنح ArrayBuffer و WebSocket تطبيقاتنا كلَّ الأدوات اللازمة لبثِّ البيانات الثنائية ومعالجتها داخل المتصفح.

إرسال البيانات النصية والثنائية (Sending Text and Binary Data)

بمجرد أن يُرسَم اتصال WebSocket، يستطيع العميل إرسال واستقبال رسائل UTF-8 والرسائل الثنائية متى شاء. ويوفّر WebSocket قناة اتصال ثنائية الاتجاه، تتيح تسليم الرسائل في الاتجاهين عبر اتصال TCP نفسه:

var ws = new WebSocket('wss://example.com/socket');

ws.onopen = function () {
 socket.send("Hello server!"); 
 socket.send(JSON.stringify({'msg': 'payload'})); 

 var buffer = new ArrayBuffer(128);
 socket.send(buffer); 

 var intview = new Uint32Array(buffer);
 socket.send(intview); 

 var blob = new Blob([buffer]);
 socket.send(blob); 
}

تقبل واجهة WebSocket API إمّا كائن DOMString، الذي يُرمَّز بترميز UTF-8 على السلك، وإمّا أحد كائنات ArrayBuffer أو ArrayBufferView أو Blob للنقل الثنائي. لكنّ لاحظ أنّ خيارات النقل الثنائي الأخيرة هي مجرّد راحةٍ في الواجهة (API convenience): إذ على السلك، تُوسَم كلُّ إطار WebSocket (frame) إمّا ثنائيًّا أو نصّيًّا عبر بتٍ واحد. وبالتبعية، إذا احتاج التطبيق أو الخادم إلى معلومات أخرى عن نوع المحتوى (content-type) الخاصة بالحمولة، فينبغي لهما استخدام آلية إضافية للتواصل بشأن هذه البيانات. ودالة send() غير متزامنة (asynchronous): إذ يصفّ العميل البيانات المقدَّمة في طابور، وتعود الدالة فورًا. ونتيجةً لذلك، وخاصةً عند نقل حمولات كبيرة، لا تخلط بين سرعة العودة وإشارة مفادها أنّ البيانات قد أُرسلت! ولمراقبة مقدار البيانات التي صفّها المتصفح، يستطيع التطبيق الاستعلام عن الخاصية bufferedAmount على المقبس:

var ws = new WebSocket('wss://example.com/socket');

ws.onopen = function () {
 subscribeToApplicationUpdates(function(evt) { 
 if (ws.bufferedAmount == 0) 
 ws.send(evt.data); 
 });
};

يحاول المثال السابق إرسال تحديثات التطبيق إلى الخادم، لكنّه لا يفعل ذلك إلا إذا كانت الرسائل السابقة قد أُفرغت من مخزن العميل. ولماذا نُقحم أنفسنا بمثل هذه الفحوص؟ جميع رسائل WebSocket تُسلَّم بالترتيب الدقيق الذي صفَّ بها العميل. ونتيجةً لذلك، فإنّ تراكمًا كبيرًا للرسائل المصفوفة، أو حتى رسالةً واحدة كبيرة، سيؤخّر تسليم الرسائل التي تصفّ خلفها—وهذا هو حجب رأس السطر (head-of-line blocking)! وللعمل حول هذه المشكلة، يستطيع التطبيق تقسيم الرسائل الكبيرة إلى أجزاء أصغر، ومراقبة قيمة bufferedAmount بعناية لتفادي حجب رأس السطر، بل وتطبيق طابور أولويات (priority queue) خاص به للرسائل المعلّقة بدلًا من صفّها جميعها على المقبس عشوائيًّا. وتولّد تطبيقات كثيرة أصنافًا متعدّدة من الرسائل: تحديثات ذات أولوية عالية، مثل حِمل التحكّم (control traffic)، وتحديثات ذات أولوية منخفضة، مثل عمليات النقل في الخلفية. ولتحسين التسليم، ينبغي للتطبيق أن يولي عنايةً فائقة لكيفية صفّ كلّ نوع من الرسائل على المقبس ومتى يُصفّ!

التفاوض على البروتوكول الفرعي (Subprotocol Negotiation)

لا يفترض بروتوكول WebSocket شيئًا بشأن صيغة كلّ رسالة: فبتٌ واحد يتتبّع ما إذا كانت الرسالة تحتوي على بيانات نصية أم ثنائية، بحيث يمكن فكّ ترميزها بكفاءة لدى العميل والخادم، لكنّ محتوى الرسالة يبقى معتمًا (opaque) على غير ذلك. وإلى جانب ذلك، فعلى خلاف طلبات HTTP أو XHR، التي تتواصل بشأن بيانات وصفية إضافية عبر ترويسات HTTP في كل طلب واستجابة، لا يوجد أيّ آلية مماثلة لرسالة WebSocket. ونتيجةً لذلك، إذا لزم وجود بيانات وصفية إضافية عن الرسالة، فيجب على العميل والخادم أن يتّفقا على تطبيق بروتوكول فرعي (subprotocol) خاص بهما للتواصل بشأن هذه البيانات:

هذه القائمة مجرّد عيّنةٍ صغيرة من الاستراتيجيات الممكنة. ومرونة رسالة WebSocket وانخفاض حملها الزائد يأتيان بثمن شيفرة تطبيق إضافية. لكنّ تسلسل الرسائل (message serialization) وإدارة البيانات الوصفية ليسا سوى جزءٍ من المشكلة! فبمجرّد أن نحدّد صيغة التسلسل لرسائلنا، كيف نضمن أن يفهم كلٌّ من العميل والخادم الآخر؟ وكيف نبقيهما متزامنين؟ لحسن الحظ، يوفّر WebSocket واجهة التفاوض على البروتوكول الفرعي (subprotocol negotiation) بسيطة ومريحة لمعالجة المشكلة الثانية. ويستطيع العميل أن يُعلن للخادم البروتوكولات التي يدعمها كجزءٍ من مصافحة الاتصال الأولية:

var ws = new WebSocket('wss://example.com/socket',
 ['appProtocol', 'appProtocol-v2']); 

ws.onopen = function () {
 if (ws.protocol == 'appProtocol-v2') { 
 ...
 } else {
 ...
 }
}

كما يوضّح المثال السابق، يقبل مُنشئ WebSocket (the WebSocket constructor) مصفوفةً اختياريةً من أسماء البروتوكولات الفرعية، ما يتيح للعميل أن يُعلن قائمة البروتوكولات التي يفهمها أو التي مستعدّ لاستخدامها في هذا الاتصال. وتُرسَل القائمة المحدّدة إلى الخادم، ويُسمح للخادم بأن يختار أحد البروتوكولات التي أعلنها العميل. وإذا كان التفاوض على البروتوكول الفرعي ناجحًا، فإنّ دالة الاستدعاء onopen تُطلق في جانب العميل، ويستطيع التطبيق الاستعلام عن الخاصية protocol على كائن WebSocket لتحديد البروتوكول المختار. ومن جهة أخرى، إذا لم يدعم الخادم أيًّا من البروتوكولات التي أعلنها العميل، فإنّ مصافحة WebSocket تكون ناقصة: تُستدعى دالة الاستدعاء onerror ويُنهى الاتصال. وتُعرَّف أسماء البروتوكولات الفرعية من قبل التطبيق وتُرسَل كما هي المحدَّدة إلى الخادم أثناء مصافحة HTTP الأولية. وبخلاف ذلك، لا يؤثر البروتوكول الفرعي المحدَّد في جوهر واجهة WebSocket API.

بروتوكول WebSocket (WebSocket Protocol)

يتكوّن بروتوكول WebSocket على مستوى السلك (wire protocol) (RFC 6455) الذي طوّرته مجموعة عمل HyBi Working Group من مكوّنين رئيسيين على مستوى عالٍ: مصافحة HTTP الافتتاحية (opening HTTP handshake) المستخدَمة والتفاوض على معاملات الاتصال، وآلية تأطير رسائل ثنائية (binary message framing) تتيح تسليم البيانات النصية والثنائية بأسلوب قائم على الرسائل وبحمل زائد منخفض.

يحاول بروتوكول WebSocket معالجة أهداف تقنيات HTTP ثنائية الاتجاه القائمة في سياق البنية التحتية لـ HTTP القائمة؛ وعليه، صُمِّم للعمل عبر منفذَي HTTP 80 و 443… لكنّ التصميم لا يقيّد WebSocket بـ HTTP، ويمكن للتطبيقات المستقبلية أن تستعمل مصافحةً أبسط عبر منفذٍ مخصّص دون إعادة اختراع البروتوكول بأكمله.

بروتوكول WebSocket، RFC 6455

بروتوكول WebSocket بروتوكول مكتفٍ بذاته وقائم بذاته (fully functional, standalone) يمكن استخدامه خارج المتصفح. ومع ذلك، فإنّ تطبيقه الأساسي هو كونه وسيلة نقل ثنائية الاتجاه للتطبيقات القائمة على المتصفح.

طبقة التأطير الثنائي (Binary Framing Layer)

تتواصل تطبيقات WebSocket في جانبَي العميل والخادم عبر واجهة قائمة على الرسائل: يوفّر المرسِل حمولةً اعتباطية (arbitrary) بترميز UTF-8 أو ثنائية، ويُبلَّغ المستقبِل بوصولها عندما تتوفّر الرسالة كاملةً. ولتيسير ذلك، يستخدم WebSocket تنسيق تأطير ثنائيًا مخصّصًا (custom binary framing format) (الشكل 17-1)، يقسّم كلّ رسالة تطبيق إلى إطار واحد أو أكثر (frames)، وينقلها إلى الوجهة، ويعيد تجميعها، ثم يُبلّغ المستقبِل أخيرًا بعد استلام الرسالة كاملةً. الشكل 17-1. إطار WebSocket: 2–14 بايت + الحمولة إطار (Frame) أصغر وحدة اتصال، يحتوي كلٌّ منها على ترويسة إطار متغيّرة الطول وحمولة قد تحمل كلّ رسالة التطبيق أو جزءًا منها. رسالة (Message) تسلسلٌ كامل من الإطارات يقابل رسالة تطبيق منطقية. أمّا قرار تقسيم رسالة التطبيق إلى عدة إطارات فيتّخذه التنفيذ الأساسي لشيفرة التأطير في جانبَي العميل والخادم. وبذلك تبقى التطبيقات غافلةً تمامًا عن إطارات WebSocket الفردية وعن كيفية تنفيذ التأطير. ومع ذلك، فمن المفيد أن نفهم أبرز النقاط حول كيفية تمثيل كلّ إطار WebSocket على السلك:

تعدُّد الإشارات (multiplexing) لـ WebSocket وحجب رأس السطر (WebSocket Multiplexing and Head-of-Line Blocking)

WebSocket معرَّض لحجب رأس السطر (head-of-line blocking): فالرسائل يمكن تقسيمها إلى إطار واحد أو أكثر، لكنّ إطارات الرسائل المختلفة لا يمكن تشابكها (interleaved)، إذ لا يوجد ما يماثل «معرّف التدفّق» (stream ID) الموجود في آلية تأطير HTTP/2؛ انظر «التدفقات والرسائل والإطارات» (Streams, Messages, and Frames)). ونتيجةً لذلك، فإنّ الرسالة الكبيرة، حتى لو قُسّمت إلى عدة إطارات WebSocket، ستعطّل تسليم الإطارات المرتبطة بالرسائل الأخرى. فإذا كان تطبيقك يسلّم بيانات حسّاسة للزمن (latency-sensitive)، فانتبه إلى حجم حمولة كلّ رسالة، وفكّر في تقسيم الرسائل الكبيرة إلى عدة رسائل تطبيقية! كما أنّ غياب تعدُّد الإشارات (multiplexing) في مواصفة WebSocket الأساسية يعني أنّ كلّ اتصال WebSocket يحتاج إلى اتصال TCP مخصّص، وهو ما قد يصبح مشكلة محتملة في عمليات نشر HTTP/1.x بسبب العدد المحدود من الاتصالات لكل أصل (origin) الذي يحافظ عليه المتصفح؛ انظر «استنزاف موارد العميل والخادم» (Exhausting Client and Server Resources). ومن الجانب المُبشِّر، فإنّ «امتداد تعدُّد الإشارات لـ WebSockets» (Multiplexing Extension for WebSockets) الجديد الذي طوّرته مجموعة عمل HyBi Working Group يعالج هذا القيد الأخير:

تعدُّد إشارات WebSocket (WebSocket Multiplexing) (مسوّدة 10)

مع هذا الامتداد في مكانه، يمكن تعدُّد اتصالات WebSocket (القنوات) المتعدّدة فوق اتصال TCP نفسه. غير أن كلّ قناة على حدة تظلّ معرَّضةً لحجب رأس السطر! وبالتبعية، فإنّ أحد الحلول المحتملة هو استخدام قنوات مختلفة، أو اتصالات TCP مخصّصة، لتعدُّد الرسائل على التوازي. وأخيرًا، لاحظ أنّ الامتداد السابق لا يلزم إلا لاتصالات HTTP/1.x. ورغم أنّه لا تتوفّر بعدُ أيّ مواصفة رسمية لنقل إطارات WebSocket عبر HTTP/2، فإنّ ذلك سيكون أسهل بكثير: إذ إنّ HTTP/2 يملك تعدُّد تدفقات مدمجًا (built-in stream multiplexing)، ويمكن نقل اتصالات WebSocket متعدّدة داخل جلسة واحدة عبر تغليف إطارات WebSocket ضمن آلية تأطير HTTP/2.

امتدادات البروتوكول (Protocol Extensions)

تسمح مواصفة WebSocket بامتدادات البروتوكول (protocol extensions): إذ يمكن توسيع تنسيق السلك ودلالات بروتوكول WebSocket برموز تشغيل جديدة (opcodes) وحقول بيانات جديدة. ورغم أنّ هذا غير معتاد إلى حدٍّ ما، فإنّه ميزةٌ قويةٌ جدًّا، إذ يتيح للعميل والخادم تنفيذ وظائف إضافية فوق طبقة تأطير WebSocket الأساسية دون الحاجة إلى أيّ تدخّل أو تعاون من شيفرة التطبيق. ما بعض أمثلة امتدادات بروتوكول WebSocket؟ مجموعة عمل HyBi Working Group، المسؤولة عن تطوير مواصفة WebSocket، تذكر امتدادين رسميَّين قيد التطوير: «امتداد تعدُّد الإشارات لـ WebSockets» (A Multiplexing Extension for WebSockets) يوفّر هذا الامتداد طريقةً تتيح لاتصالات WebSocket المنطقية المنفصلة أن تتشارك اتصال نقل أساسيًا واحدًا. «امتدادات الضغط لـ WebSocket» (Compression Extensions for WebSocket) إطارٌ لإنشاء امتدادات WebSocket تضيف وظيفة الضغط إلى بروتوكول WebSocket. وكما ذكرنا سابقًا، يحتاج كلّ اتصال WebSocket إلى اتصال TCP مخصّص، وهو ما يجعله غير كفّء. ويعالج امتداد تعدُّد الإشارات هذه المشكلة بتوسيع كلّ إطار WebSocket بمعرّف إضافي هو «معرّف القناة» (channel ID) ليتيح لقنوات WebSocket الافتراضية المتعدّدة أن تتشارك اتصال TCP واحدًا. وعلى نحو مماثل، لا تقدّم مواصفة WebSocket الأساسية أيّ آلية ولا أيّ بنود لضغط البيانات المنقولة: إذ يحمل كلُّ إطار حمولة البيانات كما قدّمها التطبيق. ونتيجةً لذلك، ورغم أنّ هذا قد لا يمثّل مشكلةً لبنى البيانات الثنائية المحسَّنة، فإنّه قد يؤدّي إلى حمل زائد كبير بالبايتات في النقل ما لم يطبّق التطبيق منطق ضغط البيانات وفكّ ضغطها الخاص به. وبالمعنى الفعلي، يتيح امتداد الضغط ما يماثل التفاوض على ترميز النقل (transfer-encoding negotiation) الذي يوفّره HTTP. ولتفعيل امتداد واحد أو أكثر، على العميل أن يعلنها في مصافحة Upgrade الأولية، وعلى الخادم أن يختار الامتدادات التي ستُستخدم طوال عمر الاتصال المتفاوض عليه ويقرّها. ولمثال تطبيقي عملي، فلننظر الآن عن قرب إلى تسلسل Upgrade.

تعدُّد إشارات WebSocket والضغط في العالم الحقيقي (WebSocket Multiplexing and Compression in the Wild)

حتى منتصف عام 2013، لم يكن تعدُّد إشارات WebSocket مدعومًا في أيّ متصفّح شائع. وعلى نحو مماثل، فإنّ دعم الضغط محدود: إذ قد يعلن Google Chrome وأحدث متصفّحات WebKit عن امتداد «x-webkit-deflate-frame» للخادم. لكنّ deflate-frame مبنيٌّ على مراجعة قديمة للمعيار وسيُهمَل في المستقبل. وكما يدلّ الاسم، فإنّ الضغط لكلّ إطار (per-frame) يضغط محتويات الحمولة إطارًا بإطار، وهو أمرٌ دون المُثلى للرسائل الكبيرة التي قد تُقسَّم بين عدة إطارات. ونتيجةً لذلك، فقد انتقل أحدث مراجعات امتداد الضغط إلى الضغط لكلّ رسالة (per-message)—وهذا هو الخبر الجيّد. أمّا الخبر السيّئ هو أنّ الضغط لكلّ رسالة لا يزال تجريبيًّا (experimental) ولم يتوفّر بعدُ في أيّ متصفّح شائع. ونتيجةً لذلك، ينبغي للتطبيق أن يولي عنايةً فائقة لنوع المحتوى (content-type) في البيانات المنقولة وأن يطبّق ضغطه الخاص حيثما ينطبق. أي على الأقلّ حتى يتوفّر الدعم الأصلي لضغط WebSocket على نطاق واسع في جميع المتصفحات الشائعة. وهذا مهمٌّ بصفة خاصة للتطبيقات المحمولة، إذ يحمل كلّ بايتٍ غير ضروري تكاليف مرتفعة على المستخدم.

التفاوض على الترقية عبر HTTP (HTTP Upgrade Negotiation)

يقدّم بروتوكول WebSocket مجموعةً كبيرةً من الميزات القوية: اتصالات قائمة على الرسائل، وطبقة تأطير ثنائية خاصة به، والتفاوض على البروتوكول الفرعي، وامتدادات بروتوكول اختيارية، وغيرها. ونتيجةً لذلك، وقبل أن تُتبادل أيّ رسائل، يجب على العميل والخادم أن يتفاوضا على المعاملات المناسبة لإنشاء الاتصال. ويقدّم استغلال HTTP لأداء المصافحة (handshake) عدة مزايا. أولًا، يجعل WebSockets متوافقًا مع البنية التحتية لـ HTTP القائمة: إذ يمكن لخوادم WebSocket أن تعمل على المنفذين 80 و 443، وهما في كثير من الأحيان المنفذان المفتوحان الوحيدان أمام العميل. ثانيًا، يتيح لنا إعادة استخدام تدفّق HTTP Upgrade وتوسيعه بترويسات WebSocket مخصّصة لإجراء التفاوض: Sec-WebSocket-Version ترسلها العميل للإشارة إلى إصدار ("13" بالنسبة إلى RFC6455) من بروتوكول WebSocket الذي يريد استخدامه. وإذا لم يدعم الخادم إصدار العميل، فيجب أن يردّ بقائمة الإصدارات المدعومة. Sec-WebSocket-Key مفتاح مُولَّد تلقائيًّا يرسله العميل، ويعمل كـ«تحدٍّ» (challenge) يثبت به الخادم دعمه للإصدار المطلوب من البروتوكول. Sec-WebSocket-Accept استجابة الخادم التي تحتوي القيمة الموقَّعة لـ Sec-WebSocket-Key، ما يثبت أنّه يفهم إصدار البروتوكول المطلوب. Sec-WebSocket-Protocol يُستخدم للتفاوض على البروتوكول الفرعي للتطبيق: يعلن العميل قائمة البروتوكولات المدعومة؛ ويجب أن يردّ الخادم باسم بروتوكول واحد. Sec-WebSocket-Extensions يُستخدم للتفاوض على امتدادات WebSocket التي ستُستخدم في هذا الاتصال: يعلن العميل الامتدادات المدعومة، ويؤكّد الخادم واحدًا أو أكثر منها بإعادة الترويسة نفسها. وبذلك، لدينا الآن كلّ القطع اللازمة لتنفيذ ترقية HTTP والتفاوض على اتصال WebSocket جديد بين العميل والخادم:

GET /socket HTTP/1.1
Host: thirdparty.com
Origin: http://example.com
Connection: Upgrade
Upgrade: websocket 
Sec-WebSocket-Version: 13 
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== 
Sec-WebSocket-Protocol: appProtocol, appProtocol-v2 
Sec-WebSocket-Extensions: x-webkit-deflate-message, x-custom-extension

تمامًا كأيّ اتصال آخر يبدأه العميل في المتصفح، تخضع طلبات WebSocket لسياسة المصدر نفسه (same-origin policy): إذ يُضيف المتصفح تلقائيًّا ترويسة Origin إلى مصافحة الترقية، ويمكن للخادم البعيد أن يستخدم CORS لقبول الطلب عبر المصادر أو رفضه؛ انظر «مشاركة الموارد عبر المصادر» (Cross-Origin Resource Sharing, CORS). ولإتمام المصافحة، يجب أن يعيد الخادم استجابة «تبديل البروتوكولات» (Switching Protocols) ناجحة ويؤكّد الخيارات التي اختارها من بين ما أعلنه العميل:

HTTP/1.1 101 Switching Protocols 
Upgrade: websocket
Connection: Upgrade
Access-Control-Allow-Origin: http://example.com 
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= 
Sec-WebSocket-Protocol: appProtocol-v2 
Sec-WebSocket-Extensions: x-custom-extension

أخيرًا، بمجرّد اكتمال المصافحة السابقة، وإذا كانت المصافحة ناجحة، فيمكن الآن استخدام الاتصال كقناة اتصال ثنائية الاتجاه لتبادل رسائل WebSocket. ومن هذه النقطة فصاعدًا، لا يوجد أيّ اتصال HTTP صريح آخر بين العميل والخادم، ويتولّى بروتوكول WebSocket المهمة.

الوسطاء والأجهزة الوسيطة و WebSockets (Proxies, Intermediaries, and WebSockets)

عمليًا، ولأسباب أمنية وسياسية، يملك كثير من المستخدمين مجموعةً محدودةً من المنافذ المفتوحة—وتحديدًا المنفذ 80 (HTTP) والمنفذ 443 (HTTPS). ونتيجةً لذلك، يُنفَّذ التفاوض على WebSocket عبر تدفّق HTTP Upgrade لضمان أفضل توافق مع سياسات الشبكات والبنية التحتية القائمة. غير أنّنا، كما ذكرنا سابقًا في «الوسطاء والأجهزة الوسيطة و TLS والبروتوكولات الجديدة على الويب» (Proxies, Intermediaries, TLS, and New Protocols on the Web)، قد لا يفهم كثير من الأجهزة الوسيطة لـ HTTP القائمة بروتوكول WebSocket الجديد، ما قد يؤدّي إلى حالات فشل متعدّدة: ترقية الاتصال عشوائيًّا (blind connection upgrades)، وتخزين إطارات WebSocket في مخزن مؤقت على غير قصد، وتعديل المحتوى دون فهم البروتوكول، وتصنيف حركة WebSocket على أنها اتصالات HTTP مخترقة، وغيرها. وتُعالج مصافحة مفتاح WebSocket ومفتاح القبول (WebSocket Key and Accept) بعض هذه المشكلات: فهي سياسة أمنية ضد الخوادم والأجهزة الوسيطة التي قد «ترقّي» الاتصال عشوائيًّا دون فهم بروتوكول WebSocket فعليًّا. غير أنّ هذا الاحتياط، وإن كان يعالج بعض مشكلات النشر مع الوسطاء الصريحين (explicit proxies)، يبقى غير كافٍ مع «الوسطاء الشفافين» (transparent proxies)، الذين قد يحلّلون البيانات على السلك ويعدّلونها دون إشعار. فما الحل؟ إنشاء نفقٍ آمنٍ من طرفٍ إلى طرف (end-to-end tunnel)—أي استخدام WSS! فبالتفاوض على جلسة TLS قبل إجراء مصافحة HTTP Upgrade، ينشئ العميل والخادم نفقًا مشفّرًا، ما يحلّ جميع المخاوف السابقة. وهذا صحيحٌ بصفة خاصة مع العملاء المحمولين، إذ تمرّ حركتهم غالبًا عبر مجموعةٍ متنوعةٍ من خدمات الوساطة التي قد لا تتعامل بسلاسة مع WebSocket.

حالات استخدام WebSocket والأداء (WebSocket Use Cases and Performance)

تقدّم واجهة WebSocket API واجهةً بسيطةً للبثّ ثنائي الاتجاه القائم على الرسائل للنصوص والبيانات الثنائية بين العميل والخادم: مرِّر عنوان WebSocket URL إلى المُنشئ، واضبط بعض دوال الاستدعاء (callbacks) المكتوبة بـ JavaScript، فيصبح كل شيءٍ جاهزًا للعمل—والباقي يتولّاه المتصفح. وإذا أضفنا إلى ذلك بروتوكول WebSocket، الذي يقدّم تأطيرًا ثنائيًا وقابليةً للتوسّع والتفاوضًا على البروتوكول الفرعي، لأصبح WebSocket خيارًا مثاليًا لتسليم بروتوكولات تطبيقية مخصّصة في المتصفح. غير أنّه، كما في أيّ نقاش حول الأداء، فإنّ التعقيد التنفيذي لبروتوكول WebSocket مخفيٌّ عن التطبيق، لكنّه يحمل مع ذلك آثارًا مهمّة على الأداء تحدّد كيف ومتى ينبغي استخدام WebSocket. وWebSocket ليس بديلًا عن XHR أو SSE، ولأفضل أداء من الضروري أن نستثمر نقاط قوّة كلّ وسيلة نقل! ارجع إلى «حالات استخدام XHR والأداء» (XHR Use Cases and Performance) و«حالات استخدام SSE والأداء» (SSE Use Cases and Performance) لمراجعة الخصائص الأدائية لكلّ وسيلة نقل.

بثّ الطلبات والاستجابات (Request and Response Streaming)

WebSocket هو وسيلة النقل الوحيدة التي تسمح بالاتصال ثنائي الاتجاه فوق اتصال TCP نفسه (الشكل 17-2): إذ يستطيع العميل والخادم تبادل الرسائل متى شاءا. ونتيجةً لذلك، يوفّر WebSocket تسليمًا منخفض الزمن (low latency) لبيانات التطبيق النصية والثنائية في الاتجاهين. الشكل 17-2. تدفّق الاتصال لـ XHR و SSE و WebSocket

زمن انتشار البيانات وزمن طابور الانتظار (Propagation and Queuing Latency)

إنّ التحوّل من XHR إلى SSE أو WebSocket لا يقلّل من زمن الذهاب والإياب (roundtrip) بين العميل والخادم! فبغضّ النظر عن وسيلة النقل، يبقى زمن الانتشار (propagation latency) لحزم البيانات هو نفسه. غير أنّه إلى جانب زمن الانتشار، هناك أيضًا زمن الطابور (queuing latency): وهو الوقت الذي تنتظر فيه الرسالة في جانب العميل أو الخادم قبل أن يمكن توجيهها إلى الطرف الآخر. وفي حالة الاستطلاع عبر XHR (XHR polling)، فإنّ زمن الطابور دالّةٌ في فاصل استطلاع العميل: قد تكون الرسالة متاحةً في الخادم، لكن لا يمكن إرسالها حتى يأتي طلب XHR التالي من العميل؛ انظر «نمذجة أداء الاستطلاع عبر XHR» (Modeling Performance of XHR Polling). وعلى النقيض من ذلك، فإنّ SSE و WebSocket يستخدمان اتصالًا دائمًا (persistent)، ما يتيح للخادم أن يُرسل الرسالة (وللعميل في حالة WebSocket) في اللحظة التي تصبح فيها متاحة. ونتيجةً لذلك، فإنّ «التسليم منخفض الزمن» (low-latency delivery) في SSE و WebSocket يشير تحديدًا إلى إلغاء زمن طابور الرسائل. أمّا نحن فلم نكتشف بعد كيف نجعل حزم بيانات WebSocket تسير أسرع من سرعة الضوء!

كفاءة البيانات والضغط (Data Efficiency and Compression)

يمكن لكلّ طلب XHR أن يتفاوض على تنسيق ترميز النقل الأمثل (مثل gzip للبيانات النصية)، عبر التفاوض HTTP المعتاد. وعلى نحو مماثل، ولأنّ SSE محصورٌ في النقل بترميز UTF-8 فقط، يمكن ضغط بيانات تدفّق الأحداث بكفاءة عبر تطبيق gzip على الجلسة بأكملها. أمّا مع WebSocket، فالحالة أكثر تعقيدًا: إذ يستطيع WebSocket نقل البيانات النصية والثنائية معًا، ونتيجةً لذلك فلا معنى لضغط الجلسة بأكملها. فالحمولات الثنائية قد تكون مضغوطة أصلًا! ونتيجةً لذلك، يجب على WebSocket أن ينفّذ آلية ضغط خاصة به ويطبّقها بشكل انتقائي على كلّ رسالة. والخبر الجيّد هو أنّ مجموعة عمل HyBi Working Group تعمل على تطوير امتداد الضغط لكلّ رسالة (per-message compression) لبروتوكول WebSocket. لكنّه غير متوفّر بعدُ في أيّ من المتصفحات. ونتيجةً لذلك، ما لم يطبّق التطبيق منطق ضغطه الخاص من خلال تحسين حمولاته الثنائية بعناية (انظر «فكّ ترميز البيانات الثنائية باستخدام JavaScript») وتطبيق منطق ضغط خاص به على الرسائل النصية، فقد يتحمّل حملًا زائدًا كبيرًا بالبايتات في البيانات المنقولة! وتدعم Chrome وبعض المتصفحات المعتمدة على WebKit مراجعةً أقدم (الضغط لكلّ إطار، per-frame compression) من امتداد الضغط الخاص ببروتوكول WebSocket؛ انظر «تعدُّد إشارات WebSocket والضغط في العالم الحقيقي» (WebSocket Multiplexing and Compression in the Wild).

بروتوكولات التطبيق المخصّصة (Custom Application Protocols)

المتصفح مُحسَّنٌ لنقل بيانات HTTP: فهو يفهم البروتوكول، ويقدّم مجموعةً واسعةً من الخدمات، مثل المصادقة (authentication)، والتخزين المؤقت (caching)، والضغط (compression)، وغيرها الكثير. ونتيجةً لذلك، ترث طلبات XHR كلَّ هذه الوظائف مجانًا. وعلى النقيض من ذلك، يتيح لنا البثّ (streaming) تسليم بروتوكولات مخصّصة بين العميل والخادم، لكنّ ذلك يأتي بثمن تجاوز كثيرٍ من الخدمات التي يوفّرها المتصفح: إذ قد تتمكّن مصافحة HTTP الأولية من إجراء بعض التفاوض على معاملات الاتصال، لكنّ ما إن تستقرّ الجلسة، تصبح كلّ البيانات اللاحقة المبوَّثة بين العميل والخادم معتمة (opaque) على المتصفح. ونتيجةً لذلك، فإنّ مرونة تسليم بروتوكول مخصّص لها جوانبها السلبية أيضًا، وقد يضطرّ التطبيق إلى تنفيذ منطقه الخاص لسدّ الفجوات الناقصة: التخزين المؤقت، وإدارة الحالة، وتسليم البيانات الوصفية للرسائل، وغيرها! وتتيح مصافحة HTTP Upgrade الأولية للخادم الاستفادة من آلية ملفات تعريف الارتباط (HTTP cookies) القائمة للتحقّق من المستخدم. وإذا أخفق التحقّق، فيرفض الخادم ترقية WebSocket.

الاستفادة من ذاكرات المتصفح والأجهزة الوسيطة المؤقتة (Leveraging Browser and Intermediary Caches)

لاستخدام HTTP المعتاد مزايا جوهرية. اسأل نفسك سؤالًا بسيطًا: هل سيستفيد العميل من تخزين البيانات المستقبَلة مؤقتًا؟ أم هل يستطيع جهاز وسيط أن يحسّن تسليم الأصل (asset) لو استطاع تخزينه مؤقتًا؟ فمثلًا، يدعم WebSocket النقل الثنائي، ما يتيح للتطبيق بثّ تنسيقات صور اعتباطية (arbitrary image formats) دون أيّ حمل زائد—وهو مكسبٌ جيّد! غير أنّ كون الصورة تُسلَّم ضمن بروتوكول مخصّص يعني أنّها لن يُخزَّن مؤقتًا في ذاكرة المتصفح المؤقتة (browser cache)، ولا في أيّ جهاز وسيط (مثل CDN). ونتيجةً لذلك، قد تتحمّل عمليات نقل غير ضرورية إلى العميل وحركةٍ أعلى بكثير إلى خوادم الأصل (origin servers). وينطبق المنطق نفسه على جميع تنسيقات البيانات الأخرى: الفيديو، والنصوص، وغيرها. ونتيجةً لذلك، تأكّد من اختيار وسيلة النقل المناسبة للمهمة! وإحدى الاستراتيجيات البسيطة والفعّالة لمعالجة هذه المخاوف هي استخدام جلسة WebSocket لتسليم البيانات غير القابلة للتخزين المؤقت، مثل التحديثات الفورية ورسائل «التحكّم» (control) الخاصة بالتطبيق، وهي رسائل تستطيع تشغيل طلبات XHR لجلب أصولٍ أخرى عبر بروتوكول HTTP.

نشر البنية التحتية لـ WebSocket (Deploying WebSocket Infrastructure)

HTTP مُحسَّنٌ للنقل القصير والمتقطّع (bursty). ونتيجةً لذلك، كثيرًا ما تُضبط الخوادم والوسطاء والأجهزة الوسيطة الأخرى مهلةً (timeout) عدوائيًّا لاتصالات HTTP الخاملة (idle)، وهو ما لا نرغب فيه إطلاقًا في جلسات WebSocket طويلة الأمد. ولمعالجة ذلك، هناك ثلاثة أمور يجب مراعاتها:

لا يتحكّم أحد في سياسة شبكة العميل. وفي الواقع، قد تحجب بعض الشبكات حركة WebSocket بالكامل، ولهذا قد تحتاج إلى استراتيجية احتياطية (fallback). وعلى نحو مماثل، لا يتحكّم أحد في الوسطاء على الشبكة الخارجية. لكنّ هنا يمكن لـ TLS أن يساعد! فبتنفيذه (tunneling) فوق اتصالٍ آمنٍ من طرفٍ إلى طرف، تستطيع حركة WebSocket أن تتجاوز جميع الوسطاء المتوسّطين. واستخدام TLS لا يمنع الجهاز الوسيط من فرض مهلة على اتصال TCP خامل. لكنّه عمليًا يزيد بدرجة كبيرة معدّل نجاح التفاوض على جلسة WebSocket، ويساعد غالبًا كذلك على تمديد فترات مهلة الاتصال. وأخيرًا، هناك البنية التحتية التي ننشرها ونديرها بأنفسنا، وهي أيضًا تحتاج في كثير من الأحيان إلى عنايةٍ وضبط. فمع أنّه سهل أن نلوم العميل أو الشبكات الخارجية، فإنّ المشكلة غالبًا ما تكون قريبةً من البيت. ويجب ضبط كلّ موازن حمل (load-balancer) وموجّه (router) ووسيط وخادم ويب في مسار الخدمة للسماح بالاتصالات طويلة الأمد. فمثلًا، يستطيع Nginx 1.3.13+ أن يوسّط حركة WebSocket، لكنّه يعتمد افتراضيًا على مهلات عدوئية مقدَّمة بـ 60 ثانية! ولزيادة الحدّ، علينا أن نعرّف المهلات الأطول صراحةً:

location /websocket {
 proxy_pass http://backend;
 proxy_http_version 1.1;
 proxy_set_header Upgrade $http_upgrade;
 proxy_set_header Connection "upgrade";
 proxy_read_timeout 3600; 
 proxy_send_timeout 3600; 
}

على نحو مماثل، ليس من غير المألوف وجود موازن حمل، مثل HAProxy، أمام خادم Nginx واحد أو أكثر. ومن المتوقّع تمامًا أن نطبّق هنا أيضًا إعدادات صريحة مماثلة—مثلًا بالنسبة إلى HAProxy:

defaults http
 timeout connect 30s
 timeout client 30s
 timeout server 30s
 timeout tunnel 1h

العُقدة (gotcha) في المثال السابق هي مهلة «tunnel» الإضافية. في HAProxy، لا تُطبَّق المهلات connect و client و server إلا على مصافحة HTTP Upgrade الأولية، لكنّ بمجرّد اكتمال الترقية تتحكّم في المهلة القيمة tunnel. وليس Nginx و HAProxy سوى اثنين من مئات الخوادم والوسطاء وموازنات الحمل المختلفة التي تعمل في مراكز بياناتنا. ولا يمكننا حصر كلّ خيارات الضبط في هذه الصفحات. والأمثلة السابقة ليست سوى صورة توضيحية على أنّ معظم البنية التحتية تتطلب ضبطًا مخصّصًا للتعامل مع الجلسات طويلة الأمد. وبالتبعية، قبل تنفيذ إبقاءات الاتصال على مستوى التطبيق (application keepalives)، تأكّد من البنية التحتية أولًا. فالجلسات طويلة الأمد والخاملة تحتلّ ذاكرةً وموارد مقابس (socket resources) على جميع الخوادم الوسيطة. ولذلك فإنّ المهلات القصيرة غالبًا ما تكون مبرَّرةً كاحتياط أمني ومواردي وتشغيلي. ونشر WebSocket و SSE و HTTP/2، وكلٌّ منها يعتمد على جلسات طويلة الأمد، يجلب معه فئةً خاصةً به من التحديات التشغيلية الجديدة.
