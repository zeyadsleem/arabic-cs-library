مقدمة (Introduction)

تمكّن الأحداث المرسلة من الخادم (Server-Sent Events، SSE) من بثّ بيانات أحداث نصية من الخادم إلى العميل بشكل فعّال — على سبيل المثال، إشعارات أو تحديثات في الوقت الفعلي تُولَّد على الخادم. لتحقيق هذا الهدف، تقدّم SSE مكوّنين: واجهة EventSource جديدة في المتصفح، التي تسمح للعميل باستقبال إشعارات الدفع (push notifications) من الخادم وتحويلها إلى أحداث DOM (DOM events)، وتنسيق "تدفق الأحداث" (event stream)، المستخدم لتسليم التحديثات الفردية. إنّ الجمع بين واجهة EventSource API في المتصفح وتنسيق تدفق الأحداث المحدد جيدًا هو ما يجعل SSE أداة فعّالة ولا غنى عنها للتعامل مع البيانات في الوقت الفعلي في المتصفح:

في الخلفية، تقدّم SSE تطبيقًا فعّالًا ومتعدّد المتصفحات لتدفق XHR (XHR streaming)؛ يتم تسليم الرسائل فعليًا عبر اتصال HTTP واحد طويل الأمد. لكن، على عكس التعامل مع تدفق XHR بأنفسنا، يدير المتصفح جميع عمليات إدارة الاتصال وتحليل الرسائل، مما يسمح لتطبيقاتنا بالتركيز على منطق العمل! باختصار، تجعل SSE التعامل مع البيانات في الوقت الفعلي بسيطًا وفعّالًا. لنلقِ نظرة تحت الغطاء.

واجهة EventSource API

تجريد واجهة EventSource لجميع تفاصيل إنشاء الاتصال وتحليل الرسائل على المستوى المنخفض خلف واجهة برمجة تطبيقات متصفح بسيطة. للبدء، نحتاج ببساطة إلى تحديد عنوان URL لمورد تدفق أحداث SSE وتسجيل مستمعي أحداث JavaScript المناسبين على الكائن:

var source = new EventSource("/path/to/stream-url"); 

source.onopen = function () { ... }; 
source.onerror = function () { ... }; 

source.addEventListener("foo", function (event) { 
 processFoo(event.data);
});

source.onmessage = function (event) { 
 log_message(event.id, event.data);

 if (event.id == "CLOSE") {
 source.close(); 
 }
}

يمكن لـ EventSource بثّ بيانات الأحداث من أصول بعيدة (cross-origin) بالاستفادة من نفس صلاحيات CORS وتدفق الاشتراك (opt-in) كما في طلب XHR عادي. هذا كل ما في الأمر بالنسبة لواجهة برمجة تطبيقات العميل. يُعالَج منطق التنفيذ (implementation logic) نيابةً عنا: يُفاوض الاتصال نيابةً عنا، وتُحلَّل البيانات المستلمة تدريجيًا، وتُحدَّد حدود الرسائل، وأخيرًا يُطلَق حدث DOM من قِبل المتصفح. تسمح واجهة EventSource للتطبيق بالتركيز على منطق العمل: فتح اتصال جديد، ومعالجة إشعارات الأحداث المستلمة، وإنهاء التدفق عند الانتهاء. تقدّم SSE تطبيقًا موفرًا للذاكرة لتدفق XHR. على عكس اتصال XHR خام، الذي يخزن الاستجابة المستلمة بالكامل حتى إسقاط الاتصال، يمكن لاتصال SSE تجاهل الرسائل المُعالَجة دون تجميعها في الذاكرة. كميزة إضافية، تقدّم واجهة EventSource أيضًا إعادة الاتصال التلقائي (auto-reconnect) وتتبع آخر رسالة تمت رؤيتها: إذا أُسقط الاتصال، سيعيد EventSource الاتصال بالخادم تلقائيًا، واختياريًا يُعلن عن معرّف (ID) آخر رسالة تمت رؤيتها، بحيث يمكن استئناف التدفق وإعادة إرسال الرسائل المفقودة. كيف يعرف المتصفح معرّف (ID) ونوع (type) وحد (boundary) كل رسالة؟ هنا يدخل بروتوكول تدفق الأحداث (event stream protocol) حيز التنفيذ. إنّ الجمع بين واجهة برمجة تطبيقات عميل بسيطة وتنسيق بيانات محدد جيدًا هو ما يسمح لنا بتفويض الجزء الأكبر من العمل إلى المتصفح. يذهبان جنبًا إلى جنب، على الرغم من أن بروتوكول البيانات على المستوى المنخفض (low-level data protocol) شفاف تمامًا للتطبيق في المتصفح.

محاكاة EventSource عبر JavaScript مخصص

كانت SSE إضافة مبكرة إلى مواصفة HTML5 وهي مدعومة أصلًا في معظم المتصفحات الحديثة. الاستثناءان البارزان، اعتبارًا من أوائل 2013، هما Internet Explorer ومتصفح Android المدمج (stock Android browser). للحالة الأحدث، راجع caniuse.com/eventsource. لكن الخبر السار هو أن واجهة EventSource بسيطة بما يكفي لمحاكاتها عبر مكتبة JavaScript اختيارية (أي "polyfill") للمتصفحات التي لا تدعمها أصلًا. وبالمثل، يمكن تنفيذ تسليم تدفق الأحداث (event stream) فوق آليات XHR (XMLHttpRequest) الموجودة:

if (!window.EventSource) {
 // load JavaScript polyfill library
}

var source = new EventSource("/event-stream-endpoint");
...

الفائدة من استخدام مكتبة polyfill هي أنها تسمح لتطبيقاتنا، مرة أخرى، بالتركيز على منطق التطبيق، بدلًا من القلق بشأن quirks المتصفح وحالة التنفيذ. بعد قول ذلك، بينما توفر مكتبة polyfill واجهة برمجة تطبيقات متسقة، كن على علم بأن نقل XHR (XHR transport) الأساسي لن يكون فعّالًا بقدر:

بدون دعم أصلي لتدفق XHR فعّال لبيانات تدفق الأحداث، يمكن لمكتبة polyfill التراجع (fallback) إلى polling، أو long-polling، أو تدفق XHR، ولكل منها تكاليف أداء خاصة به. لمناقشة كاملة، راجع Real-Time Notifications and Delivery. باختصار، تحقّق من تنفيذ مكتبة polyfill الخاصة بك للتأكد من أنها تلبي أهداف الأداء الخاصة بك! تستخدم العديد من المكتبات الأكثر شيوعًا (مثل jQuery.EventSource) polling عبر XHR لمحاكاة نقل SSE — بسيط، ولكن أيضًا نقل غير فعّال.

بروتوكول تدفق الأحداث (Event Stream Protocol)

يُسلَّم تدفق أحداث SSE كاستجابة HTTP متدفقة: يبدأ العميل طلب HTTP عادي، ويستجيب الخادم بنوع محتوى مخصص "text/event-stream"، ثم يبثّ بيانات الأحداث المشفّرة بـ UTF-8. لكن، حتى هذا يبدو معقدًا جدًا، لذا مثال في محله:

=> Request
GET /stream HTTP/1.1 
Host: example.com
Accept: text/event-stream

<= Response
HTTP/1.1 200 OK 
Connection: keep-alive
Content-Type: text/event-stream
Transfer-Encoding: chunked

retry: 15000 

data: First message is a simple string. 

data: {"message": "JSON payload"} 

event: foo 
data: Message of type "foo"

id: 42 
event: bar
data: Multi-line message of
data: type "bar" and id "42"

id: 43 
data: Last message, id "43"

بروتوكول تدفق الأحداث سهل الفهم والتنفيذ:

في الطرف المستقبل، تحلّل واجهة EventSource التدفق الوارد بالبحث عن فواصل الأسطر (newline separators)، وتستخرج الحمولة (payload) من حقول data، وتتحقق من وجود ID وtype اختياريين، وأخيرًا تطلق حدث DOM (DOM event) لإخطار التطبيق. إذا كان هناك type، فسيُطلَق حدث DOM مخصص، وخلاف ذلك يُستدعى callback العام "onmessage"؛ راجع واجهة EventSource API في كلا الحالتين.

ترميز UTF-8 ونقل البيانات الثنائية مع SSE (UTF-8 Encoding and Binary Transfers with SSE)

لا تُجري EventSource أي معالجة إضافية على الحمولة (payload) الفعلية: تُستخرج الرسالة من حقل data واحد أو أكثر، وتُدمج معًا، وتُمرَّر مباشرة إلى التطبيق. وبناءً على ذلك، يمكن للخادم دفع أي تنسيق نصي (مثل سلسلة بسيطة، أو حمولة JSON، وما إلى ذلك)، ويجب على التطبيق فك ترميزها بنفسه. مع ذلك، لاحظ أن جميع بيانات event source مشفّرة بـ UTF-8: SSE ليست آلية لنقل الحمولات (payloads) الثنائية! إذا لزم الأمر، يمكن ترميز كائن ثنائي تعسّفي بـ base64 ليكون متوافقًا مع SSE، لكن هذا يتكبّد overhead عالٍ (33%) على مستوى البايتات؛ راجع Resource Inlining. هل تقلق من التكلفة العالية لـ UTF-8 على السلك (wire)؟ اتصال SSE هو استجابة HTTP متدفقة، مما يعني أنه يمكن ضغطه (أي gzip)، تمامًا كما أي استجابة HTTP أخرى أثناء النقل! بينما SSE ليست مخصّصة لتسليم البيانات الثنائية، إلا أنها مع ذلك نقل فعّال: تأكّد من أن خادمك يُطبّق ضغط gzip على تدفق SSE. عدم دعم بثّ البيانات (streaming) الثنائية ليس إغفالًا. صُمِّمت SSE خصيصًا كنقل بسيط وفعّال من الخادم إلى العميل للبيانات النصية. إذا كنت بحاجة إلى نقل الحمولات (payloads) الثنائية، فإن WebSocket هي الأداة المناسبة. أخيرًا، بالإضافة إلى التحليل التلقائي للأحداث، تقدّم SSE دعمًا مدمجًا لإعادة إنشاء الاتصالات المُسقطة، وكذلك استرداد الرسائل التي قد يكون العميل فاتته أثناء قطع الاتصال. بشكل افتراضي، إذا أُسقط الاتصال، فسيعيد المتصفح إنشاء الاتصال تلقائيًا. توصي مواصفة SSE بتأخير 2–3 ثوانٍ، وهو الافتراضي الشائع لمعظم المتصفحات، لكن الخادم يمكنه أيضًا تعيين فاصل زمني مخصص في أي نقطة بإرسال أمر retry إلى العميل. وبالمثل، يمكن للخادم أيضًا ربط سلسلة ID تعسّفية بكل رسالة. يتذكّر المتصفح تلقائيًا آخر ID تمت رؤيته وسيُضيف تلقائيًا ترويسة HTTP "Last-Event-ID" بالقيمة المُذكَّرة عند إصدار طلب إعادة الاتصال. إليك مثال:

(existing SSE connection)
retry: 4500 

id: 43 
data: Lorem ipsum

(connection dropped)
(4500 ms later)

=> Request
GET /stream HTTP/1.1 
Host: example.com
Accept: text/event-stream
Last-Event-ID: 43

<= Response
HTTP/1.1 200 OK 
Content-Type: text/event-stream
Connection: keep-alive
Transfer-Encoding: chunked

id: 44 
data: dolor sit amet

لا يحتاج تطبيق العميل إلى تقديم أي منطق إضافي لإعادة إنشاء الاتصال أو تذكّر آخر معرّف حدث (event ID) تمت رؤيته. تدير المتصفح سير العمل بأكمله، ونتّكل على الخادم للتعامل مع الاسترداد. وعلى وجه التحديد، اعتمادًا على متطلبات التطبيق وتدفق البيانات، يمكن للخادم تنفيذ عدة استراتيجيات مختلفة:

تفاصيل التنفيذ الدقيقة لمدى الرجوع في حفظ الرسائل تخص، بالطبع، متطلبات التطبيق. علاوة على ذلك، لاحظ أن ID هو حقل اختياري في تدفق الأحداث. لذا يمكن للخادم أيضًا اختيار نقاط تفتيش (checkpoint) لرسائل أو معالم محددة في تدفق الأحداث المُسلَّم. باختصار، قيّم متطلباتك، ونفّذ المنطق المناسب على الخادم.

حالات استخدام SSE والأداء (SSE Use Cases and Performance)

SSE نقل عالي الأداء لبثّ البيانات في الوقت الفعلي من الخادم إلى العميل: يمكن دفع الرسائل في اللحظة التي تصبح فيها متاحة على الخادم (زمن استجابة منخفض)، وهناك overhead أدنى للرسائل (اتصال طويل الأمد، وبروتوكول تدفق الأحداث، وضغط gzip)، ويتعامل المتصفح مع كل تحليل الرسائل، ولا توجد buffers غير محدودة. أضف إلى ذلك واجهة EventSource API مريحة مع إعادة الاتصال التلقائي (auto-reconnect) وإشعارات الرسائل كأحداث DOM (DOM events)، لتصبح SSE أداة لا غنى عنها للتعامل مع البيانات في الوقت الفعلي (real-time data)! وهناك قيدان رئيسيان لـ SSE. أولًا، SSE من الخادم إلى العميل فقط، ومن ثمّ لا تغطي حالة استخدام بثّ الطلبات (request streaming)—مثل بثّ عملية رفع كبيرة إلى الخادم. ثانيًا، بروتوكول تدفق الأحداث (event stream protocol) مصمَّم خصيصًا لنقل بيانات UTF-8: بثّ البيانات الثنائية (binary streaming)، رغم إمكانية، غير فعّال. ومع ذلك، يمكن حلّ قيد UTF-8 غالبًا على طبقة التطبيق (application layer): تُسلِم SSE إشعارًا للتطبيق بوجود أصل ثنائي (binary asset) جديد متاح على الخادم، ويُصدر التطبيق طلب XHR لجلبه. ورغم أن هذا يتكبّد رحلة ذهاب وإياب (roundtrip) إضافية من زمن الاستجابة، فإنّه يتمتّع أيضًا بفائدة الاستفادة من الخدمات العديدة التي يوفّرها XHR: التخزين المؤقت للاستجابات (response caching)، وترميز النقل (transfer-encoding، أي الضغط)، وما إلى ذلك. وإذا تم بثّ أصل (asset)، فلا يمكن تخزينه في ذاكرة المتصفح المؤقتة (browser cache). إن الدفع في الوقت الفعلي (real-time push)، تمامًا كما الاستطلاع (polling)، يمكن أن يترك تأثيرًا سلبيًا كبيرًا على عمر البطارية. أولًا، فكّر في تجميع الرسائل (batching) لتجنّب إيقاظ وحدة الراديو. ثانيًا، تخلَّص من رسائل إبقاء الاتصال (keepalives) غير الضرورية؛ ف اتصال SSE لا "يُسقَط" (dropped) ما دام الراديو خاملًا. لمزيد من التفاصيل، راجع Eliminate Periodic and Inefficient Data Transfers.

بثّ SSE فوق TLS

تقدّم SSE وسيلة نقل بسيطة ومريحة في الوقت الفعلي فوق اتصال HTTP عادي، ما يجعل نشرها على الخادم ومحاكاتها على العميل (polyfill) أمرًا بسيطًا. لكن، قد تظل الوسائط البرمجية للشبكة القائمة (network middleware)، مثل خوادم الوكيل (proxy servers) وجدران الحماية (firewalls)، التي لا تعرف SSE (SSE aware)، مصدرًا للمشكلات: فقد تختار الوسائط البينية تخزين بيانات تدفق الأحداث (event stream) مؤقتًا (buffering)، ما يترجم إلى زيادة في زمن الاستجابة أو إلى اتصال SSE معطوب تمامًا. ونتيجةً لذلك، إذا واجهت هذه المشكلة أو مشكلات مشابهة، فقد ترغب التفكير في تسليم تدفق أحداث SSE فوق اتصال TLS؛ راجع Proxies, Intermediaries, TLS, and New Protocols on the Web.
