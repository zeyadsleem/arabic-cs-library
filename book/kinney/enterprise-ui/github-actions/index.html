GitHub Actions: أتمتة المستودعات وخطوط CI/CD

GitHub Actions هو نظام الأتمتة المدمج في GitHub للتكامل المستمر (CI)، والتسليم المستمر (CD)، وخطوط الإصدار، وتدبير شؤون المستودع، وسير عمل الأمان، وبقية الأعمال الشاقّة التي يظل البشر يحاولون إنجازها يدويًا. وسير العمل ملف YAML مخزّن في .github/workflows، ويعمل عند حدوث حدث مطابق في المستودع، أو وفق جدول زمني، أو حين يطلقه أحدهم يدويًا. ويمكن أن يكون للمستودع سير عمل كثيرة، كل منها موجّه إلى مهمة مختلفة.

والجزء الذي يربك الناس أن GitHub Actions ليس شيئًا واحدًا. فهو محرّك سير عمل، ومنصّة تنفيذ، وصيغة تغليف لإجراءات قابلة لإعادة الاستخدام، وأسطول مشغّلات، وسطح أمني، ونظام سياسات. ويبدو كـ«بعض YAML وسطرَي uses:» حتى تصير لديك تفرّعات، وعمليات نشر، ومشغّلات مستضافة ذاتيًا، وبيانات اعتماد سحابية، وصحّة ذاكرة مؤقتة، وزميل يرى في pull_request_target طريقة ممتعة للتعرّف على الاستجابة للحوادث.

النموذج الذهني

والنموذج الأساسي مباشر. سير العمل يحتوي مهمة واحدة أو أكثر. وتعمل المهام على مشغّلات، وكل مهمة تحتوي خطوات. والخطوة إما أمر صدفة بـrun: وإما إجراء يُستدعى بـuses:. ويمكن أن تعمل المهام على التوازي أو تُفرض في تسلسل بـneeds. وتعمل كل مهمة على آلة مشغّل خاصة بها أو في سياق حاوية خاص بها، ولهذا يكون تمرير الحالة بين المهام صريحًا لا سحريًا.

والإجراء لبنة بناء قابلة لإعادة الاستخدام. ويمكنك استخدام إجراءات من المستودع نفسه، أو من مستودعات عامة، أو من صور Docker Hub. ويدعم GitHub أيضًا كتابة إجراءاتك الخاصة بلغة JavaScript أو Docker أو الإجراءات المركّبة، ويوصف كل منها بملف بيانات وصفية action.yml أو action.yaml. والإجراءات المركّبة تجمع خطوات؛ وسير العمل القابل لإعادة الاستخدام يجمع مهام كاملة وبنية سير العمل. وهاتان فكرتان متقاربتان، لكنهما ليستا الشيء نفسه، إذ يبدو أن تجريدًا واحدًا قابلًا لإعادة الاستخدام كان سيكون أكثر رحمة بالبشر.

تشريح سير العمل

في المستوى الأعلى، المفاتيح التي ستعنيك أكثر هي name وrun-name وon وpermissions وenv وdefaults وconcurrency وjobs. ويُعرّف مرجع صيغة سير العمل أيضًا ميزات على مستوى المهمة مثل if وstrategy وcontainer وservices وoutputs وuses وwith وsecrets، وهي حيث يجري معظم العمل الحقيقي.

وهذا سير عمل أساسي جيد:

name: CI

on:
  push:
    branches: [main]
    paths:
      - 'src/**'
      - 'package.json'
      - 'package-lock.json'
      - '.github/workflows/ci.yml'
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:
  NODE_ENV: test

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: true
      matrix:
        node: [20, 22]

    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}

      - uses: actions/cache@v4
        with:
          path: ~/.npm
          key: npm-${{ runner.os }}-${{ matrix.node }}-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            npm-${{ runner.os }}-${{ matrix.node }}-
            npm-${{ runner.os }}-

      - run: npm ci
      - run: npm test

      - name: Save coverage
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-node-${{ matrix.node }}
          path: coverage/
          retention-days: 7

يستخدم هذا المثال الميزات التي تهمّ في المستودعات الحقيقية—مرشّحات الأحداث، وصلاحيات الرمز بأقل امتياز، والتحكم في التزامن، ومصفوفة، وتخزين الاعتمادات مؤقتًا، ومخرجات. ولا شيء من ذلك غريب. إنها الفرق بين سير عمل لعبة وآخر لا يهدر المال ولا ينصب فخاخًا أمنية لنسختك المستقبلية.

المُحفّزات ودلالات الأحداث

كتلة on: هي التي تحدّد متى يبدأ سير العمل. ويستطيع GitHub Actions أن يُحفَّز بـنشاط المستودع، أو الجداول الزمنية، أو الإطلاق اليدوي، أو استدعاءات سير العمل، أو اكتمالات سير العمل، أو الأحداث الخارجية. والحالات الشائعة هي push وpull_request وworkflow_dispatch وschedule وworkflow_call وworkflow_run. ولأحداث المستودع، يمكنك تضييق التنفيذ بأنواع النشاط types، ومرشّحات الفروع، ومرشّحات الوسوم، ومرشّحات المسارات. ويمكن بدء سير العمل اليدوي المُحفَّز بـworkflow_dispatch من تبويب Actions، أو من GitHub CLI، أو من واجهة REST.

ومرشّحات المسارات جديرة بالاستخدام بقوة، خصوصًا في المستودعات الأحادية. فإذا طابق مسار متغيّر واحد على الأقل قاعدة paths، عمل سير العمل. وهذه أرخص طريقة لمنع تعديل في التوثيق من إعادة بناء كامل حزمة تطبيقاتك، وهو نوع الاستعراض غير الضروري الذي تسمّيه الفرق «CI القياسي».

وفي عائلة pull_request مزالق يتعلّمها الناس متأخرين. فسير عمل pull_request لن يعمل إذا كان في طلب السحب تعارضات دمج، بينما يعمل pull_request_target. وفي pull_request، يكون GITHUB_SHA آخر إيداع دمج في فرع دمج طلب السحب، وليس بالضرورة أحدث إيداع في فرع رأس المساهم. وإن احتجت بصمة الرأس الفعلية للمساهم، فاستخدم github.event.pull_request.head.sha.

وpull_request_target وworkflow_run مُحفّزان ذوا امتيازات ويحتاجان حذرًا حقيقيًا. وتحذّر توثيقات الأمان في GitHub من أن استخدامهما مع سحب شيفرة غير موثوقة قد يؤدي إلى تسميم الذاكرة المؤقتة ووصول غير مقصود إلى امتيازات الكتابة أو الأسرار. والافتراضي الآمن بسيط—لا تسحب شيفرة طلبات سحب غير موثوقة تحت مُحفّز ذي امتيازات إلا إذا كنت متأكدًا تمامًا أنك تعرف ما تفعل، وأكثر الناس لا يعرفون.

المهام والخطوات وتدفّق البيانات

المهام هي حيث تحدث التنسيقية. وافتراضيًا، يمكن للمهام المستقلة أن تعمل على التوازي. أضف needs لفرض التسلسل، واستخدم if: لبوابة التنفيذ، واستخدم مخرجات المهام حين يجب أن تعبر البيانات حدود المهام. وداخل المهمة، تُنفَّذ الخطوات بالترتيب، ويمكن أن تكون كل خطوة أمرًا أو إجراءً.

وتمرير البيانات داخل المهمة وبين المهام يستخدم أدوات مختلفة. فداخل المهمة، اكتب متغيّرات البيئة في GITHUB_ENV لتقرأها الخطوات اللاحقة. ولإظهار مخرَج خطوة، اكتب في GITHUB_OUTPUT، ثم اربط مخرجات الخطوات بمخرجات المهمة عبر jobs.<job_id>.outputs، وأخيرًا استهلك تلك القيم في المهام اللاحقة عبر سياق needs.

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image_tag: ${{ steps.meta.outputs.tag }}
    steps:
      - id: meta
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - run: echo "Deploying ${{ needs.build.outputs.image_tag }}"

ونمط تمرير مخرجات الخطوة إلى مخرجات المهمة هو الطريقة المعتادة لنقل بيانات منظّمة عبر سير العمل. وهو أنظف بكثير من كتابة ملفات مؤقتة في كل مكان والأمل أن تراها المهمة التالية، وهو ما لن يحدث لأن المهام معزولة.

السياقات والتعبيرات والمتغيّرات

السياقات هي كائنات وقت التشغيل في GitHub Actions. وأهمها github وenv وvars وjob وsteps وrunner وmatrix وneeds وinputs وsecrets. ويحتوي سياق github على بيانات وصفية لتشغيل سير العمل، بينما يعرض vars متغيّرات التهيئة المعرّفة على مستوى المؤسسة أو المستودع أو البيئة.

كما يضبط GitHub مجموعة كبيرة من متغيّرات البيئة الافتراضية في كل تشغيل. وهذه المتغيّرات متاحة للخطوات، لكنها غير معرّفة عبر خريطة env في سير العمل، ولهذا تصل عمومًا إلى قيمها وقت سير العمل عبر سياقات مثل ${{ github.ref }} لا عبر ${{ env.GITHUB_REF }}. وتشير توثيقات GitHub أيضًا إلى أنك لا تستطيع الكتابة فوق المتغيّرات الافتراضية GITHUB_* أو RUNNER_*.

ومن السهل الخطأ في أسبقية المتغيّرات. ففي env العادي، يفوز النطاق الأكثر تحديدًا—فالخطوة تتجاوز المهمة، والمهمة تتجاوز سير العمل. وفي متغيّرات التهيئة ضمن vars، يفوز المستوى الأدنى—فالبيئة تتجاوز المستودع، والمستودع يتجاوز المؤسسة. وثمة فارق خبيث واحد: لا تصبح متغيّرات التهيئة على مستوى البيئة متاحة إلا بعد أن تبدأ المهمة التنفيذ، فلا تكتب فوق قيم حُسمت بالفعل في سياقَي env وvars أثناء معالجة سير العمل.

أما التعبيرات فهي النصف الآخر من النموذج. وfromJSON() مفيد لتحويل السلاسل النصية إلى قيم منطقية أو أعداد صحيحة أو مصفوفات أو كائنات مصفوفة كاملة. وtoJSON() جيد لتنقيح السياقات. وhashFiles() هو ما تستخدمه لمفاتيح ذاكرة مؤقتة مستقرة مبنية على ملفات القفل أو بيانات الاعتماد الوصفية.

jobs:
  define-matrix:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set.outputs.matrix }}
    steps:
      - id: set
        run: echo 'matrix={"include":[{"node":20},{"node":22}]}' >> "$GITHUB_OUTPUT"

  test:
    needs: define-matrix
    runs-on: ubuntu-latest
    strategy:
      matrix: ${{ fromJSON(needs.define-matrix.outputs.matrix) }}
    steps:
      - run: echo "Node version is ${{ matrix.node }}"

وحيلة المصفوفة الديناميكية تلك من الأنماط المتقدّمة القليلة التي تستحقّ المعرفة فعلًا. فهي تتيح لمهمة أن تكتشف العمل ولأخرى أن تتفرّع عليه، وهو مفيد في المستودعات الأحادية، وقوائم الأهداف المولَّدة، وخطوط النشر متعددة البيئات.

المشغّلات

المشغّل هو الآلة التي تنفّذ مهمة. والمشغّلات المستضافة من GitHub هي الآلات الافتراضية المُدارة. والمشغّلات الأكبر مشغّلات مستضافة من GitHub بمعالج وذاكرة وقرص أكبر. والمشغّلات المستضافة ذاتيًا هي آلاتك أنت. وActions Runner Controller، أو ARC، هو مشغّل Kubernetes لتنسيق المشغّلات المستضافة ذاتيًا وتوسيعها تلقائيًا كمجموعات مشغّلات.

واستهداف المشغّلات يجري عبر runs-on. وللبنية التحتية المستضافة ذاتيًا، توصي GitHub باستخدام مصفوفة من الوسوم تبدأ بـself-hosted، ثم وسوم أكثر تحديدًا مثل linux أو ARM64. ولن تعمل المهمة إلا على مشغّل يطابق كل الوسوم المحدّدة. ويمكنك أيضًا استهداف مجموعات مشغّلات. ومن العقبات التي تذكرها التوثيقات صراحةً أن Actions Runner Controller لا يدعم وسومًا متعددة ولا يدعم وسم self-hosted بالطريقة نفسها التي تدعمه بها المشغّلات المستضافة ذاتيًا على مستوى المستودع أو المؤسسة.

تشتري المشغّلات المستضافة ذاتيًا التحكّم، لكنها تشتري المخاطرة أيضًا. فلـإجراءات حاويات Docker أو حاويات الخدمة على المشغّلات المستضافة ذاتيًا، تحتاج إلى Linux وDocker مثبّتين. وتحذّر توثيقات سياسات المؤسسات في GitHub أيضًا من أن المشغّلات المستضافة ذاتيًا ليست مضمونة كآلات نظيفة قصيرة العمر، وأن طلبات السحب غير الموثوقة قد تخترقها إن عرضتها للإصابة بإهمال. ولهذا فالنمط العاقل هو مشغّلات قصيرة العمر للأحمال الحساسة أو نصف غير الموثوقة، لا آلة واحدة خالدة يتقاسم الكتابة عليها كل فرع في الشركة.

المهام في الحاويات وحاويات الخدمة

يمكن أن تعمل المهمة مباشرةً على مضيف المشغّل، أو يمكنك تغليفها في حاوية مهمة بـjobs.<job_id>.container. وحين تفعل ذلك، تُنفَّذ خطوات run: العادية داخل تلك الحاوية، بينما تعمل إجراءات الحاويات كحاويات شقيقة على الشبكة نفسها بتركيبات الوسائط نفسها. ومن الحالات الطرفية التي يفوّتها كثيرون أن الصدفة الافتراضية داخل حاوية المهمة هي sh لا bash، إلا إن تجاوزتها.

وحاويات الخدمة هي الحل المدمج للاعتمادات مثل PostgreSQL أو Redis أثناء الاختبارات. وحين تعمل المهمة نفسها في حاوية، يضع GitHub حاوية المهمة وحاويات الخدمة على شبكة جسر يعرّفها المستخدم، ويمكنك الوصول إلى خدمة بالوسم الذي أعطيته لها، فيصبح اسم مضيفها. أما حين تعمل المهمة مباشرةً على مضيف المشغّل، فتحتاج عمومًا إلى نشر منافذ من حاوية الخدمة إلى المضيف.

jobs:
  integration:
    runs-on: ubuntu-latest
    container:
      image: node:20-bookworm

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres

    steps:
      - uses: actions/checkout@v5
      - run: npm ci
      - run: npm test
        env:
          DATABASE_URL: postgres://postgres:postgres@postgres:5432/postgres

وهذا الإعداد مرتّب لأن الشبكة أبسط حين تعيش المهمة والخدمات كلها في حاويات. كما يميل إلى أن يكون أكثر قابلية للتكرار من التظاهر بأن الحالة المحيطة بمضيف المشغّل جزء من عقد الاختبار.

إعادة استخدام المنطق

آلية إعادة الاستخدام النطاق تُستدعى بـ سياق المشغّل الوصول إلى الأسرار الأفضل لـ
إجراء (JS/Docker) خطوة واحدة uses: في steps مشغّل المستدعي عبر مدخلات with: عمليات قابلة لإعادة الاستخدام بخطوة واحدة
إجراء مركّب حزمة خطوات uses: في steps مشغّل المستدعي عبر مدخلات with: وصفات متعددة الخطوات كخطوة واحدة
سير عمل قابل لإعادة الاستخدام مهام كاملة uses: على مستوى المهمة مشغّل خاص بكل مهمة secrets: أو secrets: inherit أنماط مهام كاملة (بناء + نشر)

يمكنك إعادة استخدام المنطق على ثلاثة مستويات. استخدم إجراءً حين تريد خطوة قابلة لإعادة الاستخدام. واستخدم إجراءً مركّبًا حين تريد حزمة خطوات تظل تتصرف كخطوة واحدة. واستخدم سير عمل قابلًا لإعادة الاستخدام حين تريد إعادة استخدام مهام كاملة أو صلاحيات أو بيئات أو مصفوفات أو بنية نشر. ولهذا السبب بالتحديد تضع توثيقات GitHub نفسها الإجراءات المركّبة وسير العمل القابل لإعادة الاستخدام جنبًا إلى جنب.

ويمكن أن تعيش الإجراءات نفسها في المستودع ذاته، أو في مستودع عام، أو في صورة Docker Hub. ولا يدعم GitHub إعادة التوجيه للإجراءات أو سير العمل القابل لإعادة الاستخدام، فإن أُعيدت تسمية إجراء أو سير عمل أو نُقل، فشلت المراجع القديمة. وتستخدم الإجراءات المحلية مسارًا نسبيًا من github.workspace، ولهذا تحتاج دائمًا تقريبًا إلى actions/checkout أولًا قبل استدعاء إجراء محلي.

وتأتي الإجراءات المخصصة بثلاثة أنواع. فإجراءات JavaScript هي عادةً الأسرع والأبسط للمنطق العادي. وإجراءات Docker تحزم بيئتها الخاصة وتفيد حين تحتاج أدوات محدّدة جدًا، لكن GitHub تلاحظ أنها أبطأ لأن الحاوية يجب أن تُبنى أو تُجلب. والإجراءات المركّبة مثالية حين لا تريد فعلًا سوى «هذه الخطوات الخمس معًا، في كل مرة».

وسير العمل القابل لإعادة الاستخدام يُستدعى على مستوى المهمة بـuses:—لا داخل steps. وتُمرَّر المدخلات بـwith، والأسرار بـsecrets، ويجب أن يعلن سير العمل المستدعى on: workflow_call. ويُوصَل إلى المدخلات في سير العمل المستدعى عبر سياق inputs، ولا تُحقن تلقائيًا كمتغيّرات بيئة. ويمكنك تمرير كل الأسرار المتاحة بـsecrets: inherit حين يكون المستدعي والمستدعى في المؤسسة أو المنشأة نفسها.

ولسير العمل القابل لإعادة الاستخدام أيضًا حوافّ حادة. فأنت تستطيع تداخل عشرة مستويات من سير العمل على الأكثر. ولا يمكن إلا الحفاظ على الصلاحيات أو تقليلها عبر السلسلة—لا رفعها أبدًا. ولا تنتقل الأسرار إلا خطوة واحدة في كل مرة، فإن استدعى A سير العمل B واستدعى B سير العمل C، فلا يحصل C على سرّ من A إلا إذا مرّره A إلى B ومرّره B بدوره إلى C. ويجب ربط مخرجات سير العمل من مخرجات الخطوات إلى مخرجات المهام ثم من مخرجات المهام إلى مخرجات سير العمل.

وقوالب سير العمل على مستوى المؤسسة ميزة منفصلة. فإن وضعت القوالب في مستودع .github تملكه المؤسسة تحت workflow-templates/، استطاع GitHub عرضها حين ينشئ الناس سير عمل جديدة. وتعيش البيانات الوصفية للقالب في ملف مطابق .properties.json. وهي مفيدة لتوحيد سير عمل التمهيد عبر مستودعات كثيرة دون إجبار كل شيء على المرور عبر ملف سير عمل واحد عِملاق قابل لإعادة الاستخدام.

الذاكرات المؤقتة والمخرجات والملخصات

الجانب الذاكرة المؤقتة المخرَج
الغرض إعادة استخدام الاعتمادات عبر التشغيلات حفظ مخرجات البناء أو نقلها
المفتاح مفتاح حتمي (مثل بصمة ملف القفل) الاسم + معرّف التشغيل
العمر يُطرد عند مطابقة مفتاح أو بعد 7 أيام افتراضيًا retention-days قابل للتهيئة
الاستخدام بين المهام يُستعاد بالمفتاح في أي مهمة يُنزَّل بالاسم في المهام اللاحقة
المحتوى المعتاد node_modules و.cache واعتمادات البناء التغطية، والملفات الثنائية، ولقطات الشاشة، والسجلات

تحلّ الذاكرات المؤقتة والمخرجات مشكلتين مختلفتين. فالذاكرة المؤقتة لإعادة استخدام الاعتمادات أو الملفات الوسيطة عبر تشغيلات سير العمل، بمفتاح حتمي. والمخرَج حزمة ملفات مُسمّاة ينتجها تشغيل سير عمل—أشياء مثل تقارير التغطية، ونتائج الاختبارات، والملفات الثنائية، ولقطات الشاشة، أو مخرجات البناء التي تريد حفظها أو فحصها أو تسليمها إلى مهمة لاحقة. والخلط بين الاثنين من أخطاء GitHub Actions الكلاسيكية.

وفي التخزين المؤقت، الآلية المهمة هي ترتيب البحث. فيبحث actions/cache عن key مطابق تمامًا أولًا، ثم يجرّب restore-keys من الأكثر تحديدًا إلى الأقل، وعند المطابقات الجزئية يستخدم أحدث ذاكرة مؤقتة أُنشئت. وهذا يجعل بصمات ملفات القفل الأساس المعتاد لمفاتيح الذاكرة المؤقتة، مع بادئات أوسع كبدائل.

وتُرفع المخرجات بـactions/upload-artifact وتُنزَّل بـactions/download-artifact. ويمكنك تسميتها، وضبط retention-days، وتنزيل كل المخرجات من تشغيل أو مخرَج مُسمّى واحد فقط، واستخدام المخرجات لنقل الملفات بين المهام. وإن أردت تنزيل مخرجات من تشغيل آخر أو سير عمل آخر، فتحتاج رمز وصول ومعرّف تشغيل.

ويدعم GitHub Actions أيضًا ملخصات المهام عبر GITHUB_STEP_SUMMARY. وعند انتهاء المهمة، يجمع GitHub ملخصات الخطوات في ملخص مهمة واحد في صفحة تشغيل سير العمل. وهذا رائع للتقارير المقروءة بشريًا—إجماليات الاختبارات، ونسب التغطية، والروابط، وملاحظات النشر—كي لا يضطر الناس إلى التجوّل في السجلات كأنهم سكّان أنفاق.

المصفوفات والتوازي والتحكم في التزامن

المصفوفات هي كيفية توزيع مهمة منطقية واحدة على توليفات كثيرة من المتغيّرات مثل نظام التشغيل، أو إصدار وقت التشغيل، أو المنطقة، أو البيئة الهدف. ويمكنك تنقيحها بـinclude وexclude، ويُعالَج include بعد exclude، ما يعني أنك تستطيع إعادة إضافة حالات خاصة عن قصد. ويمكنك أيضًا التحكم في السلوك بـfail-fast وcontinue-on-error. وقيمة fail-fast الافتراضية true، فقد يلغي إخفاق صلب واحد مهام المصفوفة الشقيقة المنتظرة أو الجارية.

ويمكنك أيضًا تقييد المصفوفة بـmax-parallel، وهو مفيد حين تكون مشغّلاتك شحيحة أو تصطدم المهمة بحدّ معدّل خارجي. وتوثّق GitHub أيضًا حدًّا صلبًا للمصفوفة عند 256 مهمة لكل تشغيل سير عمل، فالإجابة عن «هل أستطيع توليد مصفوفة بـ900 مسار لأنها تبدو أنيقة» هي، والحمد لله، لا.

وconcurrency هو سطح التحكم الكبير الآخر. وتضمن مجموعة التزامن ألا يعمل في وقت واحد إلا سير عمل أو مهمة واحد في تلك المجموعة، ويمكن لتشغيل جديد بالمفتاح نفسه أن يلغي القديم. وهذا مفيد خصوصًا لعمليات النشر، أو CI القائم على الفروع، أو سير عمل طويلة الأمد لا يهمّ فيها إلا أحدث تشغيل.

عمليات النشر والبيئات

البيئات هي حواجز النشر في GitHub Actions. فيمكنك ربط مهمة ببيئة، وتخزين أسرار ومتغيّرات خاصة بالبيئة، وفرض قواعد حماية النشر مثل الموافقات اليدوية، ومؤقّتات الانتظار، وقيود الفروع، وحتى قواعد حماية مخصصة عبر تطبيقات GitHub. وعلى المهمة التي تشير إلى بيئة أن تستوفي تلك القواعد قبل أن تعمل أو تصل إلى أسرار البيئة.

هنا يصبح GitHub Actions منصّة نشر فعلية بدل «CI بوصول إلى الصدفة». فيمكنك فصل staging عن production، وطلب مراجعين للإنتاج، وتسلسل استخدام البيئة بـconcurrency. وتلاحظ توثيقات الحدود في GitHub أيضًا أن تشغيلات سير العمل قد تنتظر حتى 30 يومًا على موافقات البيئة، وهو إما ميزة مؤسسية مفيدة وإما نصب تذكاري لتردّد تنظيمي، حسب مكتبك.

وهذه مهمة نشر نموذجية:

jobs:
  deploy:
    runs-on: ubuntu-latest
    needs: test
    environment: production
    concurrency:
      group: deploy-production
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write

    steps:
      - uses: actions/checkout@v5
      - name: Authenticate to cloud with OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-prod
          aws-region: us-east-1
      - run: ./deploy.sh

والجزء المهم ليس إجراء السحابة نفسه. بل الشكل—بيئة صريحة، وتزامن صريح، وصلاحيات رمز صريحة. هذه هي النسخة الناضجة من أتمتة النشر.

الأمان

يبدأ أمان GitHub Actions من GITHUB_TOKEN. وتوصي GitHub بمنحه الحد الأدنى من الصلاحيات المطلوبة، ويقول مرجع الاستخدام الآمن صراحةً إن الافتراضي الجيد وصول للقراءة فقط إلى محتويات المستودع، ثم رفع الصلاحيات للمهام التي تحتاج أكثر فعلًا فقط. وهناك قاعدة أخرى يسهل تفويتها—إن حدّدت أي صلاحية صراحةً، أصبحت أي صلاحية لم تحدّدها none.

كما يستطيع أي إجراء الوصول إلى GITHUB_TOKEN عبر github.token حتى إن لم تمرّر له secrets.GITHUB_TOKEN صراحةً. ولهذا تكون كتل permissions: على مستوى المهمة بهذه الأهمية. فالرمز موجود سواء تذكّرته أم لا. كما تخفض GitHub صلاحيات طلبات السحب الواردة من تفرّعات إلى القراءة فقط في الحالة الشائعة، وتعمل سير عمل طلبات السحب التي يُحفّزها Dependabot كما لو جاءت من تفرّع—GITHUB_TOKEN للقراءة فقط، وبلا أسرار.

والأسرار تستحق ثقة أقل قليلًا مما يمنحها الناس. فتقول GitHub إن الأسرار متغيّرات مخزّنة على مستوى المؤسسة أو المستودع أو البيئة، ولا تحصل سير عمل على الوصول إليها إلا حين تضمّنها صراحةً. لكن GitHub تحذّر أيضًا من أن الحجب التلقائي غير مضمون في كل التحويلات، وتشير إرشادات الاستخدام الآمن لديهم إلى أن كل من يملك وصول كتابة إلى المستودع يملك وصول قراءة إلى كل أسرار المستودع. وللقيم المولَّدة أو غير السرية التي ما زالت تحتاج إخفاءً، استخدم ::add-mask::.

وحقن الشيفرة هو الفخ الكبير التالي. فتحذّر توثيقات الأمان في GitHub صراحةً من أن بيانات يتحكم بها المهاجم قد تتدفّق عبر سياقات مثل github.event.issue.title أو github.event.pull_request.body. وإن أدخلت تلك القيم مباشرةً في نص صدفة، قيّمت GitHub التعبير أولًا ثم فسّرت الصدفة النتيجة، وهكذا يحدث حقن الأوامر. والنمط الأكثر أمانًا هو تمرير القيم غير الموثوقة كمدخلات إجراء أو عبر متغيّرات بيئة وتنصيصها بشكل صحيح.

وإجراءات وسير عمل الأطراف الثالثة مخاطرة في سلسلة التوريد. ومرجع الاستخدام الآمن في GitHub صريح—فإجراء طرف ثالث واحد مخترق قد يكشف أسرار المستودع ويسيء استخدام GITHUB_TOKEN. والتخفيف الموصى به هو تثبيت الإجراءات على بصمة إيداع كاملة الطول، وهي ما تسمّيها الشكل الوحيد غير القابل للتغيير لإصدار إجراء. فالوسوم مريحة، لكنها قابلة للتحريك. وتتيح GitHub أيضًا للمؤسسات والمستودعات فرض سياسات تحدّ من الإجراءات وسير العمل القابل لإعادة الاستخدام المسموح بها، بل واشتراط تثبيت البصمات كاملة الطول.

ويستحق CODEOWNERS أن يُستخدم لـ.github/workflows. فـGitHub توصي به صراحةً كطريقة لطلب مراجعة تغييرات سير العمل. وهي من أرخص الطرق لمنع «تعديلات YAML الصغيرة» من تغيير نموذجك الأمني بهدوء.

وOIDC هو الافتراضي الصحيح لمصادقة السحابة الآن. فتقول توثيقات GitHub إن سير العمل يمكنه استخدام رموز OIDC بدل أسرار سحابية طويلة العمر، ويتطلب الإعداد تغييرين كبيرين—ضبط مزوّد السحابة ليثق بـGitHub كهوية موحّدة، وتحديث سير العمل لطلب رمز الهوية وتبادله عبر إجراء المزوّد أو منطق مكافئ. وعمليًا يعني ذلك permissions: id-token: write في المهمة التي تحتاج وصولًا إلى السحابة.

ويدعم GitHub أيضًا إثباتات المخرجات لإثبات منشأ البناء. ولتوليدها في Actions، تتطلب GitHub الصلاحيات الصحيحة، بما فيها id-token: write وcontents: read وattestations: write، ثم خطوة تستخدم actions/attest-build-provenance. وهي مفيدة حين تريد إثبات منشأ موقّعًا للملفات الثنائية أو صور الحاويات أو قوائم SBOM لا مجرد انطباعات وملاحظة إصدار.

حدود تهمّ عمليًا

لـGitHub Actions حدود منصّة حقيقية، والتظاهر بغير ذلك هو ما ينتهي به الناس إلى اكتشافها في الإنتاج. فقد يستمر تشغيل سير العمل حتى 35 يومًا في المجموع. وقد يمتد انتظار موافقة البيئة حتى 30 يومًا. وقد تعمل مهمة مستضافة من GitHub حتى 6 ساعات، ومهمة مستضافة ذاتيًا حتى 5 أيام. وقد تولّد المصفوفة 256 مهمة على الأكثر. ولعمليات الذاكرة المؤقتة حدود معدّل أيضًا، ولـGITHUB_TOKEN حدّ معدّل خاص بواجهة برمجة التطبيقات—1,000 طلب في الساعة لكل مستودع، أو 15,000 للموارد التابعة لحساب GitHub Enterprise Cloud.

وينبغي لهذه الحدود أن تشكّل تصميمك. فمصفوفات الاختبار الضخمة جدًا ينبغي تقليمها أو تقطيعها. ومهام النشر ينبغي أن تستخدم مجموعات تزامن. والعمل طويل الأمد لا ينبغي أن يعيش على مشغّلات GitHub المستضافة القياسية إلا إذا اتّسع داخل الصندوق الزمني. وإن كان لديك إجراء أو سكربت ينهال على واجهة GitHub، فحدّ المعدّل ليس هاجسًا نظريًا—إنه علّة جدولة تنتظر الحدوث.

أنماط عملية تصمد

في CI العادي، استخدم سير عمل منفصلة للهموم المنفصلة—واحد لـCI، وواحد للإصدار، وواحد للنشر، وواحد للصيانة المجدولة—بدل ملف واحد عِملاق يفعل كل شيء. فنموذج الأحداث ومرشّحات المسارات وسير العمل القابل لإعادة الاستخدام في GitHub جيدة بما يكفي لأن يكون «سير العمل الواحد الضخم» في العادة مجرد إخفاق في ضبط النفس، لا متطلبًا منصّيًا.

ولمعايير المؤسسة، فضّل سير العمل القابل لإعادة الاستخدام لأنماط المهام الكاملة مثل «البناء والفحص»، أو «النشر إلى بيئة»، أو «نشر حزمة»، واستخدم الإجراءات المركّبة لحزم الخطوات الصغيرة مثل «تهيئة سلسلة الأدوات والمصادقة مع سجل الحزم». وهذا التقسيم يتماشى جيدًا مع الطريقة التي صمّمت بها GitHub هذه الميزات، ويمنع نموذج إعادة الاستخدام لديك من التحوّل إلى منحوتة YAML تجريدية.

وللأمان، ابدأ بصلاحيات GITHUB_TOKEN مقيّدة، وثبّت إجراءات الأطراف الثالثة على بصمات كاملة، وتجنّب المُحفّزات ذات الامتيازات مع سحب شيفرة غير موثوقة، وانقل مصادقة السحابة إلى OIDC، وضع CODEOWNERS على .github/workflows. هذا ليس مبالغة. بل هو الحد الأدنى لئلا تسلّم وصول الكتابة والأسرار لأي إجراء عشوائي من السوق بدا شائعًا في الثانية فجرًا.

وللأداء، استخدم مرشّحات المسارات، والمصفوفات فقط حيث تشتري تغطية حقيقية، وذاكرات مؤقتة بمفاتيح من ملفات القفل، ومجموعات تزامن لسير عمل الفروع والنشر، ومخرجات فقط للأشياء التي تحتاج حفظها فعلًا. فالذاكرات المؤقتة لإعادة الاستخدام عبر التشغيلات. والمخرجات للحفظ والنقل. وخلط هذين النموذجين الذهنيين هو كيف تصبح سير عمل أبطأ وأصعب في الفهم في الوقت نفسه. إنجاز بشري مذهل.

المزالق الشائعة

افتراض أن pull_request يعمل على إيداع رأس المساهم بالضبط. وهو عادةً لا يفعل—فـGITHUB_SHA يشير إلى إيداع الدمج في فرع دمج طلب السحب. وإن احتجت بصمة رأس المساهم، فاستخدم github.event.pull_request.head.sha.

افتراض أن كل شيء في سير العمل المستدعى القابل لإعادة الاستخدام يظهر كمتغيّرات بيئة. وهو لا يظهر. فمدخلات jobs.<job_id>.with التي تُمرَّر إلى سير عمل قابل لإعادة الاستخدام متاحة عبر سياق inputs في سير العمل المستدعى، لا كمتغيّرات بيئة افتراضيًا.

افتراض أن env: يتصرف كلغة برمجة نصية. وهو لا يتصرف كذلك. ففي صيغة سير العمل، لا يمكن تعريف المتغيّرات في خريطة env نفسها بالاعتماد على بعضها بعضًا، ويستخدم GitHub النطاق الأكثر تحديدًا عند تعارض الأسماء.

نسيان أن الإجراءات المحلية تعيش تحت github.workspace. فإن أردت uses: ./.github/actions/my-action، فتحتاج المستودع مسحوبًا أولًا، والمسار نسبي إلى مساحة العمل المسحوبة لا إلى ملف سير العمل لديك.

افتراض أن إعادة تسمية الإجراءات غير مؤذية. فGitHub لا تدعم صراحةً إعادة التوجيه للإجراءات أو سير العمل القابل لإعادة الاستخدام، فإن تغيّر المالك أو الاسم، فشلت مراجع سير العمل القديمة. وسبب إضافي لتثبيت الاعتمادات عن قصد وعدم معاملة مراجع السوق كقوانين طبيعية دائمة.

افتراض أن الأسرار تتدفّق تلقائيًا عبر سلاسل سير العمل القابل لإعادة الاستخدام. وهي لا تتدفّق. فالأسرار لا تنتقل إلا إلى سير العمل المستدعاة مباشرةً إلا إن مرّرت صراحةً في كل خطوة.

افتراض أن المهام داخل الحاويات تتصرف كخوادم Linux عادية. ففي مهمة داخل حاوية، الصدفة الافتراضية لـrun: هي sh لا bash، وهذه طريقة فعّالة جدًا لاكتشاف مدى اعتماد سكربتاتك على خصائص Bash أقسمت أنها محمولة.

الخلاصة

GitHub Actions سهل في البداية وجدّي في التشغيل. وهو على نطاق صغير أداة أتمتة لطيفة قائمة على YAML. وعلى نطاق أكبر يصبح تصميم سير عمل، واستراتيجية مشغّلات، وتحديد نطاق الرمز، ونظافة سلسلة التوريد، واتحاد سحابي، وسياسة نشر—كلها متنكّرة في هيئة نظام CI. والفرق التي تنجح فيه ليست التي تكتب أذكى YAML. بل التي تعامل Actions كبنية تحتية إنتاجية، لأنها كذلك.

الخلاصة السريعة (TL;DR)

النموذج الذهني

سير العمل يحتوي مهام. والمهام تحتوي خطوات. وتعمل المهام بمعزل على مشغّلات منفصلة.

  • سير العمل: يُحفّزه حدث. ويعيش في .github/workflows/.
  • المهمة: تعمل على مشغّل جديد. وتمرّر الحالة إلى مهام أخرى صراحةً عبر outputs وneeds.
  • الخطوة: تُنفَّذ تتابعيًا داخل المهمة. وتتشارك نظام الملفات مع بقية الخطوات في المهمة نفسها.
  • تتدفّق الحالة داخل المهمة عبر GITHUB_ENV وGITHUB_OUTPUT. وتتدفّق بين المهام عبر needs.job_id.outputs.

دلالات المُحفّزات

ليست كل المُحفّزات متساوية.

المُحفّز يعمل على هل يملك أسرارًا؟ مستوى الخطر
push الإيداع المدفوع نعم منخفض
pull_request بصمة إيداع الدمج للقراءة فقط منخفض
pull_request_target الفرع الأساس كاملة مرتفع
workflow_dispatch محفّز يدوي نعم منخفض
  • يستخدم pull_request إيداع الدمج لا إيداع الرأس. ولهذا لا تطابق البصمة ما دفعته.
  • يعمل pull_request_target بأسرار كاملة على الفرع الأساس—لا تسحب شيفرة غير موثوقة هنا أبدًا.

آليات إعادة الاستخدام

ثلاثة مستويات لإعادة الاستخدام، لكل منها مقايضاته.

الآلية النطاق الوصول إلى الأسرار معرّفة في
الإجراء خطوة واحدة المستدعي action.yml
الإجراء المركّب متعددة الخطوات المستدعي action.yml
سير العمل القابل لإعادة الاستخدام مهام كاملة المستدعي + الخاصة به .github/workflows/
  • الإجراءات أصغر وحدة—خطوة واحدة، وهمّ واحد.
  • الإجراءات المركّبة تحزم خطوات متعددة لكنها لا تستطيع تعريف مهام أو أسرار.
  • سير العمل القابل لإعادة الاستخدام يستطيع تعريف مخططات مهام كاملة بكتل permissions الخاصة بها.

أساسيات الأمان

الإعدادات الافتراضية متسامحة. شدّدها.

  • اضبط permissions على read-all أو أضيق على مستوى سير العمل. لا تتّكل على إعدادات المستودع الافتراضية.
  • ثبّت إجراءات الأطراف الثالثة على بصمات إيداع كاملة لا وسوم. فالوسوم قابلة للتغيير.
  • لا تشغّل pull_request_target أبدًا وactions/checkout موجّه إلى github.event.pull_request.head.ref.
  • استخدم OIDC لمصادقة السحابة بدل أسرار اعتماد طويلة العمر.
  • عامل ${{ github.event.*.title }} والحقول الأخرى التي يتحكم بها المستخدم كنواقل حقن—واستخدم دائمًا متغيّرات بيئة وسيطة.
