تمرير الحالة في السياق (Passing State in Context)

ماذا سنتعلّم؟

في الدرس السابق عرّفنا سياقًا لمسار الجذر، لكنّ قيمته كانت ثابتة: كائن نكتبه مرّة واحدة عند إنشاء الموجّه فلا يتغيّر بعد ذلك. التطبيق الحقيقي لا يعمل بهذه الطريقة؛ حالة المستخدم تتبدّل حين يدخل وحين يخرج، ومصدرها الأصلي ليس الموجّه بل React نفسها: خُطّاف useState، أو موفّر مصادقة، أو خُطّاف يعيد بيانات المستخدم. والمعضلة أنّ الموجّه يُنشأ في أعلى main.tsx على مستوى الوحدة، أي خارج أي مكوّن، والخُطّافات لا تُستدعى إلا داخل مكوّنات React.

يبني هذا الدرس الحلّ على ثلاث طبقات: ننقل حالة المستخدم ودالّتَي login وlogout إلى مكوّن App يجلس فوق الموجّه، ثم نمرّرها إليه عبر خاصيّة context في RouterProvider بدل قيمة createRouter الثابتة، ثم نقرأها في المكوّنات بخُطّاف Route.useRouteContext() فنرى الواجهة تتبدّل فورًا. وفي الطريق نصطدم بمشكلة ترتيب حقيقية: تغيير الحالة لا يُعلم الموجّه من تلقاء نفسه، وrouter.invalidate() وحدها لا تكفي إن سبقت تطبيق الحالة؛ فنحلّها بـflushSync.

الشرح

السياق ليس تمرير خصائص من طبقة إلى طبقة

حين تحتاج قيمةً في مكوّن بعيد، فالطريق المعتاد في React أن تمرّرها خصائص (props) من الأب إلى الابن، وعلى كل مكوّن في الطريق أن يعرفها ويقبلها ويعيد تمريرها وإن لم يستعملها. هذا هو تمرير الخصائص المتسلسل (props-drilling): كلّ طبقة تُضاف إلى الشجرة تفرض تعديلًا في الطبقات التي فوقها، ويصير التعديل الواحد موزّعًا على ملفات لا علاقة لها بالموضوع.

السياق في TanStack Router يقطع هذه السلسلة: القيمة تُعلن مرّة واحدة في مسار الجذر، وتسير مع شجرة المسارات نفسها، فيقرؤها مكوّن أيّ مسار — ولو كان في العمق — دون أن يمرّ بها أحد في الطريق. والفرق الثاني أهمّ في درسنا: السياق لا يحمل قيمةً فقط، بل يحمل أيضًا الدوالّ التي تغيّرها، فكل مستهلك يستطيع أن ينادي login أو logout بلا أن يملك الحالة ولا أن يعرف كيف تُخزَّن. والفرق الثالث أنّ النوع يُعلن مرّة، فيراه TypeScript في موضع الضبط وفي كل موضع قراءة.

وليس السياق بديلًا عن سياق React؛ هما يعملان معًا: تأخذ القيمة من خُطّاف أو من موفّر مصادقة داخل React، ثم تضعها في سياق الموجّه لينالها ما لا يستطيع استعمال الخُطّافات، مثل دوالّ التحميل.

نقل نوع User إلى ملف مشترك

كان نوع المستخدم معرَّفًا داخل src/routes/__root.tsx، وقد صار مطلوبًا في ملفين: تعريف السياق في مسار الجذر، ومكوّن App الذي يملك الحالة. فبدل نسخه مرّتين نُخرجه إلى ملف مشترك ونصدّره:

export interface User {
  id: string;
  name: string;
}

الحقلان id وname هما كل ما يعرفه التطبيق عن المستخدم، ولا شيء فيهما يخصّ الموجّه؛ ولهذا موضعهما الطبيعي مجلّد الأنواع لا ملف مسار.

لماذا نحتاج مكوّن App أصلًا؟

الموجّه يُنشأ في main.tsx خارج أي مكوّن، وخُطّافات React لا تُستدعى في ذلك الموضع؛ فلا useState ولا خُطّاف مصادقة. الحلّ أن ننقل RouterProvider إلى مكوّن App، فيصير لنا موضع داخل React نملك فيه الحالة ونستطيع استعمال أيّ خُطّاف، ثم نمرّر ناتجها إلى الموجّه. الموجّه نفسه لا يتغيّر، لكنّ مصدر السياق انتقل من كائن مكتوب في الملف إلى حالة حيّة يملكها React.

القيمة الابتدائية في main.tsx

نبدأ من أعلى main.tsx: الاستيرادات، ثم إنشاء الموجّه بقيمة ابتدائية للسياق.

import { StrictMode, useState } from "react";
import { createRoot } from "react-dom/client";
import "./index.css";
import { createRouter, RouterProvider } from "@tanstack/react-router";
import { routeTree } from "./routeTree.gen";
import type { User } from "./types";
import { flushSync } from "react-dom";

const router = createRouter({
  routeTree,
  context: {
    user: null,
    login: () => {},
    logout: () => {},
  },
});

لاحظ ثلاثة أمور: استيراد flushSync من react-dom وسنعود إليه، واستيراد النوع User من الملف المشترك، وخيار context وقد صار يحمل قيمًا مؤقّتة: user يساوي null، ودالّتان فارغتان لـlogin وlogout. القيم المؤقّتة ليست عبثًا: نوع سياق الجذر يطالب بهذه الحقول الثلاثة، فلو غاب أحدها لما مرّ الملف من TypeScript؛ وهي ستُستبدل لحظة التصيير بالقيم الحقيقية القادمة من App. أمّا كتلة declare module التي تلي إنشاء الموجّه، فهي تُعلِم TanStack Router بنوعه كي تستنتج أنواع المسارات في المشروع كلّه.

الحالة والدالّتان في مكوّن App

هنا يقع قلب الدرس: مكوّن واحد يملك الحالة، ويعرّف الدالّتين اللتين تعدّلانها، ثم يسلّم الثلاثة إلى الموجّه.

function App() {
  const [user, setUser] = useState<User | null>(null);
  async function login(user: User) {
    flushSync(() => {
      setUser(user);
    });
    router.invalidate();
  }
  function logout() {
    flushSync(() => {
      setUser(null);
    });
    router.invalidate();
  }
  return <RouterProvider router={router} context={{ user, login, logout }} />;
}

سطرًا سطرًا: useState<User | null>(null) تبدأ بـnull، أي أنّ الزائر غير مسجّل عند أول تحميل. ودالّة login تأخذ مستخدمًا وتضعه في الحالة، ودالّة logout تعيد الحالة إلى null، وكلتاهما تنادي router.invalidate() بعد التعديل. والسطر الأخير هو العقد الجديد: RouterProvider يقبل خاصيّة context مستقلّة، وهي تُقدَّم فوق القيمة الابتدائية التي مرّرناها إلى createRouter؛ فما دام التطبيق يعمل، السياق الذي تقرؤه المسارات هو هذا الكائن الحيّ لا ذاك الثابت. ولهذا صحّ أن نترك الدالّتين الفارغتين في createRouter: دورهما إرضاء النوع في لحظة الإنشاء فقط.

أمّا async على login فهي بقية من محاولة أوسط سنراها بعد قليل؛ الدالّة لا تنتظر شيئًا الآن، وflushSync هو ما يؤدّي الغرض.

توسيع واجهة السياق في مسار الجذر

في src/routes/__root.tsx يتغيّر أمران: النوع User يصير مستوردًا، والواجهة تكبر من حقل واحد إلى ثلاثة.

import {
  Link,
  Outlet,
  createRootRouteWithContext,
} from "@tanstack/react-router";
import { TanStackRouterDevtools } from "@tanstack/react-router-devtools";
import type { User } from "../types";

interface RootRouteContext {
  user: User | null;
  login: (user: User) => void;
  logout: () => void;
}

export const Route = createRootRouteWithContext<RootRouteContext>()({
  component: RootComponent,
});

login دالّة تأخذ User ولا تعيد شيئًا، وlogout لا تأخذ شيئًا ولا تعيد شيئًا. بهذا يعرف TypeScript في أيّ مسار أنّ login تقبل مستخدمًا وأنّ logout لا تُمرَّر لها وسائط، فما خالف ذلك لا يُترجم. وcreateRootRouteWithContext هي نفسها التي عرفناها، لكنّها الآن تربط الموجّه بعقد أكبر من مجرّد قراءة: عقدٌ فيه حالة ودوالّ تعديلها.

القراءة والاستعمال في المكوّن الجذر

يبقى المكوّن نفسه، وهو الآن أقصر مما كان: لا useState فيه، ولا دالّة محليّة واحدة.

function RootComponent() {
  const { user, login, logout } = Route.useRouteContext();
  return (
    <div className="bg-blue-950 p-2">
      <h1 className="text-2xl font-bold">Root Route</h1>
      {user ? (
        <div className="mb-4">
          <h2 className="text-xl font-bold">Welcome, {user.name}!</h2>
          <button onClick={logout}>Logout</button>
        </div>
      ) : (
        <div className="mb-4">
          <h2 className="text-xl font-bold">Welcome, Guest!</h2>
          <button onClick={() => login({ id: "dwdw", name: "Test" })}>
            Login
          </button>
        </div>
      )}
      <div className="p-2 flex gap-2 mb-4 bg-teal-600 border-2">
        <Link to="/" className="[&.active]:font-bold">
          Home
        </Link>
        <Link className="[&.active]:font-bold" to="/about">
          About
        </Link>
      </div>
      <Outlet />
      <TanStackRouterDevtools position="top-right" />
    </div>
  );
}

السطر الأول يستخرج الحقول الثلاثة من السياق دفعةً واحدة. فإن وُجد user عرض الترحيب باسمه وزرّ الخروج، وإن غاب عرض ترحيب الزائِر وزرّ الدخول. وزرّ الدخول ينادي login بمستخدم وهمي، أمّا زرّ الخروج فيمرّر الدالّة نفسها مباشرة لأنها لا تحتاج وسائط. والمكوّن لا يعرف من أين جاءت الحالة ولا كيف تُحدَّث؛ يعرف فقط أنّ في السياق مستخدمًا ودالّتين. هذا هو الفصل المقصود: العرض في مكان، وملكية الحالة في أعلى مكان واحد.

لماذا لا تتغيّر الواجهة: router.invalidate()

جرّب المؤلف في الفيديو: يضغط زرّ الدخول فلا يحدث شيء، ثم ينتقل إلى مسار آخر فيرى الاسم وزرّ الخروج. السبب أنّ الموجّه حسب سياقه ومساره مرّة واحدة، وما لم يُطلب منه إعادة الحساب فلن يعرف أنّ مصدر القيمة تغيّر تحت يديه؛ فحالة React خارج شجرة الموجّه ولا يصله إشعار عنها.

router.invalidate() هي ذلك الإشعار: تقول للموجّه إنّ ما حسَبه صار قديمًا، فيعيد حساب السياق ويعيد تشغيل ما يعتمد عليه من beforeLoad وloader وتصيير. ولهذا هي ضرورية لما هو أبعد من الواجهة: حارسٌ في beforeLoad يقرأ context.user ليقرّر المنع أو السماح لا يعيد قراره إلا إذا أُعيد تشغيله؛ فإن غاب الإبطال بقي الحارس على جوابه القديم بعد الدخول أو بعد الخروج، فيمنع مسجّلًا أو يسمح لزائر خرج للتوّ.

ترتيب التحديث: لماذا flushSync؟

لكن إضافة router.invalidate() بعد setUser لم تكفِ في المحاولة الأولى، وهذا وجه المشكلة الأهمّ. تحديث حالة React غير متزامن: setUser تسجّل الطلب ولا تطبّقه فورًا، والنفاذ إلى السطر التالي يرى القيمة القديمة. فحين يصل التنفيذ إلى router.invalidate() مباشرةً بعد setUser، يعيد الموجّه الحساب بقيمة user القديمة — أي null — فيبدو الأمر كأنّ شيئًا لم يحدث.

جرّب المؤلف أولًا حلًّا مؤقّتًا: جعل الدالّة async وانتظر جزءًا من الثانية قبل الإبطال، فنجح العرض بعد الانتظار، لكنه وصفه بأنه حلّ ملتوٍ: مدّة لا يضمنها شيء، وتأخيرٌ مصطنع في كل دخول.

الحلّ الصحيح flushSync المستورد من react-dom: تأخذ دالّة، وتطبّق ما فيها من تحديثات حالة تطبيقًا فوريًّا قبل أن يعود التنفيذ إلى السطر التالي. فتصير الحالة محدَّثة عند وصول التنفيذ إلى router.invalidate()، ويعيد الموجّه الحساب بالقيمة الجديدة. ولهذا غُلّف setUser داخل flushSync في الدالّتين، فصار الدخول والخروج يحدّثان الواجهة فورًا بلا حاجة إلى تنقّل.

فحص السياق في أدوات التطوير

إذا شككت في قيمة يراها مسار، فـTanStackRouterDevtools يعرضها: اختر أيّ مسار في الشجرة، وسترى كائن سياقه كما يقرؤه الموجّه — user وlogin وlogout — فيصير التصحيح بالنظر لا بالتخمين.

ويبقى في الموضوع فرعٌ لم نأتِه بعد: حصر السياق بفرعٍ من الشجرة بدل الجذر كلّه، وهو ما سيأتي مع دوالّ التحميل.

النتيجة

اللقطة ملتقطة والتطبيق في حالة زائر: أعلى الصفحة عنوان Root Route، وتحته Welcome, Guest! وزرّ Login أسود، ثم شريط التنقّل الذي يبرز فيه رابط Home لأننا على المسار الرئيسي، وأسفل الشريط محتوى مسار المنشورات. بعد الضغط على الزرّ يتبدّل السطران إلى Welcome, Test! وزرّ Logout في اللحظة نفسها. هذا هو أثر الدرس: حالة واحدة في App، وسياق واحد يقرؤه كل مسار، وإبطال يجعل الموجّه يعيد حساب ما بناه على تلك الحالة.

جرّب بنفسك

  1. اضغط Login وراقب الترويسة: تتبدّل فورًا. ثم أزل flushSync من الدالّتين وأعد التجربة، وسترى الواجهة تبقى على حالها حتى تنتقل إلى مسار آخر.
  2. غيّر المستخدم الوهمي في onClick إلى اسمك ومعرّف آخر، وتأكّد أنّ الاسم الجديد هو ما يظهر في الترويسة، إذ لا شيء في المكوّن يخزّن الاسم بنفسه.
  3. اقرأ السياق من مسار ابن لا من الجذر: افتح src/routes/posts.index.tsx وأضف const { user } = Route.useRouteContext(); داخل RouteComponent واعرض user.name، فتتأكّد عمليًّا من وصول السياق إلى العمق بلا تمرير خصائص.
  4. احذف login وlogout من كائن context في createRouter فقط، لا من الواجهة، ولاحظ خطأ الأنواع؛ ثم أعدهما وافهم أنّ القيمة الابتدائية ليست تفصيلًا شكليًّا.
  5. افتح TanStackRouterDevtools واختر مسارًا داخليًّا مثل posts، ثم اضغط Login وأعد النظر إلى السياق: القيمة التي يراها الموجّه هي الحالة الحيّة نفسها.
