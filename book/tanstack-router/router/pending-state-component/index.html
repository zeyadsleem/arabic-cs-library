ماذا سنتعلّم؟

قبل أن يعرض الموجّه مسارًا جديدًا، ينتظر انتهاء المُحمِّل (loader) الخاص به. فإن كان الجلب يستغرق ثوانٍ، بقي المستخدم أمام شاشة لا تتغيّر: إمّا صفحة خالية عند التحديث الكامل، وإمّا الصفحة السابقة مجمّدة عند التنقّل. لا رسالة ولا مؤشّر، فيظنّ أنّ التطبيق تعطّل.

يبني هذا الدرس مكوّن انتظار (pending) للمسار posts/$postId، ثم يضبط عَتَبَتَي التوقيت اللتين تحكمانه: العتبة التي بعده يظهر المكوّن، والمدّة الدنيا التي يبقى فيها ظاهرًا. والفكرة التي يثبتها الدرس أنّ تجربة الانتظار ليست مسألة شكل فقط، بل مسألة توقيت: إظهار المؤشّر في اللحظة الخطأ قد يكون أسوأ من عدم إظهاره.

الشرح

المشكلة: صمتٌ يستمر ثلاث ثوانٍ

لنُبطئ الطلب عمدًا حتى نرى المشكلة بوضوح. نضيف تأخيرًا صناعيًا داخل دالة جلب تعليقات التدوينة:

export async function getPostComments(id: number) {
  const res = await fetch(`https://dummyjson.com/posts/${id}/comments`);
  // await new Promise((r) => setTimeout(r, 3000));
  if (res.ok) {
    return (await res.json()) as PostCommentsResponse;
  } else {
    throw new Error("Failed to fetch post comments");
  }
}

هذا هو نصّ الملف في فرع الدرس بعد أن انتهى الشرح: السطر الذي يضيف التأخير موجود لكنه معلَّق، لأنّ المؤلف أضافه ليعاين المشكلة ثم عطّله ليعاين الحالة السريعة. حين يكون التأخير فعّالًا وتفتح posts/1 مباشرةً، لا يُصيَّر شيء: الموجّه لم يُكمل تحميل المسار، فلا يوجد ما يعرضه داخل المنفذ. وحين تنتقل إلى التدوينة من قائمة التدوينات، تبقى القائمة كما هي ثلاث ثوانٍ كاملة، فتبدو النقرة كأنها لم تُسجَّل. المشكلتان لهما سبب واحد: لا شيء يخبر المستخدم بأنّ العمل جارٍ.

إعلان مكوّن الانتظار في المسار

الحلّ الأول والأبسط هو خيار واحد في تعريف المسار. هذا ملف المسار كاملًا في فرع الدرس:

import { createFileRoute } from "@tanstack/react-router";
import Post from "./-components/Post";
import { getPost, getPostComments } from "../data/posts";

export const Route = createFileRoute("/posts/$postId")({
  component: RouteComponent,
  pendingComponent: () => <div>Loading...</div>,
  pendingMs: 0,
  pendingMinMs: 500,
  loader: async ({ params }) => {
    const [post, comments] = await Promise.all([
      getPost(+params.postId),
      getPostComments(+params.postId),
    ]);
    return {
      post,
      comments,
    };
  },
});

function RouteComponent() {
  return <Post />;
}

pendingComponent هو المكوّن الذي يحلّ محلّ component الخاص بالمسار أثناء انتظار المُحمِّل. لاحظ أنّه لا يغيّر منطق الجلب: loader بقي كما هو، وما أُضيف هو بديلٌ يُعرض في أثناء عمله. ولاحظ أيضًا أنّ الملف يستعمل Promise.all ليجلب التدوينة وتعليقاتها معًا، فمدة الانتظار هي مدة أبطأ الطلبين لا مجموعهما.

الغرض العملي من pendingComponent ليس التجميل، بل الإفصاح: المستخدم يرى نصًّا يقول إنّ شيئًا يحدث، فيتوقّف عن تكرار النقر. ويمكن أن يكون هيكلًا عظميًا من نوع skeleton يشبه شكل المحتوى القادم، لكنّ المؤلف اكتفى بنصّ Loading... لأنّ الدرس عن التوقيت لا عن التصميم.

أين يُرسم مكوّن الانتظار؟

هذا المكوّن لا يُعرض بدل التطبيق كلّه، بل في موضع المسار نفسه داخل منفذ Outlet التابع لأقرب مسار أب. خذ تخطيط الجذر في فرع الدرس:

      <div className="p-2 flex gap-2 mb-4 bg-teal-600 border-2">
        <Link to="/" className="[&.active]:font-bold">
          Home
        </Link>
        <Link className="[&.active]:font-bold" to="/about">
          About
        </Link>
      </div>
      <Outlet />
      <TanStackRouterDevtools position="top-right" />
    </div>
  );
}

<Outlet /> هو الفتحة التي يضع الموجّه فيها محتوى المسار الابن. وحين يكون ذلك الابن قيد الانتظار، يحلّ pendingComponent محلّ محتواه داخل الفتحة نفسها. لذلك يبقى تخطيط الجذر — العنوان، ورسالة الترحيب، وزرّ الدخول، وشريط التنقّل — ظاهرًا وحيًّا، ولا يفقد المستخدم سياقه ولا مقدرته على المغادرة. هذا الفرق هو ما يميّز حالة الانتظار عن الخطأ: كلاهما يُعرض في المنفذ، لكنّ الانتظار مؤقّت ومقصود.

متى يظهر: الخيار pendingMs

لو ظهر مكوّن الانتظار عند كل تنقّل، لارتجفت الواجهة أمام المستخدم في كل نقرة سريعة. لذلك لا يُظهره TanStack Router فورًا، بل ينتظر مدة عتبة قبل أن يحكم بأنّ التحميل بطيء فعلًا. القيمة الافتراضية ألف ميلي ثانية، أي ثانية واحدة.

مع التأخير الصناعي البالغ ثلاث ثوانٍ، تكون النتيجة: ثانية كاملة لا يظهر فيها شيء، ثم يظهر Loading... نحو ثانيتين، ثم تُعرض التدوينة. أي أنّ السلوك الافتراضي لا يعالج إلا التأخيرات الطويلة، وهذا مقصود: التأخير القصير يمرّ دون أن يراه أحد.

وللتحكّم في هذه العتبة نضع pendingMs في تعريف المسار. في فرع الدرس ضُبطت على 0، فصار المكوّن يظهر في اللحظة الأولى التي يصبح فيها المسار قيد الانتظار، بلا أيّ مهلة. وبهذا صار الانتقال من قائمة التدوينات يعطي إشارة فورية بدل الجمود على الصفحة السابقة.

كم يبقى: الخيار pendingMinMs

العتبة وحدها لا تكفي. لنعكس الحالة: نُزيل التأخير الصناعي، فتصبح البيانات جاهزة في أجزاء من الثانية. هنا يظهر مكوّن الانتظار لحظةً واحدة ثم يختفي، وهي وميضٌ مزعج يلفت النظر إلى شيء لم يحدث. وكلّما كانت العتبة صفرًا زاد هذا الوميض لأنّ المكوّن يُرسم قبل أن تصل البيانات مباشرةً.

لذلك يفرض الموجّه حدًّا أدنى لمدّة العرض: pendingMinMs، وقيمته الافتراضية خمسمئة ميلي ثانية. فإذا ظهر المكوّن، بقي ظاهرًا هذه المدّة على الأقل حتى لو وصلت البيانات قبلها. والشرط المهمّ أنّ هذا الحدّ لا يعمل إلا إذا ظهر المكوّن؛ فإذا لم تتجاوز العتبة، لم يُعرض شيء ولم تُضَف أيّ مدّة.

وضع المؤلف في الفرع pendingMinMs: 500 صريحةً، وهي القيمة الافتراضية نفسها، لكن كتابتها تُظهر للمستخدم كيف تُضبط. ولو رفعناها إلى ثلاثة آلاف، لبقي Loading... ظاهرًا ثلاث ثوانٍ كاملة رغم أنّ البيانات وصلت في أوّل مئة ميلي ثانية؛ وهذا ما يفعله المؤلف في الفيديو ليثبت أنّ الخيار يعمل، لا لأنّه إعداد مناسب للإنتاج.

الخلاصة في جدول واحد:

الإعداد ما يراه المستخدم
الافتراضي: عتبة ألف، حدّ أدنى خمسمئة لا شيء في الثانية الأولى، ثم مؤشّر يبقى ما دام التحميل جاريًا
pendingMs: 0 مع تحميل بطيء مؤشّر فوري يستمر طوال التحميل
pendingMs: 0 مع تحميل سريع مؤشّر يبقى خمسمئة ميلي ثانية ثم يزول، فلا وميض
pendingMinMs: 3000 مؤشّر يبقى ثلاث ثوانٍ ولو وصلت البيانات قبلها
عتبة كبيرة جدًا لا مؤشّر أبدًا، والواجهة تبقى على حالها حتى يصل المسار الجديد

ضبط التوقيت للموجّه كلّه

لا يلزم تكرار الخيارين في كلّ مسار. تُمرَّر القيم الافتراضية عند إنشاء الموجّه نفسه:

const router = createRouter({
  routeTree,
  context: {
    user: null,
    login: () => {},
    logout: () => {},
  },
});

هنا موضع defaultPendingMs وdefaultPendingMinMs: أيّ مسار لا يذكر قيمة خاصة به يرث هاتين القيمتين. والأولوية للمسار على الموجّه، فما تكتبه في تعريف المسار يتغلّب على الافتراضي العام. وهذا التوزيع مفيد عمليًا: اضبط في الموجّه عتبةً قصيرة تناسب تطبيقك، ثم خصّص المسارات البطيئة المعروفة — كتلك التي تجلب قوائم كبيرة — بعتبة أطول أو مكوّن انتظار مختلف. وتذكر التوثيق الرسمية أيضًا الخيار defaultPendingComponent للمكوّن نفسه، فيمكن تعريف مؤشّر عام واحد لكلّ المسارات.

النتيجة

في الصورة نرى التطبيق كما يظهر في أثناء انتظار المسار. تخطيط الجذر حاضر بكلّ عناصره: Root Route، ورسالة Welcome, Guest!، وزرّ Login، وشريط التنقّل الذي يحمل Home وAbout. وفي الموضع الذي كانت ستُعرض فيه التدوينة وتعليقاتها نقرأ Loading... فقط. لاحظ أنّ الشريط لم يختفِ ولم يُعطَّل: بإمكان الزائر أن يغيّر رأيه ويغادر إلى صفحة أخرى قبل أن ينتهي التحميل. هذا هو أثر الدرس كاملًا: تحميل بطيء صار معلومًا ومقروءًا بدل أن يكون صمتًا، والتخطيط بقي قائمًا حوله.

جرّب بنفسك

  1. أعد تفعيل سطر التأخير في getPostComments ثم افتح posts/1 مباشرةً. سجّل ما تراه في الثانية الأولى، ثم بعدها، وقارنه بعد وضع pendingMs: 0.
  2. أزل التأخير وأبقِ pendingMs: 0 مع pendingMinMs: 500، ثم راقب الانتقال من القائمة إلى التدوينة. بعدها اجعل pendingMinMs: 0 وكرّر لترى الوميض الذي يمنعه الخيار.
  3. ضع pendingMinMs: 3000 وافتح تدوينة، ثم لاحظ أنّ المؤشّر يبقى ثلاث ثوانٍ رغم أنّ البيانات وصلت. اسأل نفسك: أيّ تجربة أسوأ، انتظار حقيقي أم انتظار مصطنع؟
  4. انقل الخيارين إلى createRouter باسمَي defaultPendingMs وdefaultPendingMinMs، ثم خصّص مسارًا واحدًا بقيمة تخالف الافتراضي وتحقّق من أنّ الأولوية للمسار.
  5. اكتب مكوّن انتظار بشكل هيكل عظمي يحاكي شكل عنوان التدوينة وفقراتها بدل نصّ Loading...، وقارن الإحساس العام في الحالتين.
