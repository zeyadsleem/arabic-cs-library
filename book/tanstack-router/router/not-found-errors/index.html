ماذا سنتعلّم؟

حين يطلب المستخدم عنوانًا لا يقابله مسار في تطبيقك، لا يصحّ أن يرى شاشةً فارغة أو رسالة خطأ تقنية. يسمّي TanStack Router هذه الحالة «خطأ عدم الوجود»، ويولّدها تلقائيًا حين لا يجد مسارًا يطابق العنوان المطلوب. لكنّ التوليد التلقائي وحده لا يكفي: قد تريد رسالةً بالعربية، أو رابطًا يعيد الزائر إلى الصفحة الرئيسية، أو تخطيطًا يحتفظ بالتنقّل حول الصفحة المفقودة.

في هذا الدرس نتعلّم كيف نتحكّم في هذه الحالة من أعلى إلى أسفل: مكوّن افتراضي على مستوى الموجّه كلّه، ثم مكوّن خاصّ بمسار أب، ثم كيف نحوّل خطأ 404 القادم من الشبكة إلى خطأ عدم وجود بدل أن يظهر كخطأ عام. ونفهم أيضًا الخيار الذي يحدّد أيّ مسار يتولّى العرض.

مكوّن عدم الوجود الافتراضي

حين لا يطابق العنوان أيّ مسار، يرمي الموجّه خطأ عدم وجود من تلقاء نفسه. فإن لم تكن قد أعددت أيّ مكوّن للعرض، لجأ إلى مكوّن بسيط جدًا لا يعرض إلا نصًّا قصيرًا. هذا السلوك مقصود: الرسالة الافتراضية واضحة لكنها ليست مصمَّمة، ولا تعطي الزائر مخرجًا.

لذلك تبدأ المعالجة دائمًا من الأعلى: مكوّن واحد يعرض رسالةً مفهومة، ويُستعمل في كلّ الحالات التي لا يجد فيها الموجّه مكوّنًا أقرب.

تخصيص مكوّن عدم الوجود في المسار الجذر

في ملف المسار الجذر نضيف الخيار notFoundComponent إلى تعريف المسار. المقتطف التالي من فرع الدرس:

export const Route = createRootRouteWithContext<RootRouteContext>()({
  component: RootComponent,
  notFoundComponent: () => <div>Root Not Found.</div>,
});

بعد هذا التعديل، أيّ عنوان لا يطابق شيئًا سيعرض Root Not Found. بدل الرسالة الافتراضية. ولاحظ أنّ المكوّن يُعرَّف بجانب component في الكائن نفسه، فلا حاجة إلى مسار منفصل ولا إلى مكوّن خارجي: الموجّه يبحث عن أقرب تعريف لمكوّن عدم الوجود ويستعمله.

تخصيصه في مسار أب

المسار الجذر ليس المستوى الوحيد. تذكّر بنية تطبيقنا: لدينا settings وهو أب لصفحتَي payment وprofile، وله منفذ تصيير Outlet يعرض الصفحة الابن داخله. فإذا كتب الزائر عنوانًا مثل settings/nonexistent، فالأب موجود والابن مفقود. في هذه الحالة يحتفظ الموجّه بتخطيط settings ويعرض مكوّن عدم الوجود في موضع المنفذ.

لنجعل الرسالة تخصّ هذا القسم، نضيف الخيار في ملف _settingsLayout.settings.tsx:

export const Route = createFileRoute("/_settingsLayout/settings")({
  component: RouteComponent,
  notFoundComponent: () => <div>Settings Not Found</div>,
});

فإذا كان العنوان يبدأ بـsettings/ ثم يتبع بشيء غير معروف، بقيت قائمة الإعدادات ورسالة Settings Not Found داخل التخطيط نفسه، بدل أن تختفي الصفحة كلّها. أما إذا فتح الزائر عنوانًا لا صلة له بـsettings من قريب ولا من بعيد، فلا يجد الموجّه أبًا أنسب من الجذر، فيعود إلى مكوّن الجذر.

تحديد نطاق البحث: notFoundMode

يبقى سؤال: ما معنى «أقرب مسار»؟ الجواب يحدّده الخيار notFoundMode الذي يُمرَّر إلى createRouter عند إنشاء الموجّه:

const router = createRouter({
  routeTree,
  notFoundMode: "fuzzy",
  defaultNotFoundComponent: () => <div>Default Not Found</div>,
  context: {
    user: null,
    login: () => {},
    logout: () => {},
  },
});

القيمة الافتراضية fuzzy تجعل الموجّه يبحث عن أقرب مسار يملك مكوّن عدم وجود، فيحافظ بذلك على أكبر قدر ممكن من التخطيط الذي يتوقّعه الزائر. أما القيمة root فتلغي هذا البحث وتُحيل كلّ الحالات إلى مكوّن المسار الجذر، وهو ما يفيد إذا أردت رسالة موحّدة لا تختلف باختلاف القسم.

ولاحظ الخيار الثاني في المقتطف نفسه: defaultNotFoundComponent يعمل احتياطًا حين لا يملك المسار الأقرب مكوّنًا خاصًّا به، فيرث هذا المكوّن بدل أن تسقط الصفحة إلى الرسالة الأولية. الفرق بينه وبين مكوّن الجذر أنّ مكوّن الجذر مرتبط بمسار الجذر وحده، أما هذا فيُستعمل مع أيّ مسار يحتاج إليه.

إطلاق خطأ عدم الوجود من المُحمِّل

النوع الثاني من هذه الأخطاء لا يخصّ العنوان، بل يخصّ المورد نفسه: التدوينة posts/1 عنوانها صحيح، لكن لا توجد تدوينة بهذا المعرّف. هنا لا يستطيع الموجّه أن يستنتج شيئًا، فأنت من يعلن الخطأ من داخل loader بعد أن تصل الاستجابة من الشبكة.

نستورد الدالة أولًا:

import { notFound } from "@tanstack/react-router";

ثم نغيّر دالة الجلب بحيث ترمي خطأ عدم الوجود بدل الخطأ العام حين تكون حالة الاستجابة 404:

export async function getPost(id: number) {
  const res = await fetch(`https://dummyjson.com/posts/${id}`);
  if (res.ok) {
    return (await res.json()) as Post;
  } else {
    if (res.status === 404) {
      throw notFound();
    }
    throw new Error("Failed to fetch post");
  }
}

الفرق جوهري في تجربة القارئ: قبل هذا التعديل كان كلّ فشل يُعامل كخطأ عام فتُعرض رسالة الخطأ وزرّ إعادة المحاولة، أمّا الآن فحالة 404 وحدها تُحوَّل إلى خطأ عدم وجود، فيتولّاه الموجّه ويعرض المكوّن المعدّ له، بينما تبقى الأخطاء الأخرى على مسارها.

وإذا أردت أن يعرف هذا المسار رسالته الخاصة، أضف notFoundComponent إلى تعريفه. هذا مقتطف من تعريف المسار كاملًا في فرع الدرس:

export const Route = createFileRoute("/posts/$postId")({
  component: RouteComponent,
  onError: (error) => {
    console.error("Error loading post:", error);
  },
  onCatch: (error) => {
    console.error("onCatch", error);
  },
  notFoundComponent: () => <div>Post Not Found</div>,
  errorComponent: ({ error, reset }) => {
    const router = useRouter();
    return (
      <div>
        {error.message} <br />
        <button
          onClick={() => {
            router.invalidate();
          }}
        >
          Retry
        </button>
      </div>
    );
  },
  pendingComponent: () => <div>Loading...</div>,
  pendingMs: 0,
  pendingMinMs: 500,
  loader: async ({ params }) => {
    const commentsPromise = getPostComments(+params.postId);
    const post = await getPost(+params.postId);

    return {
      post,
      commentsPromise,
    };
  },
});

الترتيب في هذا الكائن يوضّح الفكرة: notFoundComponent وerrorComponent وpendingComponent ثلاثة عروض لحالات مختلفة للمسار نفسه — مورد مفقود، وخطأ حقيقي، وانتظار. وكلّ واحد منها يُستعمل في موضعه، فلا تختلط الرسائل.

النتيجة

في الصورة نرى تخطيط الجذر كما هو: الترويسة، ورسالة الترحيب بالزائر، وزرّ الدخول، وشريط التنقّل. وفي الموضع الذي كانت تعرض فيه التدوينة ظهرت رسالة Post Not Found وحدها. هذا هو المقصود من خطأ عدم الوجود: لا تختفي الواجهة، ولا يخرج الزائر من التطبيق، بل يبقى السياق حوله وتصل إليه رسالة دقيقة.

جرّب بنفسك

  1. افتح عنوانًا غير موجود أصلًا مثل settings/unknown، ثم بدّل notFoundMode بين fuzzy وroot وراقب أيّ مكوّن يُعرض في كلّ حالة.
  2. أضف notFoundComponent إلى مسار posts الأب، ثم افتح posts/9999 وقارن النتيجة بمكوّن المسار الابن.
  3. أضف defaultNotFoundComponent يعرض رابطًا إلى الصفحة الرئيسية، ثم احذف مكوّن الجذر مؤقّتًا وتحقق من ظهوره.
  4. اجعل getPost يرمي notFound() لكلّ حالة فشل، لا لحالة 404 وحدها، ثم افتح تدوينة موجودة وأوقف الشبكة لتلاحظ الفرق.
