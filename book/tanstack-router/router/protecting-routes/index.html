ماذا سنتعلّم؟

نضيف في هذا الدرس إلى تطبيقنا أبسط صورة من نظام الحماية: صفحة /about لا يجوز أن يراها زائر غير مسجَّل، وصفحة /login لا يجوز أن يراها مَن سجَّل دخوله بالفعل. لا نملك بعد نظام مصادقة حقيقيًا، لكنّ الموجّه يحمل في سياقه كائن المستخدم ودالتَي الدخول والخروج، وهذا يكفي لبناء الحماية كاملةً والتحقّق منها.

الفكرة التي يثبتها الدرس أنّ الحماية مسألة توقيت لا مسألة واجهة. لا نخفي الروابط، ولا نُخفي مكوّنات الصفحة بعد تصييرها، بل نتحقّق قبل أن يُحمَّل أيّ شيء أصلًا. فإن فشل التحقّق رمينا استثناءً من نوع تحويل (redirect)، فيتوقّف تحميل البيانات وتصيير المسار، ولا يرى الزائر شيئًا من الصفحة المحميّة. ثم نُكمل الحلقة: نحفظ الوجهة التي كان يقصدها في معامل بحث، ونعيده إليها بعد نجاح الدخول، ونغلق الثغرة المقابلة بحيث لا يصل المسجَّل إلى صفحة الدخول.

الشرح

سياق الموجّه هو مصدر الحقيقة

كلّ حماية تحتاج سؤالًا يُجاب عنه بنعم أو لا: هل هذا الزائر مسجَّل؟ والجواب لا يأتي من داخل المسار، بل من الحالة التي تعيش فوق الموجّه كلّه. لذلك يبدأ الدرس من تعريف نوع السياق في المسار الجذر:

interface RootRouteContext {
  user: User | null;
  login: (user: User) => void;
  logout: () => void;
}

export const Route = createRootRouteWithContext<RootRouteContext>()({
  component: RootComponent,
  notFoundComponent: () => <div>Root Not Found.</div>,
});

createRootRouteWithContext يجعل النوع RootRouteContext معروفًا لكلّ مسار في الشجرة، فلا تحتاج إلى تمرير النوع يدويًا عند كلّ تحقّق. وبغير هذا الإعلان يصبح context في beforeLoad مجهول النوع، وتفقد المطابقة بين ما يمرّره الموجّه وما يتوقّعه المسار.

أمّا القيمة نفسها فتُمرَّر عند تصيير الموجّه، وهي في main.tsx حالة React عادية:

function App() {
  const [user, setUser] = useState<User | null>({ id: "1", name: "Test" });
  async function login(user: User) {
    flushSync(() => {
      setUser(user);
    });
    router.invalidate();
  }
  function logout() {
    flushSync(() => {
      setUser(null);
    });
    router.invalidate();
  }
  return <RouterProvider router={router} context={{ user, login, logout }} />;
}

هذا المقتطف هو قلب الدرس. لاحظ الحالة الابتدائية: المستخدم يبدأ بقيمة كائن وهمي، لأنّ المؤلف يريد أن ينطلق من كون الزائر مسجَّلًا ليجرّب الحماية في الاتجاهين. ولاحظ flushSync حول تحديث الحالة: هي تجبر React على تطبيق التغيير قبل السطر التالي، فيرى الموجّه المستخدم الجديد فورًا حين نستدعي router.invalidate() بعده. وinvalidate تجبر كلّ مسار نشط على إعادة التحميل، أي على إعادة تشغيل beforeLoad والـloader، ومن هنا تأتي أهمّية الربط بين الخروج والحماية كما سنرى.

التحقّق في beforeLoad

لكلّ مسار دالتان: loader لجلب البيانات، وbeforeLoad تُنادى قبل loader وقبل التصيير، وتستقبل الخصائص نفسها التي يستقبلها loader، ومنها context وlocation. هذا الترتيب هو سبب اختيارها: حين تعمل، لا يكون قد جُلب شيء ولا رُسم شيء، فتوقّفها يعني توقّف المسار كلّه.

نضيف التحقّق إلى /about:

import { createFileRoute, redirect } from "@tanstack/react-router";

export const Route = createFileRoute("/about")({
  component: RouteComponent,
  beforeLoad: ({ context, location }) => {
    if (!context.user) {
      throw redirect({
        to: "/login",
        search: {
          redirect: location.href,
        },
      });
    }
  },
});

redirect ليست دالة تُعيد قيمة، بل كائن استثناء يُرمى بـthrow. والفرق عملي: لو أعدناه بـreturn لما توقّف شيء، ولو رمينا خطأً عاديًا لانتهى الزائر إلى حدّ الأخطاء (errorComponent). الرمي بـredirect يخبر الموجّه أنّ هذا خروج مقصود من المسار، فيُنفّذ التحويل ولا يُصيَّر المكوّن ولا يعمل loader.

الحفاظ على الوجهة

لاحظ الخيار search داخل التحويل. بغير هذا السطر يعود الزائر بعد الدخول إلى صفحة رئيسية عامّة، فيخسر ما كان يقصده. الطريقة التي يستعملها المؤلف هي تمرير العنوان الحالي كاملًا من location، وهو الكائن الذي يعطيك الموجّه إيّاه في beforeLoad:

        search: {
          redirect: location.href,
        },

فيصل الزائر إلى /login?redirect=%2Fabout، أي إلى صفحة الدخول ومعه عنوان ما أراد. والمهمّ أنّ redirect تقبل الخيارات نفسها التي تقبلها navigate، فإن أردت مثلًا ألّا يبقى عنوان الصفحة المحميّة في سجلّ التنقّل أضفت replace: true. والتوثيق الرسمي ينبّه إلى استخدام location وليس الحالة الداخلية للموجّه، لأنّ تلك قد تتأخّر عن العنوان الفعلي.

مسار login يستقبل الوجهة ويحمي نفسه

الآن ننشئ مسار /login. هو مسار عادي في ملف src/routes/login.tsx، لكنّه يحتاج ثلاثة أشياء: تعريف شكل معاملات البحث، وزرّ يعيد المستخدم إلى وجهته، وحماية معاكسة تمنع المسجَّل من رؤيته.

import { createFileRoute, redirect } from "@tanstack/react-router";
import { zodValidator } from "@tanstack/zod-adapter";
import z from "zod";

const loginSearchParamsSchema = z.object({
  redirect: z.string().optional(),
});

export const Route = createFileRoute("/login")({
  component: RouteComponent,
  validateSearch: zodValidator(loginSearchParamsSchema),
  beforeLoad: ({ context, search }) => {
    if (context.user) {
      throw redirect({ to: search.redirect || "/" });
    }
  },
});

المخطط يجعل redirect معاملًا اختياريًا معروف النوع، وvalidateSearch يتحقّق منه أثناء مطابقة المسار. الترتيب هنا مقصود: المطابقة والتحقّق من معاملات البحث يسبقان beforeLoad، لذلك يجد التحقّق قيمة search.redirect جاهزة ومُتحقَّقًا منها، ولا يحتاج إلى قراءة العنوان يدويًا. ثم يأتي التحقّق المعاكس: إن كان المستخدم موجودًا فالزائر مسجَّل، فلا معنى لصفحة الدخول، فنرمي تحويلًا إلى وجهته المحفوظة أو إلى الصفحة الرئيسية /. بغير هذا الحظر يبقى /login متاحًا للمسجَّل، وهي حالة غير متّسقة تعرض عليه زرّ دخول وهو داخل أصلًا.

أمّا المكوّن فيقرأ الثلاثة من خُطّافات المسار نفسه:

function RouteComponent() {
  const { login } = Route.useRouteContext();
  const { redirect } = Route.useSearch();
  const navigate = Route.useNavigate();
  return (
    <div>
      Hello "/login"!
      <button
        onClick={() => {
          login({ id: "dwdw", name: "Test" });
          navigate({ to: redirect || "/" });
        }}
      >
        Login
      </button>
    </div>
  );
}

Route.useRouteContext() يصل إلى دالة login التي مرّرناها في main.tsx، وRoute.useSearch() يعطي المعامل المتحقَّق منه، وRoute.useNavigate() يعطي دالة تنقّل مربوطة بهذا المسار. في الضغطة الواحدة يحدث أمران بالترتيب: تحديث المستخدم في السياق عبر login، ثم التنقّل إلى الوجهة. ولا حاجة إلى كتابة شرط "إن لم توجد وجهة" مرّتين، فالتعبير redirect || "/" يغطّي الحالة التي يفتح فيها الزائر /login مباشرة بلا معامل.

تسجيل الخروج يعيد تشغيل الحماية

الجزء الذي يبدو سحريًا وليس سحريًا: أنت في /about مسجَّلًا، فتضغط زرّ الخروج في التخطيط الجذر. تستدعي logout الدالة router.invalidate() بعد تصفير المستخدم، فتُعاد المسارات النشطة، ومنها /about، فيعمل beforeLoad من جديد ويجد context.user فارغًا فيرمي التحويل. أي أنّ الحماية لا تحتاج إلى مراقب خاصّ لحظة الخروج، لأنّ إبطال الموجّه يمرّ بها مرة أخرى.

حماية مجموعة مسارات بتخطيط واحد

المبدأ نفسه يتوسّع من مسار واحد إلى مجموعة. بدلًا من تكرار beforeLoad في كلّ صفحة محميّة، تُنشئ مسار تخطيط أبًا (مسار بلا مقطع في العنوان)، وتضع التحقّق فيه مرة واحدة، وتُصيّر داخله Outlet. ولأنّ beforeLoad للأب يُنادى قبل beforeLoad لكلّ ابن من أبنائه، فإنّ الرمي فيه يمنع تحميل الأبناء جميعًا. هذا هو الأسلوب الذي يشرحه المؤلف في نهاية الدرس، وهو الأسلوب نفسه الذي تعرضه صفحة التوثيق الرسمية للمسارات المحميّة. أمّا فرع هذا الدرس فيطبّق الحماية على /about وحدها، ويُترك التخطيط المحمي كخطوة تالية.

النتيجة

في الصورة ترى أثر الدرس في التخطيط الجذر: موضع رسالة الترحيب لم يعد يقول Welcome, Guest! ولا يعرض زرّ Login، بل صار يقول Welcome, Test! ويعرض زرّ Logout، وشريط التنقّل يعرض Home وAbout وRandom Word. هذه هي الحالة التي بُنيت من أجلها الحماية: ما دام المستخدم موجودًا في السياق، مرّ beforeLoad في /about بلا اعتراض وظهرت الصفحة، ولو ضغطت زرّ الخروج لعاد الموجّه إلى /login حاملًا معامل الوجهة.

جرّب بنفسك

  1. أعد الحالة الابتدائية في main.tsx إلى null، ثم افتح /about مباشرة وراقب العنوان بعد التحويل: ستجد معامل redirect يحمل مسار الصفحة التي مُنعت.
  2. أضف replace: true إلى التحويل في /about، ثم عد إلى الوجهة بعد الدخول واضغط زرّ الرجوع في المتصفح وقارن السلوك.
  3. احذف validateSearch من مسار /login مؤقّتًا، ثم افتح /login?redirect=/about ولاحظ أنّ نوع search.redirect لم يعد معروفًا وأنّ الإكمال التلقائي في المحرّر يخسر المعلومة.
  4. احذف beforeLoad من /login، ثم سجّل الدخول وافتح /login مباشرة لتقع في الحالة غير المتّسقة التي يمنعها الدرس.
  5. أنشئ مسار تخطيط بلا مقطع في العنوان، وانقل شرط التحقّق إليه، ثم ضع مسارين ابنين تحت التخطيط وتأكّد أنّ حجب الأب يحجب الاثنين معًا.
